# Песочница на пользователя: план

Снимок данных: 2026-11-09, 19:35 UTC. Все числа в документе сняты с живой машины.

## Вердикт

Ты упираешься не в железо, а в отсутствие квот. 11 пользователей на 4 vCPU и 8 ГБ — обычная нагрузка для такого сервиса; проблема в том, что у них **один** контейнер с общим потолком. Один потолок = один общий отказ. Разносим по контейнерам: у каждого свой потолок, свой каталог, свой ключ. Хост при этом остаётся один, и его физический предел никуда не девается — но исчезает общая точка отказа.

## Что сейчас

| Что | Значение |
|---|---|
| Песочница | один контейнер `open-terminal-sandbox` на всех |
| Доступ | `access_grants: principal_id "*"` — то есть у всех 11 пользователей |
| Потолки | 2 ГБ RAM, 1 CPU, 256 процессов на весь контейнер |
| Занято в простое | 31 МиБ |
| Общий рабочий каталог | 6.7 ГБ (`/workspace`), файлы всех в кучу |
| Вложения из чата | кладутся в тот же `/workspace` |

Следствия: два тяжёлых запроса одновременно — контейнер выбивает по памяти, и терминал пропадает **у всех**; файлы видны всем; чужой незакрытый процесс видно всем.

## Что строим

1. **Контейнер на пользователя.** Каждому из 11 — свой контейнер из того же образа, с каталогами только этого пользователя. Прошивка та же: не-root (`1000:1000`), `cap_drop: ALL`, `read_only`, без docker.sock, без монтирования хоста.
2. **Свой потолок.** По умолчанию 1 ГБ RAM и 0.5 CPU на контейнер. Кому мало — поднимаем точечно в файле состояния, не открывая это всем.
3. **Provisioner на хосте.** Скрипт + systemd-таймер раз в минуту: смотрит пользователей в базе WebUI, приводит контейнеры к нужному состоянию. Появился пользователь — создаёт; удалили — гасит и убирает доступ; сменилась роль — снимает доступ.
4. **Соединение в WebUI на каждого.** Своя запись «терминал» в админке с грантом только этому пользователю и своим ключом. В списке моделей и в чате пользователь видит только свою песочницу.
5. **Текущая общая песочница остаётся тебе.** 6.7 ГБ твоих тестов никуда не деваются, грант с неё снимается до администратора. Пользователи начинают с пустых каталогов.

## Из чего состоит

| Файл / юнит | Что делает |
|---|---|
| `/home/ai_service/sandbox-users/template.compose.yml` | шаблон одного контейнера: переменные `SB_SLUG`, `SB_KEY`, пути |
| `/home/ai_service/sandbox-users/state.json` (0600) | карта «пользователь → слаг, контейнер, ключ, лимиты» |
| `/usr/local/bin/sandbox-provisioner.py` | сверка состояния, вызов docker compose, правка соединений через админ-API WebUI |
| `sandbox-provisioner.service` + `.timer` | запуск раз в минуту, лог в журнал |
| `/home/ai_service/sandbox/users/<slug>/{workspace,home,arduino}` | каталоги пользователя на хосте (uid 1000) |

Ядра Arduino не дублируются: базовое дерево лежит один раз, каждому пользователю раскидывается жёсткими ссылками (`cp -al`) — файлы общие на диске, каталоги разные.

## Как это работает по шагам

**Появился пользователь** (роль «Пользователь»): provisioner создаёт каталоги, генерирует ключ, поднимает контейнер, ждёт `healthy`, и только после этого добавляет соединение в WebUI с грантом на этого пользователя. Первые 30–60 секунд после регистрации терминал у него ещё не виден — это лучше, чем соединение, которое отдаёт ошибку.

**Пользователь пишет в чат:** WebUI идёт в его контейнер по внутреннему имени, модель работает в `/workspace` этого пользователя. Вложения чата попадают туда же.

**Пользователя удалили:** provisioner замечает отсутствие в базе, снимает соединение и гасит контейнер. Каталог с файлами живёт ещё N дней (предлагаю 30), потом удаляется. Так случайное удаление аккаунта не убивает файлы сразу.

**Роль сменилась на «Ожидает» или «Админ»:** грант снимается, контейнер стоп. Пользователю без подтверждения песочница не положена.

**Ребут хоста:** все контейнеры с `restart: always` поднимаются сами, таймер всё равно сверяет состояние и чинит расхождения (контейнер есть, а соединения нет — добавит; соединение есть, а пользователя нет — уберёт).

**Админ (ты):** видишь все контейнеры и соединения, можешь поднять лимит любому, поменяв одно число в `state.json`.

## Цифры

| Ресурс | Сейчас | После |
|---|---|---|
| RAM в простое | 31 МиБ на всех | ~31 МиБ × 11 ≈ 340 МиБ |
| Потолок RAM | 2 ГБ на всех | 1 ГБ на каждого, суммарно 11 ГБ потолков |
| Свободно RAM на хосте | 4.1 ГБ | те же 4.1 ГБ минус ~300 МиБ |
| CPU | 1 ядро на всех | 0.5 × 11 = 5.5 доли на 4 ядра |
| Диск | 38 ГБ свободно | образ один на всех, каталоги пользователей пустые |
| Время создания контейнера | — | 3–5 с (образ уже на диске) |

Процессор не «сложится»: доли — это гарантия, а не резервация. Один пользователь не отберёт у другого его половину ядра, но если пятеро одновременно компилируют, все пятеро будут ждать. Это нормальное поведение, а не поломка.

## Трейдоффы

| Решение | Зачем | Чем платим |
|---|---|---|
| Контейнер на пользователя | падение одного не трогает остальных | 11 контейнеров в `docker ps`, ~340 МиБ в простое |
| 1 ГБ по умолчанию | 2 ГБ × 11 не влезают в 8 ГБ физически | тяжёлые сборки (esp32 и крупные скетчи) могут не влезть, поднимаем точечно |
| 0.5 CPU | 11 × 1 = 11 долей на 4 ядра — очередь | медленнее под нагрузкой, зато без голодания |
| Грант только своему пользователю | чужой контейнер не виден и не открывается | 11 записей в админке вместо одной |
| Provisioner раз в минуту | не нужен вебхук от WebUI, работает после ребута и после ручных правок | до минуты задержка на создание и удаление; лишний опрос базы |
| Каталоги на хосте, а не docker volume | видно `du`, можно хардлинкить ядра, легко бэкапить | файлы пользователей лежат в `/home/ai_service` и попадают под обычную логику бэкапов |
| Свой ключ на контейнер | утечка одного ключа не открывает остальные | ключи в `state.json`, файл 0600, в git не идёт |
| Старая песочница остаётся тебе | не делим 6.7 ГБ задним числом | у пользователей старого содержимого нет |

## Что это не решает

- **Физический предел машины.** Если четверо одновременно упрутся в свои 1 ГБ, свободной памяти не останется, и ядро выберет жертву по своему алгоритму — это может быть не песочница. Контейнеры разводят отказы, но не создают память.
- **Диск.** `/workspace` каждого — обычный каталог на том же диске (38 ГБ свободно). Один пользователь, заливший 40 ГБ, роняет сервер целиком. Лечится только квотой файловой системы или контролем размера с алертом. Предлагаю второе: проверка в том же таймере и сообщение в Telegram при превышении 2 ГБ на пользователя.
- **Сеть.** Все контейнеры в одной сети стека, как и сейчас: из песочницы видно `litellm`, `postgres`, `open-webui`. Без учётных данных доступа нет, но если захочешь строже — отдельная сеть, к которой подключён только WebUI.
- **Общее ядро и общий диск.** Настоящая изоляция требует отдельной машины, а не контейнера.

## Порядок работ

**Фаза 1 — шаблон и ручной прогон на одном пользователе.** Собираем compose-шаблон, поднимаем один контейнер вручную, проверяем: uid 1000, `cap_drop` применён, `/etc` только на чтение, нет docker.sock, arduino-cli компилирует. Добавляем соединение через админ-API с грантом на тестового пользователя.
*Проверка:* заходим тестовым пользователем в WebUI, просим терминал выполнить `id` и `ls /workspace` — видим свой uid и пустой каталог; чужой контейнер не виден.

**Фаза 2 — provisioner.** Скрипт + таймер, состояние в `state.json`. Прогон: создать пользователя → контейнер и соединение появились; удалить → соединение убрано, контейнер погашен, каталог остался.
*Проверка:* два прогона подряд не создают дублей; после перезапуска таймера состояние не меняется.

**Фаза 3 — раскатка на 11.** Provisioner создаёт всех, грант с общей песочницы сужается до администратора.
*Проверка:* `docker ps` — 11 контейнеров; у каждого пользователя в чате виден ровно один терминал; общая песочница доступна только тебе.

**Фаза 4 — контроль диска и порядок в репозитории.** Проверка `du` по каталогам пользователей и алерт в Telegram; шаблон, скрипт и юниты в git; скилл обновлён.

**Откат:** на любой фазе — снять соединения пользователей и оставить общую песочницу с грантом всем, как сейчас. 10 минут.
