# Персональная память и песочницы AI-ассистента

**Технический обзор реализации · Состояние на 14 ноября 2026 года, 23:44 UTC**

## Коротко

В системе у каждого пользователя есть собственная рабочая среда и общая для его чатов персональная память. Ассистент получает не отдельные результаты поиска по памяти, а три целых текстовых файла: инструкции, профиль пользователя и сведения из прошлых разговоров. Он может изменять эти файлы через специальный инструмент; сам терминал пользователя видит их только для чтения.

Память встроена в обычные чаты с помощью расширений Open WebUI. Отдельный управляющий процесс создаёт персональные песочницы, подключает их к аккаунтам, поддерживает общие инструкции и контролирует использование диска. Для сортировки записей и поиска противоречий используются дополнительные модели.

**Это работающая система, а не только проект.** На момент обзора активен глобальный фильтр памяти, встроенная память интерфейса выключена, а 13 персональных песочниц находятся в состоянии healthy. При этом отдельные части поведения зависят от модели, автоматический перенос записей не является транзакцией, а полноценное восстановление пользовательской памяти из резервной копии в этом обзоре не подтверждено.

Документ подготовлен для внешнего читателя: реальные сведения о пользователях, адреса, учётные данные, внутренние пути и названия персональных сред намеренно опущены.

## 1. Задача и основные решения

Обычный чат ограничен текущей историей сообщений: новый разговор не обязательно знает, что было важно в старом. Здесь эта проблема решается персональной файловой памятью, которая подключается к запросу перед ответом модели.

Основные решения:

- **Один пользователь — одна рабочая среда.** У каждого свой контейнер, свои рабочие файлы и собственное подключение терминала.
- **Один пользователь — своя память для всех чатов.** Разные чаты одного аккаунта используют одни и те же файлы, а не отдельные копии памяти для каждой беседы.
- **Память подставляется целиком.** Ассистент получает файлы вместе с запросом, а не ищет по ним релевантные фрагменты.
- **Инструкции отделены от фактов.** Правила поведения, сведения о человеке и контекст проектов хранятся раздельно.
- **Запись проходит через контролируемый инструмент.** Свободная запись в каталог памяти из пользовательского терминала запрещена.
- **Расширения используются внутри существующего интерфейса.** Логика памяти реализована через Filter и Tool Open WebUI и существующий управляющий процесс песочниц, а не через отдельный сервис или форк приложения.

### Общая схема

```text
Пользователь отправляет сообщение
              │
              ▼
Open WebUI определяет пользователя
              │
              ▼
Фильтр проверяет привязку к личной среде
              │
              ├── читает инструкции, профиль и память
              ├── обрабатывает состояние и новые записи
              └── добавляет блок памяти к системному контексту
              │
              ▼
Основная модель получает сообщение и контекст
              │
              ├── отвечает пользователю
              └── при необходимости вызывает инструмент памяти
                             │
                             ▼
                Инструмент проверяет операцию
                и изменяет персональные файлы

Отдельно: персональный терминал работает в своём контейнере
и видит каталог памяти только для чтения.
```

## 2. Из чего состоит память

В персональном каталоге находятся три файла в формате Markdown и служебное состояние механизма.

### AGENTS.md — инструкции

Содержит правила работы ассистента: назначение файлов, принципы сохранения, приоритет инструкций, обработку противоречий и формат записей. Здесь же могут находиться персональные инструкции пользователя.

Часть файла управляется общим шаблоном: управляющий процесс регулярно сверяет и обновляет её. Пользовательский текст вне управляемого блока должен сохраняться. Это позволяет централизованно менять общие правила, не заменяя весь файл целиком.

### PROFILE.md — сведения о человеке

Предназначен для устойчивых сведений: например, предпочтений, занятий, семейного контекста и других фактов, полезных в будущих разговорах. Общий размер файла и длина отдельной записи жёстким пределом механизма не ограничены.

### MEMORY.md — сведения из работы и разговоров

Содержит проекты, задачи, решения, договорённости и другой контекст, который может пригодиться позднее. Для него действуют отдельные ограничения:

- мягкий порог всего файла — **10 000 символов**, включая служебный текст и разделители;
- жёсткий предел новой записи — **400 символов**;
- рекомендуемый ориентир — формулировать запись кратко, не теряя смысла, а не заполнять все 400 символов.

### Служебное состояние

Отдельный файл хранит состояние переполнения, отметки о проверенных записях, информацию о переносах и очередь обнаруженных противоречий. Это не отдельная база фактов: он нужен для продолжения действий между ходами и тоже входит в состав резервируемого каталога.

Записи оформляются отдельными пунктами Markdown с выделенным ключом. Для новых записей формат проверяет сам инструмент, а не только инструкция модели. Старые записи в другом поддерживаемом формате могут оставаться читаемыми.

## 3. Как память попадает в запрос

Перед обычным пользовательским ходом глобальный фильтр получает серверную идентичность пользователя и находит соответствующую персональную среду. Клиентский выбор терминала сам по себе не считается доказательством принадлежности памяти.

Далее фильтр:

1. Проверяет идентификатор и активную привязку к личному каталогу.
2. Открывает каталог и три файла с проверками против небезопасных ссылок и подмен.
3. Формирует помеченный блок и добавляет его к первому системному сообщению, сохраняя существующий системный текст модели.
4. Если в запросе уже был предыдущий блок этой памяти, заменяет его, чтобы копии не накапливались.
5. Для обычных пользовательских чатов подключает инструмент памяти к уже имеющимся инструментам, не затирая их список. Если API явно передал собственный набор инструментов, фильтр его не заменяет.

Внутри блока файлы идут в порядке **AGENTS → MEMORY → PROFILE**. Фоновые и внутренние задачи по проверяемым метаданным пропускаются.

Если привязка или чтение не удались, предусмотрен ответ без персональной памяти с предупреждением вместо перехода на общий или чужой каталог. Однако видимость предупреждения зависит от конкретного пути выдачи ответа: сохранённый ответ, потоковые данные и отображение в интерфейсе — не одно и то же. Поэтому нельзя обещать одинаковую доставку предупреждения во всех клиентах и при всех обрывах соединения.

**Когда обновление становится видимым:** после изменения файла результат операции доступен в текущем контексте вызвавшей её модели; актуальные файлы заново подставляются на следующем пользовательском ходе. Изменение файла не переписывает историю уже состоявшегося разговора.

## 4. Как ассистент сохраняет и изменяет сведения

Инструмент памяти поддерживает четыре операции:

- **list** — прочитать актуальные записи выбранного файла;
- **append** — добавить новую запись;
- **replace** — заменить одну конкретную запись;
- **delete** — удалить явно выбранные записи.

Для удаления или замены нужны и номер, и точный текущий текст записи. Если список изменился или выбор неоднозначен, инструмент отказывает и просит перечитать данные. Запись файлов выполняется через временный файл и атомарную замену.

Общие инструкции предписывают модели сохранять устойчивые факты, решения и договорённости самостоятельно, даже без слова «запомни». Перед добавлением она должна посмотреть нужный файл и избегать повторов. Разовые детали, эмоции, догадки и сведения, которые пользователь просил не сохранять, добавлять не следует.

**Важное различие:** формат, проверка входных данных и доступ к файлам обеспечиваются кодом. А решение модели о том, что именно считать важным, следует ли сейчас вызвать инструмент и как кратко сформулировать мысль, остаётся вероятностным. Правило о самостоятельном сохранении не гарантирует, что каждый важный факт действительно попадёт в память или что модель никогда не сохранит лишнего.

## 5. Что происходит при заполнении MEMORY

Предел устроен как мягкий порог, а не как обрезание данных:

1. Если новая корректная запись пересекает 10 000 символов, она сохраняется целиком.
2. Последующие операции, увеличивающие уже заполненный файл, блокируются.
3. Пользователю предлагается точный нумерованный список записей и рекомендация удалить около четверти из них. Это рекомендация, не обязательное число.
4. Пользователь выбирает записи; инструмент сверяет номера и тексты с текущим файлом перед удалением.
5. После изменения показывается актуальный список и запрашивается подтверждение. Если пользователь игнорирует предложение или отказывается, данные не удаляются автоматически; предусматриваются напоминания.

При полном списке фильтр отдельно помечает автоматическое уведомление: модель иногда может вывести собственный сокращённый или дублирующий список. Пользователю предлагается выбирать по точному списку фильтра.

Ранее сценарий проверялся в браузере на синтетических данных: запись, пересёкшая тогдашний порог, сохранялась; выбранные записи удалялись, а после игнорирования показывалось короткое напоминание. Позже порог и предел записи были увеличены. Это свидетельство проверенных сценариев, а не гарантия поведения каждой модели или каждого клиента.

## 6. Автоматическая сортировка и противоречия

### Раскладка между файлами

Фильтр проверяет новые записи в MEMORY и PROFILE и передаёт их дополнительной модели-классификатору. Если та считает назначение записи однозначным, фильтр может перенести её между этими двумя файлами **без отдельного подтверждения пользователя**. За один ход выполняется не более трёх таких переносов. Записи автоматически не переносятся в AGENTS и не удаляются из него.

Сведения о проверенных формулировках сохраняются по хешу текста; повторная проверка такой же записи не гарантируется. Записи свыше установленного внутреннего размера и отдельные служебные элементы пропускаются. Классификация ограничена порциями, а не является полной переоценкой всей памяти на каждом ходе.

**Ограничение надёжности:** перенос состоит из отдельных добавления и удаления, а не из единой транзакции. Код не проверяет поле успешности результата добавления перед последующим удалением; при отказе добавления или конкурентном изменении теоретически возможна потеря либо дублирование записи. Это риск реализации, а не свойство самой файловой схемы.

### Обнаружение противоречий

Дополнительная модель сравнивает часть новых записей с ограниченным числом записей противоположного файла. Если обнаруживается возможное противоречие, система показывает обе записи и просит выбрать, какую оставить. Другая модель разбирает ответ; при неясном ответе удаление не предполагается.

Механизм не сравнивает каждую запись со всеми остальными: на одном проходе проверяется ограниченная выборка новых записей и до пяти записей из противоположного файла на каждую проверяемую запись. Поэтому отсутствие вопроса **не доказывает отсутствие противоречий**. Ошибка классификации или распознавания ответа также возможна.

В ранее проведённом сквозном сценарии с синтетическими противоречащими фактами выбор пользователя привёл к удалению соответствующей проигравшей записи. Этот результат подтверждает конкретный сценарий, но не все варианты формулировок и гонок.

### Какие модели участвуют

Помимо основной модели, отвечающей в чате, текущая конфигурация использует:

- **GPT-6.1 Terra** — классификация новых записей и поиск отдельных противоречий;
- **Perplexity Decision** — разбор отдельных состояний и ответов пользователя, в том числе выбора при конфликте.

Запросы к дополнительным моделям содержат данные, нужные для соответствующей проверки: записи памяти, отдельные пары или контекст текущего взаимодействия. Это означает передачу персональной информации за пределы локального процесса через настроенный шлюз и внешние модельные маршруты. Приватность внешнего провайдера и его политика хранения данным обзором не проверялись.

## 7. Инструкции и их приоритет

В системе есть несколько источников инструкций:

1. Системные правила и настройки, заданные администратором для модели.
2. Общие и персональные правила в AGENTS.md.
3. Фактические сведения из MEMORY и PROFILE.
4. Текущее сообщение пользователя и история диалога.
5. Инструкции конкретного терминала, когда он подключён к чату: что доступно в песочнице, как устанавливать пакеты и передавать файлы.

В пользовательском блоке задано правило: при конфликте старых сведений предпочтение отдаётся MEMORY перед PROFILE; новые явные сведения из текущего разговора важнее устаревшего факта. Спорные записи не следует удалять наугад.

Это **инструкции модели**, а не формальное доказательство того, что она всегда разрешит конфликт правильно. Кроме того, текст памяти помещается в системный контекст, хотя MEMORY и PROFILE задуманы как пользовательские данные. Вредоносная или ошибочная формулировка в таком тексте может влиять на поведение модели; само название раздела не создаёт аппаратной границы доверия.

Администраторские системные промпты моделей остаются включёнными и не заменяются файловой памятью. Редактирование отдельных пользовательских системных промптов в интерфейсе ограничено; при миграции ранее сохранённых пользовательских значений их перенос проверялся отдельно. Это не следует выдавать за доказанный запрет произвольных системных сообщений через любой API.

## 8. Персональные песочницы

Для одобренных аккаунтов роли пользователя и администратора управляющий процесс создаёт отдельные контейнеры с терминальным сервером и персональными рабочими каталогами. Неодобренные аккаунты в эту схему не включаются.

На момент проверки работали **13 контейнеров**, все сообщали состояние healthy. Для всех проверенных контейнеров подтверждены:

- запуск от непривилегированного пользователя;
- корневая файловая система контейнера только для чтения;
- отдельное монтирование каталога памяти только для чтения;
- лимит **1,5 ГиБ оперативной памяти**, общий предел памяти и swap **2 ГиБ**, до **256 процессов**.

Шаблон также задаёт **1 CPU** по умолчанию, запрет повышения привилегий и удаление Linux capabilities с добавлением только необходимой для запуска компоненты. Лимиты являются ограничениями контейнера, а не гарантированными резервами ресурсов: все песочницы используют общие ресурсы одного сервера.

Рабочий каталог пользователя доступен для записи. Можно устанавливать пользовательские пакеты и отдельные программы без административных прав. Установка системных пакетов и изменение общей системы из песочницы не предполагаются. Общим для пользователей является образ контейнера; общего редактируемого слоя с пакетами шаблон не задаёт.

Загруженные в чат файлы могут попадать в рабочий каталог персонального терминала. Для обычных файлов пользователь получает путь и открывает файл через файловую панель интерфейса: обычная Markdown-ссылка на путь рабочего каталога не является проверенным механизмом скачивания.

### Управление жизненным циклом

Управляющий процесс регулярно, примерно раз в минуту, сверяет аккаунты, контейнеры, каталоги и подключения. Для новой среды подключение создаётся после успешной проверки состояния контейнера. Доступ к персональному подключению выдаётся конкретному пользователю.

Выбор терминала в интерфейсе сохраняется на стороне браузера; вспомогательный клиентский код пытается выбрать персональную среду автоматически. Поэтому доступность подключения на сервере и фактический выбор в конкретной вкладке — разные вещи.

Если аккаунт удалён или больше не имеет подходящей роли, среда останавливается. Каталог по текущей политике сохраняется три дня, после чего управляющий процесс может его удалить. Это правило относится и к памяти внутри рабочего каталога; исключение памяти из очистки по размеру не делает её бессрочной.

## 9. Диск и защита каталога памяти

Для обычных рабочих файлов установлен порог **2 ГиБ на пользователя**. Управляющий процесс считает размер и при превышении удаляет старые файлы по времени изменения, пока объём не вернётся к порогу. Это механизм последующей очистки, а не жёсткая файловая квота: кратковременное превышение возможно, а работающие приложения заранее не получают гарантии свободного места.

Некоторые верхнеуровневые каталоги исключены из подсчёта и очистки: память, пользовательские пакеты, инструменты и отдельные каталоги сред разработки. Поэтому реальное место, занятое пользователем на диске, может быть больше 2 ГиБ. При превышении порога защищёнными каталогами предусмотрено уведомление владельцу.

Каталог памяти защищён отдельным монтированием только для чтения внутри контейнера. Это важно не только для запрета редактирования файла: в проверенном синтетическом сценарии отдельная точка монтирования также не позволила переименовать или удалить сам каталог из пользовательской среды. Доверенный инструмент внутри WebUI работает с исходными файлами через другой путь и может их изменять после проверок.

При открытии памяти код дополнительно проверяет серверный идентификатор, активную привязку, ожидаемое расположение каталога, тип и владельца файлов, а также отказывает при опасных символьных и жёстких ссылках. Проверенные сценарии разделения двух пользователей и запрета записи повышают уверенность, но не доказывают отсутствие всех возможных атак.

## 10. Резервное копирование и восстановление

Каталоги персональной памяти, включая служебное состояние, копируются в отдельный **приватный Git-репозиторий**. Настроен ежедневный запуск в **00:00 UTC**; сохраняются версии изменённых файлов, а об успехе или ошибке отправляется уведомление. На момент обзора таймер активен; ранее зафиксирован первичный снимок 13 аккаунтов и подтверждена его отправка в удалённый репозиторий.

Что это даёт:

- копию памяти вне рабочего каталога сервера;
- историю изменений файлов и возможность найти предыдущую версию;
- отдельный механизм резервирования пользовательской памяти, не зависящий только от базы чатов.

Что важно понимать:

- **Приватный репозиторий не означает шифрование содержимого самим механизмом резервирования.** В копии могут быть персональные и чувствительные сведения; доступ к репозиторию и его истории должен быть строго ограничен.
- Удаление факта из текущей памяти не удаляет его из старых коммитов, истории чатов, ранее отправленных запросов к моделям или других копий.
- Ежедневная копия допускает потерю изменений между последним успешным снимком и отказом сервера.
- В текущем скрипте при отсутствии новых локальных изменений выполняется выход без повторной отправки. Если предыдущий push не удался после локального коммита, следующий запуск без новых изменений сам по себе не гарантирует повторный push. Сбой должен быть замечен по уведомлению и устранён.
- Восстановление пользовательских файлов памяти из этой копии на отдельной системе в рамках данного обзора **не выполнялось и не подтверждено**. Наличие коммита и успешный push не равны проверенному восстановлению.

Встроенная память Open WebUI в текущей конфигурации выключена, включая системное подмешивание и фоновую проверку. Её старые записи сохранялись в базе для сверки и возможного отката; выключение не означает их физического удаления.

## 12. Ограничения и реальные риски

1. **Поведение основной модели не полностью предсказуемо.** Она может не сохранить важное, сохранить лишнее, ошибочно пересказать список или заявить об успешной операции без правильной интерпретации результата. Код ограничивает формат и операции, но не гарантирует качество понимания.
2. **Автоматический перенос не атомарен.** Добавление и удаление выполняются раздельно; результат добавления не проверяется перед удалением. Возможна потеря или дублирование записи в неблагоприятном сценарии.
3. **Поиск конфликтов неполный.** Сравнивается ограниченная выборка, поэтому противоречия могут остаться незамеченными. Решения дополнительных моделей также могут ошибаться.
4. **Параллельные изменения не сериализованы полноценно.** Атомарная замена отдельного файла защищает от частично записанного содержимого, но сама по себе не предотвращает потерю изменений при одновременных операциях.
5. **Память увеличивает каждый контекст запроса.** MEMORY ограничен, но PROFILE и AGENTS по общему размеру не ограничены. Большой профиль увеличивает объём передаваемых данных и потенциально задержку и стоимость. Фактическое влияние на кэш запросов в рамках обзора не измерялось.
6. **Персональные данные участвуют во внешних вызовах и резервировании.** Записи передаются модельным маршрутам по необходимости и сохраняются в приватной Git-истории. Это требует доверия к настройкам доступа и поставщикам; политики их хранения здесь не проверены.
7. **Предупреждение и его прочтение — разные вещи.** Сохранение текста, отправка события и показ в открытой вкладке не равны гарантированной доставке и прочтению пользователем. При открытии интерфейса без нового сообщения отдельное напоминание не подтверждено как реализованное.
8. **Песочница — ограничение ущерба, а не доказательство абсолютной изоляции.** Контейнеры разделяют ядро и ресурсы хоста; рабочая сеть общая с частью инфраструктуры. Уязвимости ядра, контейнерного окружения, приложения или ошибки доступа остаются за пределами проверок этого обзора.
9. **Резервная копия ещё не равна восстановлению.** История существует, но отдельное полное восстановление файловой памяти не подтверждено; повторная отправка после неудачного push имеет описанное выше ограничение.

## Итог

Получилась персональная файловая память, встроенная в обычный интерфейс и связанная с отдельными рабочими средами пользователей. Её сильные стороны — понятное разделение инструкций и фактов, прозрачные файлы, контролируемый инструмент записи, запрет прямой записи из песочницы и наличие резервной истории.

Главная граница проходит между **детерминированными проверками кода** и **решениями моделей**. Код может проверить формат записи, принадлежность каталога или точный текст выбранной записи; он не может гарантировать, что модель правильно поняла человека, заметила каждое противоречие или выбрала верное действие. Наиболее конкретное техническое место для улучшения — надёжность автоматического переноса между файлами; для резервирования — проверенное восстановление и обработка неудачной отправки.
