# ВПН упал: две карточки на случай аварии

Короткая шпаргалка на два сценария. Полное описание схемы — `vpn-runbook.md`, тут только
«что делать сейчас». Симптомы пишутся без гаданий: первые три команды отделяют один
сценарий от другого.

## Общая диагностика (делается первой, 3 команды)

```
# 1. с домашней сети / телефона (МТС, Краснодар)
tracert 141.98.166.213          # обрыв внутри сети оператора = блок адреса
curl -sk --max-time 10 https://vpn.esmien.ru:8443/   # 200 = имя и TLS в порядке

# 2. с сервера
ping -c2 1.1.1.1 ; systemctl is-active hysteria-server vpn-socks-relay ; vpn-cfg status

# 3. из Европы через туннель (проверка, что сервер жив и выход работает)
curl -s -x socks5h://127.0.0.1:11091 https://ipinfo.io/json
```

Разбор результата:

| Что видно | Что это |
|---|---|
| tracert обрывается у оператора, из Европы сервер жив | блок IP или подсети |
| tracert доходит, TLS до `vpn.esmien.ru` не поднимается | блок имени (SNI) |
| трафик идёт, но встаёт через ~16 КБ | заморозка TCP, переключаться на UDP-узел |
| всё живо, у одного человека не работает | его клиент/подписка, не сервер |

---

## Сценарий 1. IP или подсеть

Признак: с домашней сети обрыв у провайдера, из Европы сервер отвечает.

1. **Проверить, что дело в адресе, а не в имени:** `curl -sk https://<IP>:8443/` из РФ по IP
   без DNS. Отвечает — имя живое, адрес нет.
2. **Понять масштаб:** один адрес или вся сеть. `tracert` с другого российского выхода
   (мобильный интернет) и `whois <ip>` — если в блоке соседние адреса того же ASN,
   это подсеть, новый IP у того же хостера не поможет.
3. **Вход-прослойка.** Включаем заранее подготовленный дешёвый VPS в чужой сети
   (не Hetzner/OVH/DigitalOcean/Vultr/Scaleway — их сети заморожены целиком):

   ```bash
   # на прослойке: /etc/nginx/stream.d/entry.conf
   server { listen 8443; proxy_pass 141.98.166.213:8443; proxy_timeout 3600s; }
   server { listen 443 udp; proxy_pass 141.98.166.213:443; proxy_timeout 300s; }
   ```
   `nginx -t && systemctl reload nginx`. TLS остаётся сквозным, сертификат не меняется.

4. **Переключить клиентов.** В `brand.json` / подписках заменить адрес узла на адрес
   прослойки и `make_sub.py`. Клиенты подхватят за ≤12 часов сами (`profile-update-interval 12`).
   Подписки к этому моменту должны уже жить на CF — иначе они лежат на забаненном адресе
   и обновление не придёт.
5. **WebUI.** A-запись `ai` → новый адрес, TTL 300 (5 минут). Если WebUI за CF — ничего не делать.

Проверка: `curl -x socks5h://… https://ipinfo.io/json`, `https://www.gosuslugi.ru/` = 200,
`speed.cloudflare.com` на скорость. Время: 10–30 минут, если IP дают, 1–2 часа при переезде.

## Сценарий 2. Домен (блок имени)

Признак: по IP сервер отвечает, по имени TLS не поднимается; либо подписка перестала
обновляться, а уже настроенный узел работает.

1. **Определить, какое имя умерло** — туннельное или подписки:
   - `vpn.esmien.ru:8443` не поднимает TLS, а `esmien.com` (CF) отвечает → туннельное;
   - оба лежат → имя подписки.
2. **Если туннельное имя:** завести новый поддомен (или другой домен), выпустить сертификат,
   поменять `sni`/адрес в подписках, `make_sub.py`. Клиенты подхватят сами, ≤12 часов.
   Эстония, IP, прослойка — не трогаются.
3. **Если имя подписки:** новое имя на CF + Worker (R2 уже наполнен), проверить `/sub/<токен>`.
   Затем одно сообщение в бота: кнопка на страницу-инструкцию и deep-link на новую подписку.
4. **WebUI при блоке апекса:** новый поддомен + A-запись, рассылка в бота.

Проверка: тот же набор curl-ов, плюс `base64 -d | grep -c hysteria2` на выдаче подписки.
Время: туннельное имя — 30 минут, имя подписки — сообщение в бота, остальное решают люди.

---

## Что должно быть готово ДО аварии

Без этих четырёх пунктов оба сценария превращаются в ручную рассылку:

1. Подписки на CF (R2 + Worker + имя на CF).
2. Адреса узлов в подписках указывают на прослойку/имена, а не на голый эстонский IP.
3. Бот с привязкой по `?start=<токен>` и командой `/sub`.
4. Страница-инструкция на CF Pages (VPN + WebUI), короткие id вместо токенов в query.
