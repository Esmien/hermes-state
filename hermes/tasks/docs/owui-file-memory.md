# Файловая память и скиллы для пользователей Open WebUI

Идея: память и навыки агента — не RAG, а md-файлы в воркспейсе конкретного
пользователя (`PROFILE.md`, `.agent/MEMORY.md`, `.agent/skills/*.md`).
Один универсальный системный контракт на всех, изоляция — физическая,
за счёт пер-юзерских песочниц open-terminal, которые уже смонтированы
в `/home/ai_service/ai-stack/ai/sandbox-users/`.

Зачем: штатная «персонализация» WebUI — вероятностная (порог
`rag.relevance_threshold`), факт то подтягивается, то нет, и это не
проверить глазами. Файл читается целиком, лежит в git-воркспейсе,
правится руками и переносится на другой интерфейс как текст.

## Решения (не пересматривать при реализации)

1. **Инъекция детерминированная.** Не «модель должна прочитать файл»,
   а Filter/`inlet` в Open WebUI читает воркспейс сессии и вставляет
   содержимое в контекст до вызова модели. Просьба в системном промпте
   — не гарантия: дешёвая модель забудет, дорогая решит, что помнит.
2. **Запись ограничена протоколом.** Append-only, одна строка на факт,
   префикс даты, потолок ~60 строк, полная перезапись файла запрещена.
   Без этого блокнот превращается в свалку за месяц.
3. **Универсальная модель, а не пер-юзерская.** Данные разные не
   потому, что разные промпты, а потому что разные контейнеры и папки.
4. **Изоляция — предпосылка.** Пока основной `open-terminal` смотрит
   в корень хоста и в `docker.sock`, любой сбой схемы = чтение чужого
   блокнота. Уборка и изоляция не отменяются, они идут первыми.

## Приёмка (три проверки, иначе идея в бэклог)

1. Новый чат того же пользователя помнит факт из файла без напоминания,
   на дешёвом маршруте (`deepseek-flash`), не на terra.
2. После десяти диалогов `git diff` по файлу — вменяемый прирост,
   без мусора и дублей.
3. Из песочницы одного пользователя чужой воркспейс не читается.

## Границы

- Новых контейнеров и сервисов — ноль. Только файл, промпт и один Filter.
- Один вечер. Не прошло приёмку — в бэклог, не в тюнинг.
- После приёмки — стоп и упаковка в артефакт: README, схема, цифры
  (N пользователей, ноль векторной БД, hit-rate кэша, ₽ за диалог).

## Правило против расползания (жёсткое)

**Не «только добавления», а «только подмены через документированную точку».**

Замена встроенной RAG-памяти на файловую — сознательная цель задачи, а не
побочный эффект: уходим от порога релевантности и покупаем стабильный
префикс под кэш. Подмена разрешена, если она делается флагом и расширением:

- **можно:** `memories.enable: false` (один булев в конфиге, ноль патчей)
  + свой Filter/`inlet` через документированный API;
- **нельзя:** патчить код WebUI, форкать образ, подменять узлы без точки
  расширения (tool-loop, сессии, компакция, UI) — вот это форк, и он
  гниёт на каждом апдейте.

Тест перед каждой следующей хотелкой:
- есть документированная точка расширения? Нет → стоп;
- нужно править код WebUI или форкать образ? Да → стоп;
- сколько узлов я уже подменил? Один — фича; третий — ты уже пишешь
  свой WebUI, называй это так и заводи отдельный проект;
- придётся перепроверять после каждого апдейта WebUI? Да → вечный налог.

**Владение поведением — цена, которую платим осознанно.** Пока память
наша, каждый «почему забыл» — наш баг, и апстрим его не починит. Для
шести пользователей это нормальный размен; для «улучшить всё» — нет.

**Ловушка кэша (убивает половину смысла).** Кэш живёт на стабильном
префиксе. Инъекция файла на старте сессии стабильна → хит есть. Если
модель пишет в файл по ходу диалога, содержимое инъекции меняется,
префикс ломается, и кэш-хит падает ровно там, где ты его покупал.
Поэтому: читаем снимок на старте сессии, пишем — в конце или по просьбе,
не после каждой реплики.

Сознательно вырезано из первоначального замаха: ретеншн с проверкой
актуальности (файл на 60 строк правится глазами), git-трекинг для
не-технических пользователей, триггеры на запись/удаление/правку,
валидация и калибровка памяти, «переделать tool-calling». Всё это либо
не окупается, либо уже начинается второй WebUI. Появится реальная боль —
заводится отдельная задача со своим гейтом.
