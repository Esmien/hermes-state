# VPN-сервис одним бэкендом (Docker + SQLite)

## Цель

Собрать всю логику VPN в один сервис с одним репозиторием. Сейчас она размазана по семи скриптам, трём
каталогам с данными и двум git-репо, и именно из этого растут поломки: профиль создаётся без своего
формата выдачи, удалённый человек оставляет живую страницу, статистика живёт отдельным JSON.

Сервис — единственный владелец состояния: люди, ключи, подписки, страницы, конфиг xray, статистика.
Всё остальное на хосте — производные артефакты и транспорт.

## Что заменяет

`users.py`, `make_sub.py`, `make_pages.py`, `make_template.py`, `subgen_api.py`, `stats_collect.py`,
а также ту часть `vpn-bluegreen.py`, которая относится к рендеру конфига (сам blue/green apply остаётся
механикой переключения и переезжает внутрь сервиса как функция).

## Принцип: параметризация вместо хардкода

Предыдущее ТЗ было снято с текущей конфигурации — 24 инбаунда, 9 узлов LTE, конкретные пути. Это
описание сегодняшнего стенда, а не продукта. В сервисе топология должна быть данными:

- инбаунды и их теги — из конфиг-файла/таблицы, а не из кода;
- набор маршрутов и сценариев — тоже данные;
- форма выдачи подписки (`meta` / `whitelist` / `full`) — свойство подписки, а не имя файла в каталоге;
- число узлов в LTE — следствие списка провайдера, а не константа 9.

Проверка качества: стенд с другим числом инбаундов и другим доменом должен подниматься сменой конфига,
без правки питоновского кода.

## Этапы

1. **Каркас**: FastAPI + SQLAlchemy 2.0 async + SQLite, Dockerfile + compose, systemd-юнит, health.
   Миграция `users.json` в базу как первая ревизия Alembic; проверка — рендер даёт те же 169 клиентов.
2. **Рендер конфига + apply**: конфиг xray как производная от базы и конфига топологии; blue/green apply
   с пробой инбаундов; откат при сбое.
3. **Подписки и страницы**: три формы выдачи, base64/clash/sing-box, страницы `/u/<токен>`, удаление
   осиротевших страниц при каждом рендере.
4. **Статистика**: периодический сбор из xray stats, дельты с учётом рестарта контейнера, агрегаты SQL,
   хранение 90 дней.
5. **Админка**: SPA за basic auth — люди, создание, перевыпуск, удаление, ссылки, статистика, аудит.
6. **Вывод старых скриптов**: неделя параллельной работы, затем в `archive/`.

## Репозиторий

Один репо с сервисом, конфигом топологии, миграциями и compose-файлом. Живые секреты и база — вне git;
в репо едет только шифрованный дамп базы. Соседний `vps-infra` остаётся репо восстановления хоста и
перестаёт содержать VPN-логику.

## Риски

- **Apply** — единственное место, где можно уронить доступ. Поэтому он идёт по шагам с локом, пробой
  нового цвета и без переключения при ошибке.
- **Миграция** — только по одному слою, с проверкой артефактов байт-в-байт перед переключением.
- **Соблазн одного большого переезда** — именно так теряют вечер и доступ; переезд по этапам выше.

## Что не входит

Сам xray и маршрутизация трафика, сертификаты, DNS, nginx-конфиги хоста, чужие подписки провайдера.

## Соглашения по развёртыванию

- **nginx — только системный, всегда.** Никогда не в докере: он обслуживает все хосты и сертификаты
  машины, контейнер тут ничего не даёт, только отнимает.
- **xray — системный бинарь под systemd**, не контейнер: ему нужны порты 443/8443 и host network.
- **Бэкенд и фронт — в докере** одним стеком: перезапустил, перекачал, состояние контролируемо.
  Причина выбора именно такая — против дрейфа, а не ради моды.
- Контейнер приложения — `network_mode: host`, чтобы видеть API xray на loopback и слушать свой порт
  для nginx. Изоляции меньше, зато нет проброса портов и сюрпризов с соединением.
- **База — каталог на хосте**, примонтированный в контейнер, не том докера: бэкапить проще.
- **Никакого доступа к `docker.sock` из контейнера.** Перезапуск xray — через файл-заявку и маленький
  хост-юнит, который делает `xray -test` и рестарт. Права на всё машине сервису не нужны.
- Люди добавляются и убираются через API xray на живом сервере; перезапуск нужен только при правке
  маршрутов.
