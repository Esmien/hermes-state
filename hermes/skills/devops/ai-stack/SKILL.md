# AI Stack (this VPS)

## When to Use

Load this skill whenever the task touches the AI service stack on this VPS — LiteLLM, Open WebUI, SearXNG, open-terminal, **the music bot (lyria)**, the host PostgreSQL, Nginx/Certbot TLS, `deploy.sh`, or the `backups/` dumps. It tells you where the stack lives and how to operate it.

The stack is versioned in git: run git as `ai_service` (root gets `dubious ownership`), know what must never be committed, and match the commit shape the owner expects — `references/repo-hygiene.md`.

LiteLLM / Open WebUI / SearXNG / open-terminal stack, with PostgreSQL 17 + pgvector on the host and Nginx+Certbot for TLS. The music bot (lyria) is a **separate** deployment on the same host — see its own section below; it has its own containers, its own Postgres and is NOT covered by `deploy.sh` or the `postgres-backup` timers.

## Location — IMPORTANT

The stack lives at **`/home/ai_service/ai-stack`** on the host.

- The host root is mounted **directly as `/`** — this agent runs on the host root, NOT in a container with a `/mnt/host` bind. **`/mnt/host` does not exist on the host.** Never prefix host paths with `/mnt/host`; use them as-is (`/home/...`, `/etc/...`).
- **`/mnt/host` exists only inside `open-terminal`** (it mounts `/` there, `cwd=/mnt/host`, docker.sock passed through). An agent driving that web terminal reads `/mnt/host/home/ai_service/...` as valid, but the Docker daemon resolves bind sources on the HOST, where the path is absent — it auto-creates an empty directory there and the container mounts a directory over a file (`IsADirectoryError` crash loop). **Never recreate a stack container from open-terminal's shell or with `/mnt/host` paths**; recovery drill in `references/operations.md`.
- Owner: user `ai_service`.

> **open-terminal memory:** single Python process whose anonymous heap ratchets to a high-water mark and is never returned to the OS (CPython + glibc arenas; per-session output is capped at 64 KB, so it is not live sessions). Measured 2026-10: a 191 MB `/files/read` took RSS 85 MB → 592 MB and it stayed there; a second identical read and a 50 MB read reused those blocks without growth — the floor equals the biggest single request ever served, not a cumulative leak. At `mem_limit: 1g` that turned into a memcg OOM-kill 7 min after start; now `mem_limit/memswap_limit: 2g` plus `MALLOC_TRIM_THRESHOLD_=131072`, `MALLOC_MMAP_THRESHOLD_=131072`, `MALLOC_ARENA_MAX=2`, `PYTHONMALLOC=malloc` (verified effective in fresh container processes: 400 MB bytearray alloc/free returns RSS to 9 MB — but it does not shrink the server's already-established floor). That is why `open-terminal-restart.timer` exists: nightly `docker restart open-terminal` at 04:40 UTC (07:40 MSK) via `/usr/local/bin/open-terminal-restart.sh` — the script touches `/var/lib/docker-autorecover/pause` so the incident detector stays quiet, waits for `healthy` (max 120 s) and logs rss_before/rss_after to `/var/log/open-terminal-restart.log` (measured 592 MB → 85 MB). It drops open terminal sessions by design; a manual `docker restart` does not increment `RestartCount`. Its port 8000 is NOT published: test the API with `docker exec open-terminal curl -H "Authorization: Bearer $OPEN_TERMINAL_API_KEY" http://127.0.0.1:8000/...` (host `127.0.0.1:8000` belongs to `lyria-bot`).

Nothing should reintroduce it.

## Media pipeline (images / TTS through LiteLLM)

Images and speech are **not** separate services — both go through the same gateway: Open WebUI → `http://litellm:4000/v1` → an `img.openrouter/*` or `tts.openrouter/*` model group. Read the wiring from `webui_db.config` (never from container env):

```bash
sudo -u postgres psql -d webui_db -Atc "select key||' = '||left(value::text,200) from config where key ~* 'audio|tts|image|stt' and key not like '%api_key%' order by key;"
```

Current shape: `image_generation.engine=openai` + `image_generation.model=img.openrouter/hy-image-v3.5`; `audio.tts.engine=openai` + `audio.tts.model=tts.openrouter/gemini-3.8-flash-lite-tts` + `audio.tts.voice=zephyr`.

- **Gemini TTS supports `response_format=pcm` ONLY.** `mp3` → `400 litellm.BadRequestError: [OI]Exception - Gemini TTS only supports response_format="pcm"`; `wav` → `400 invalid_value ... expected one of "mp3"|"pcm"`. The default (no `response_format`) answers `200` with `content-type: audio/pcm` and **headerless raw PCM** (magic bytes are zeros, ~48 KB/s at 24 kHz 16-bit mono). Do not "fix" TTS by forcing `mp3` — that is the exact request that fails.
- **It plays only because Open WebUI transcodes.** `transcode_audio_to_mp3` in `routers/audio/__init__.py` special-cases `audio/pcm|audio/l16|audio/raw` (24 kHz/16-bit/mono defaults, pydub + ffmpeg, both present in the image) and writes mp3; it returns early and writes the raw bytes when `BYPASS_PYDUB_PREPROCESSING` is set. So the TTS chain depends on that flag staying unset and on ffmpeg/pydub surviving the OWUI upgrade.
- **`voice` is provider-specific.** `zephyr` is a Gemini voice; after pointing `audio.tts.model` at a non-Gemini group the request 400s on the voice. Re-pick the voice whenever the TTS model changes.
- **Probe TTS without ever printing the key** — run inside the gateway, judge content-type and body bytes, not the status code alone:
  ```bash
  docker exec litellm /app/.venv/bin/python -c "import os,json,urllib.request; k=os.environ['LITELLM_MASTER_KEY']; b=json.dumps({'model':'tts.openrouter/gemini-3.8-flash-lite-tts','input':'тест','voice':'zephyr'}).encode(); r=urllib.request.urlopen(urllib.request.Request('http://127.0.0.1:4000/v1/audio/speech',data=b,headers={'Authorization':'Bearer '+k,'Content-Type':'application/json'})); d=r.read(); print(r.status, r.headers.get('content-type'), len(d), d[:12])"
  ```
- **Probe the whole media surface with `scripts/probe-media-endpoints.py`** — `docker exec -i litellm /app/.venv/bin/python - < scripts/probe-media-endpoints.py` (append `--images` to also spend on one image generation). It prints status / content-type / magic bytes for voices, default TTS, `response_format=mp3` and optionally an image, and takes the key from the container env so nothing is printed.
- **Distinguish real use from your own probes** via the spend log: a `metadata::json->>'user_api_key'` of `litellm_proxy_master_key` means the row is yours; OWUI arrives under its own key alias. Zero `/api/audio/speech` lines in `docker logs open-webui` plus only master-key spend rows = the feature is unused, not "working".
- **Image failures are upstream-model flakiness, not gateway glue.** Group failures per model before blaming LiteLLM: `hy-image-v3.5` served every request, `gpt-image-2.5-sunburst` ~2/3, `muse-image` ~1/5. Report the split, and propose a fallback group rather than touching the proxy.
- **Treat `image_generation.enable` and observed traffic as separate facts.** The config flag can read `false` while `/v1/images/generations` answers `200`; find which switch actually governs before "fixing" the flag, and say so.
- **`edge-tts` (openai-edge-tts) is not a working fallback and is not part of lyria.** It is referenced by nothing (no OWUI config, no bot env), its upstream `wss://speech.platform.bing.com` has answered `403 Invalid response status`, and its API key is the image default `your_api_key_here`. Before counting any container as redundancy, exercise it with a real `/v1/audio/speech` call.

## Music bot (lyria)

A second, self-contained deployment on the same host — aiogram Telegram bot + taskiq workers, images built locally (image name == container name).

| Container | Role |
|---|---|
| lyria-bot | Telegram bot + aiohttp webhook server on 127.0.0.1:8000 |
| lyria-generation-worker | taskiq consumer, generation queue |
| lyria-enricher-worker | taskiq consumer, metadata enrichment |
| lyria-postgres / lyria-redis / lyria-rabbitmq | its own datastore — `postgres:17-alpine`, `redis:7-alpine`, `rabbitmq:3-management` |

- **Its own Postgres** — `lyria-postgres`, credentials `lyria`/`lyria`, tables `generations`, `users`, `generation_feedbacks`. This is NOT the host Postgres and NOT `webui_db`/`litellm_db`; it is **not backed up** by the `postgres-backup` timers and not in `backups/postgres/`. Say so explicitly if the user assumes their music data is covered by backups.
- **Startup AMQP errors are expected and benign.** Workers boot before `lyria-rabbitmq` is accepting, so their logs contain an `aiormq.exceptions.AMQPConnectionError: [Errno 111] Connect call failed` traceback, followed seconds later by `Worker ... is listening for tasks...` and `Listening started.` — tenacity reconnects. Do NOT report these as a fault; judge worker health by the presence of the `Listening started.` line after them and by queue consumers, not by the traceback count.
- **Health check = consumers, not logs.** `docker exec lyria-rabbitmq rabbitmqctl list_queues name messages messages_unacknowledged consumers` — a healthy stack shows `1` consumer on `dev.generation.tasks` and `dev.enricher.tasks`, and `0` on every `dead_letter` queue. Anything sitting in `*_dead_letter` is a genuinely failed task worth surfacing. (`rabbitmqctl` can take ~10-60 s to answer — give the call a generous timeout.)
- **`generations` rows left in `pending` are not necessarily broken.** On a graceful restart, in-flight generations are often left as `pending` rows that no queue message backs, so they never drain on their own. They do not block the workers. Before treating them as a bug, check whether anything is actually queued (`messages` column above) and how old they are.
- Restart with `docker restart <container>`; there is no compose file and no systemd unit to use.
- **`edge-tts` runs on `stack-net` but belongs to neither this bot nor OWUI** — it is a leftover TTS attempt for Open WebUI; see "Media pipeline" above.
- **Song generation goes straight to OpenRouter, NOT through LiteLLM.** `src/domains/generation/service.py` POSTs `https://openrouter.ai/api/v1/chat/completions` with `stream: true, modalities: ["text","audio"], audio: {"format":"mp3"}` and the bot's own `OPENROUTER_API_KEY` — so songs never reach `LiteLLM_SpendLogs` and get no gateway limits or fallback. Enrichment *does* use the stack (`ENRICH_URL=https://ai.esmien.qd.je/api/v1/chat/completions`, model `enricher`), so one feature has two different routes to the same provider. If the user asks for unified spend/limits, name this split; routing generation through the gateway is a real change (streaming audio passthrough), not a config tweak.
- **The SSE audio assembly is the delicate part and it is already correct — do not "simplify" it.** Base64 is decoded incrementally with 4-char alignment kept between chunks, cumulative chunks are tracked by an `index`/`offset` cursor (falling back to length), `MAX_AUDIO_B64_LEN` is 40 MB with `MAX_SSE_LINE_LENGTH` deliberately larger (one cumulative line can carry the whole file), and a missing terminal `[DONE]` raises instead of yielding a truncated mp3. Saving is temp-file + atomic rename with sha256 stored, and delivery re-checks size and checksum. A review of this project should say so before listing gaps.
- **`AUDIO_STORAGE_PATH=/data/audio` has NO volume.** `docker inspect lyria-bot lyria-generation-worker --format '{{json .Mounts}}'` returns `[]` for both: mp3s live in the container's writable layer, so any rebuild wipes them while `generations` rows keep a dead `audio_path`, and nothing prunes the layer (~4 MB per song). This is the first structural gap to report — ahead of style remarks — and the fix is a named volume plus a retention sweep in the worker.
- **Credits are derived, not counted:** remaining songs = OpenRouter key balance ÷ `SONG_PRICE` (0.08) from `/api/v1/key`. Elegant, but it lies when the model price changes or the key has no spend limit.
- **Judge this project by its own data, not by vibes.** `docker exec lyria-postgres psql -U lyria -d lyria -tAc "select status, count(*) from generations group by 1"` plus the queue-consumer check above: a deployed-but-idle bot (all rows on one date, `0` messages queued, `1` consumer per queue) is ready, not broken, and "no generations in 72 h" means untested — never present it as a failure or as proof the pipeline works.

## Gateway watchdog (independent of LiteLLM)

- **Docker events already cover `die`/`restart`/`oom`, but not "container Up+healthy, traffic dead".** That gap is closed by `/usr/local/bin/litellm-watchdog.py` + `litellm-watchdog.{service,timer}` (root, oneshot every 60 s, `Requires=sysinit.target` only — never add a `Requires=` naming the service, that makes the timer start it at boot). It probes `http://127.0.0.1:4000/health/liveliness` (`FAIL_THRESHOLD=2` consecutive misses ⇒ DOWN alert, plus a recovery alert), reports the container state in the message, and runs a second check over `LiteLLM_SpendLogs`: last 15 min, ≥10 calls and ≥50 % failures (excluding `/v1/models` and `pass_through_endpoint`) ⇒ «всплеск отказов» alert, throttled 30 min. Alerts go straight to the Bot API (BOT_TOKEN/BOT_OWNER from `/home/ai_service/notifications/.env`), so they arrive while the gateway is dead; state `/var/lib/server-monitor/litellm_watchdog_state.json`, log `/var/log/litellm-watchdog.log`. Test with `--test` (real delivery, returns `message_id`), `--no-send` (prints the alert body), or `LITELLM_WATCHDOG_URL=http://127.0.0.1:4999/...` (fake dead endpoint — fires on the 2nd run).

## Updating one container (e.g. Open WebUI)

Review the delta first (recipe in `references/upstream-release-review.md`), then backup and pull+recreate just that service — never a full `deploy.sh` (it restores DBs):

```bash
docker inspect open-webui --format '{{.Image}}'   # record the CURRENT image id for rollback
sudo -u ai_service /home/ai_service/ai-stack/ai/backup-databases.sh   # ABSOLUTE path; retention keeps newest 3 per DB
cd /home/ai_service/ai-stack/ai
docker compose pull open-webui                    # foreground is fine
docker compose up -d open-webui                   # run with background=true, then process_manage action=wait
```

- **`up -d` must be run with `background=true`.** It returns instantly in reality, but the terminal tool's foreground guard rejects it as an "apparent long-lived server/watch process" — run it backgrounded (add `notify`), then wait on the handle with `process_manage action=wait`. `pull` runs fine in the foreground.
- **Verify** (with fresh output): `docker inspect open-webui --format '{{.State.Health.Status}}'` (expect `healthy`), `curl -s 127.0.0.1:8080/api/version` (returns the version actually running — JSON, not the image tag), `docker inspect open-webui --format '{{.RestartCount}}'` (expect `0`), and `curl -s -o /dev/null -w '%{http_code}' 127.0.0.1:8080/` (expect `200`). Then read the alembic lines: `docker logs open-webui --since 5m | grep -iE 'alembic|migrat|error|traceback'` — schema migrations run on start, so a failed migration shows up there.
  - A clean boot on a patch bump can log only `Context impl PostgresqlImpl` / `Will assume transactional DDL` with **no `Running upgrade` line** — that means no pending migrations, not a broken run.
  - Grepping the logs for `error` also matches unrelated benign noise. In particular `open_webui.routers.audio:get_available_voices ... http://litellm:4000/v1/audio/voices → 404` is structural — LiteLLM does not implement that path (`curl 127.0.0.1:4000/v1/audio/voices` returns 404) and it appears on every Open WebUI version. - Images are pinned only by tag (`:main`), so the replaced image becomes dangling but stays until pruned — rollback = `docker tag <old-id> ghcr.io/open-webui/open-webui:main && docker compose up -d open-webui` (again via `background=true`).

### Updating LiteLLM (its tag is rolling — find out what it ships first)

Same backup → pull → recreate → verify sequence, with three extra checks specific to LiteLLM:

- **Read the version inside the image before committing to a tag.** The container has **no `pip`, no `python` on `PATH` and no `curl`** — only the venv interpreter, so `import litellm; litellm.__version__` fails (the module has no `__version__`) and `pip show` returns `executable file not found`.     -c "import importlib.metadata as m;print(m.version('litellm'))"      # probe a tag WITHOUT touching the live container
- **`main-latest` is a rolling tag that serves pre-release builds — never upgrade to it blindly.** Compare what it resolves to against the newest *stable* release from `curl -s 'https://api.github.com/repos/BerriAI/litellm/releases?per_page=10' | grep -E '"(tag_name|published_at)"'` (ignore every `-rc.`/`-dev.` tag). If `main-latest` ships a dev version, **pin the compose image to the newest stable `ghcr.io/berriai/litellm:vX.Y.Z`** rather than rolling — a one-line compose edit, reversible the same way, and it stops silent dev upgrades on every future pull. Update the services table above when you change the pin.
- **Verify with a real completion through the gateway, not just health.** A bearer key can be read from the container's own env without ever printing it: `docker exec litellm /app/.venv/bin/python -c "import os,json,urllib.request; k=os.environ['LITELLM_MASTER_KEY']; ..."` against `http://127.0.0.1:4000/v1/chat/completions` (and `/v1/models` for a model count). Recipes — filter the 500+ PR bullets programmatically, check route existence in the tag's git tree, diff the provider transformation file between tags — are in `references/upstream-release-review.md`, section 3.

## Signup approval bot (pending users → Telegram)

- **`owui-signup-approver.service`** (root, `Restart=always`, enabled) runs `/usr/local/bin/owui-signup-approver.py`: every `TICK_SECONDS` (120) it reads `select id, name, email, created_at from "user" where role='pending'` straight from `webui_db` and sends the owner (`TG_OWNER=214062001`) a message with `✅ Принять` / `🗑 Удалить`; the same process long-polls `getUpdates` (`allowed_updates=["callback_query"]`) so presses act immediately. Config `/root/.config/owui-signup-approver/env` (600: token, owner, DSN — DB/OWUI passwords are read from `ai/.env` at runtime, not duplicated), state `/var/lib/owui-signup-approver/state.json` (600, offset + notified ids), log `/var/log/owui-signup-approver.log` (logrotate weekly ×8). CLI: `--check`, `--once`, `--whoami`, `--approve <id>`, `--reject <id>`.
- **A systemd timer cannot receive button presses** — callbacks only arrive through a long-poll, and two pollers on one bot token return `409 Conflict` (that is why this bot is separate from `server-monitor-bot`/`BOT_TOKEN`). One process doing tick + long-poll is the correct shape.
- **Approve = SQL, reject = admin API, deliberately.** `UPDATE "user" SET role='user'`, not the API: role is loaded per request from the DB (Redis caches only token revocations), so it applies instantly and needs no JWT. Reject goes through `DELETE /api/v1/users/{id}` because only 3 FKs cascade from `"user"` (`api_key`, `group_member`, `oauth_session`) while ~40 tables (`chat`, `file`, `memory`, `folder`, …) hold `user_id` with no FK — a raw `DELETE` would orphan rows and uploads.
- **Do not expect OWUI webhooks to reach a local listener.** `utils/webhook.py::validate_url` blocks loopback/private targets, so an `auth.signup` webhook would need a public nginx path. Polling the DB avoids that entirely.
- **Pending users have no content**: `get_verified_user` rejects `role='pending'` with 401, so a rejected signup never leaves chat/file orphans. OWUI sends them nothing either — no SMTP configured, no email verification; the bot only ever messages `TG_OWNER`, and every callback checks `from.id`.
- **Every callback and long-poll batch is now logged** (2026-10-23): `callback: action='r' uid=… from=… message_id=…`, `delete confirmation requested/cancelled for …`, `getUpdates: N update(s)`, and a `poll loop was stalled for Ns` warning when an iteration takes >90 s. Before this the `🗑 Удалить` branch wrote nothing on success, so a press that never arrived and a press that was handled looked identical in the log — when the owner says «кнопка не работает», read these lines FIRST and only then suspect the code. A one-off «подвисло и раздуплилось» is consistent with a stuck `urlopen` on the 25 s long poll; a repeat will now leave a timestamped stall line.
- Verify end-to-end by creating a throwaway signup (`POST /api/v1/auths/signup`, returns `role=pending`), forcing a scan (`systemctl restart`), then driving the code path in-process (`importlib` + `handle_callback` with a synthetic `callback_query`) — a real press cannot be automated; `answerCallbackQuery` will 400 `query is too old` on synthetic ids, which is expected. Clean up with the same admin `DELETE`.

## Backups & notifications

- **`Requires=` in a timer's `[Unit]` makes the timer START its service — including at every boot.** Both backup timers originally carried `Requires=postgres-backup.service` / `Requires=postgres-backup-notify.service`; because `timers.target` starts the timers at boot, systemd pulled the services in too, so every reboot produced a full pg_dump pair (~150 MB, ~13 s CPU) plus a Telegram digest. `Persistent=true` was NOT the cause (stamps were current). Activation is already handled by the implicit `Unit=` (`foo.timer` → `foo.service`); the `Requires=` lines were removed. Symptom to recognise: `journalctl -b | grep postgres-backup` shows `Started postgres-backup.timer` immediately followed by `Starting postgres-backup.service` seconds after boot. Verify a fix with `systemctl show <timer> -p Requires` (must not list the service) and by restarting the timer — the service must stay `inactive`.
- `postgres-backup.timer` (02:30 UTC / 05:30 MSK) runs `ai/backup-databases.sh`: pg_dump of `webui_db` + `litellm_db`, then keeps only the newest `RETENTION_COUNT` (default 3) dumps **per database** and deletes the rest — count-based, not date-based, so several backups made on the same day still collapse to the last 3. DB names are derived from the dump filenames; ordering is by mtime.
- `postgres-backup-notify.timer` (03:00 UTC / 06:00 MSK) runs `notifications/monitor.py backup`: sends the newest dump of each DB to the **file bot** (`FILE_BOT_TOKEN`, `@esmien_ai_backups_bot`) and a digest to the **message bot** (`BOT_TOKEN`, `@esmien_vps_notificator_bot`). Dumps > 45 MiB are split adaptively: `split_part_count(size) = ceil(size / TG_DOC_LIMIT)`, so every part stays under the 45 MiB margin (140 MiB → 4 parts, not 2×70 MiB). The join command names all parts and is phrased via `plural_ru(count, ...)` so the wording is right for 3+ parts.
- Notifications live in **`/home/ai_service/notifications/`** (sibling of `ai-stack`, NOT inside it): `monitor.py`, `README.md`, `.env` (mode 640 root:ai_service). `.env` holds `BOT_TOKEN`, `FILE_BOT_TOKEN`, `BOT_OWNER=214062001`, `BACKUP_DIR`, `BACKUP_PATTERN=*.dump`, `DISK/INODE_WARN|CRIT_PERCENT`, `MAX_BACKUP_AGE_HOURS`, `MONITOR_*_STATE_FILE`. Never print it.
- **Prove delivery with the Bot API's own receipt, not the exit code.** Wrap `monitor.urlopen` to log `{"ok", result.message_id}`, then run the command under test — that is an API-level confirmation the message landed. Note a bot cannot message a user until the user pressed Start; `chat not found` means the owner must open the bot first.
- `/etc/cron.d/server-monitor` runs only `alerts` every 10 min. Docker container events (start/die/stop/restart/oom/create) are watched by `server-monitor-events.service` (root, `monitor.py events`, long-running, `Restart=on-failure`) — the old 3-min `containers` polling cron was replaced by this Events API watcher. It batches events in `MONITOR_EVENT_WINDOW_SECONDS` (default 60 s, which doubles as the send throttle) and reconnects with tenacity exponential backoff (tenacity comes from apt `python3-tenacity`, NOT pip — the cron/systemd interpreter is `/usr/bin/python3` and has no pip). Server metrics are on-demand via the bot command `/health` (snapshot taken at request time).
- `server-monitor-bot.service` (root, `monitor.py bot`) long-polls `getUpdates` and answers BOT_OWNER only: `/health`, `/healthcheck`, `/docker_ps`, `/backups`, `/help`, `/start`. `/healthcheck` is a liveness probe for the bot itself — it replies the fixed `200. Poll offset lives in `/var/lib/server-monitor/bot_state.json`; `flock` blocks a second instance. Code change needs `systemctl restart server-monitor-bot`.
- `/backups` also proves validity: the newest dump of each DB is restored into a throwaway DB (`verify_restore_<db>_<pid>_<ts>`, `pg_restore --no-owner --no-privileges` as `sudo -u postgres`) and the temp DB is dropped in `finally`. Dumps Telegram receives split (`webui_db` > 45 MiB) are re-split with the same adaptive count and re-joined first, so the verified bytes are exactly what the recipient gets. ~13 s total (webui ~11 s, litellm ~1 s); the bot sends a «⏳ Проверяю…» ack first.
- **`monitor.py verify` (the nightly 03:15 report) also restores now** — it calls `_restore_into_temp_db` for the newest dump of each DB and prints a «Восстановление (во временную БД)» block; a failed restore lands in «Проблемы» and the closing line reads «✅ Всё в порядке: дампы на месте и восстановлены во временную БД». The nightly `monitor.py backup` digest stays fast and does NOT restore — it is only an upload receipt, so never read its «Сохранены бэкапы» list as proof of restorability.

Observed: one cron run produced two sequential `verify` runs (two `verify_restore_*` DB sets, two reports, restore times differing by ~1 s) because the agent ran the same tool command twice in one execution. A single `systemctl`/`hermes cron runs` status cannot reveal the duplicate.
- `monitor.py backup --dry-run` prints the send plan without calling Telegram. `monitor.py verify` checks the last run and sends a report to the message bot; `monitor.py send "text"` sends arbitrary text.
- **`Result=success` on the notify unit now means the files actually arrived.** `notify_backup` still collects per-file failures into `upload_errors` and renders them as a «⚠️ Не удалось отправить файлы» block inside the digest, but it then **raises `MonitorError`**, which `main()` maps to exit 1 — a lost upload surfaces as `Result=failed`, not a healthy-looking success. ## Memory & disk headroom

- **Host-level filesystem reclamation (Docker/containerd images, build cache, orphan volumes, snap revisions, journald) is a separate procedure — see the `vps-disk-reclamation` skill.** The disk-growth notes below are specific to Open WebUI DB ingest, not to the general «what eats disk» question.

- **RAM: 7.8 GB, and swap is a 4 GiB `/swapfile` (in `/etc/fstab`, `vm.swappiness=10` in `/etc/sysctl.d/99-swap.conf`).** Before this fix there was NO swap at all, and no container had a memory limit (`Memory=0`, cgroup `memory.max=max`) — so one container's spike triggered a **global** OOM kill that took down whatever the kernel picked by `oom_score`, including `open-webui` and `hermes-gateway` itself. If OOM symptoms return, check `/etc/fstab` still has the swapfile and `swapon --show` shows it active — a host reboot without the fstab line silently drops back to zero swap.
- **Attribute the RAM before naming a cause; full procedure in `references/memory-troubleshooting.md`.** Flat RSS across samples + long uptime + `RestartCount=0` = a static allocator footprint, **not** a leak — never propose a restart cron for it. Many anonymous `rw-p` regions of ~64 MiB on a 64 MiB stride in `/proc/<pid>/smaps_rollup` = **glibc malloc secondary arenas** (default max `8 × ncores`, driven by the process's thread count); fix with `MALLOC_ARENA_MAX=2`, which the loader reads at process start so it needs a container **recreate**. Add `mem_limit` at the same time.
- **LiteLLM's ~1.4 GB is retained Python heap, not a leak signature and not libraries — and the reasons are config-specific, so enumerate them instead of guessing. Full breakdown in `references/memory-troubleshooting.md` §7.** Measured here: `[heap]` ~700 MB + anonymous mmap ~650 MB, file-backed ~55 MB only, plus a separate ~50 MB Prisma query-engine child; RSS sampled flat while idle with 31 h uptime and `RestartCount=0` ⇒ static footprint, no restart cron. The triggers to name: `STORE_MODEL_IN_DB=True` with all ~120 models in `litellm_db` (plus the failing 30 s sync loop above), `prometheus_client` installed so per-model/key series accumulate and are never freed, the spend-log in-memory queue, and no Redis ⇒ auth/router/LLM-client caches live in-process. **`litellm_db` is on the HOST PostgreSQL — query it with `sudo -u postgres psql -d litellm_db`, never `docker exec lyria-postgres psql -U postgres`** (that instance's superuser is `lyria` and it does not hold this DB; it answers `FATAL: role "postgres" does not exist`).
- **LiteLLM state lives in `litellm-redis` since 2026-10-19; response caching is deliberately OFF.** `REDIS_HOST/REDIS_PORT/REDIS_PASSWORD` + `depends_on: litellm-redis: condition: service_healthy` move auth-key cache, spend/rate-limit counters and router cooldown/health state out of the process (verify: keys like `spend:user:*`, `{api_key:*}:tokens`, `{model_per_key:*}` appear via `redis-cli --scan`, `DBSIZE` grows with traffic). **Never add `litellm_settings.cache: true`** — proxy-level response caching returns a stored completion for an identical request hash, which corrupts agent tool-calls and hides fresh context; the provider-side prefix cache is what should carry that job. Also set on `litellm`: `MALLOC_ARENA_MAX=2` (the same glibc-arena trap as open-webui) and `MAX_IN_MEMORY_QUEUE_FLUSH_COUNT=5000` / `MAX_SIZE_IN_MEMORY_QUEUE=500` (upstream #12685 spend-queue limits).
- **Owner rules for the gateway — do not propose these as "gaps" again:** (1) **no cross-model fallbacks, ever** — a broken group must surface the error, switching models is forbidden (so `router_settings.fallbacks`/`routing_groups` stay empty; the comment in `litellm/config.yaml` claiming «потом падает на fallback-модель» is stale and wrong); (2) **no budgets/rpm/tpm limits on keys** — the contour is private and single-user, `0/33` keys having limits is deliberate.
- **Prometheus is NOT enabled — `/metrics` answers 404.** The image ships `prometheus_client`, but that alone exposes nothing: LiteLLM needs `litellm_settings.callbacks: [prometheus]` in `config.yaml` (then `curl 127.0.0.1:4000/metrics -H "Authorization: Bearer $LITELLM_MASTER_KEY"`). Never cite "prometheus series accumulating" as a memory cost without checking that callback first — on 2026-10-19 the callback was absent and the claim was wrong. LiteLLM metrics give per-key/team/model spend & tokens, latency histograms, request/status counts, in-flight, cooldowns; enabling needs a restart. **Owner decision (2026-10-19): keep the callback OFF and build any reporting from `LiteLLM_SpendLogs` instead** (`request_duration_ms`, `status`, tokens, spend are all there) — do not re-propose Prometheus/Grafana.
- **Failed `/v1/models` and pass-through calls ARE written to `LiteLLM_SpendLogs` as `status='failure'`** (with `model_group=''`), so raw failure counts grossly overstate real LLM errors: 7 days here showed 94 111 "failures" of 98 013 rows, but 93 686 of them were one day's `/v1/models` burst from a host-side `curl` loop (`requester_ip_address 172.18.0.1`, user-agent `curl/8.18.0`). Always exclude `call_type in ('/v1/models','pass_through_endpoint')` before reporting an error rate.
- **Memory limits on `litellm`:** `mem_reservation: 3g` (soft) + `mem_limit: 3.5g` (hard) + **`memswap_limit: 3.5g`** — set the swap limit too, or Docker silently gives the container `2 × mem_limit` (7 GB here) of swap and a memory spike becomes swap thrash rather than an OOM-kill + restart. Changing limits needs a recreate (`up -d litellm`) or `docker update --memory-swap …` live; verify with `docker inspect … '{{.HostConfig.Memory}}/{{.HostConfig.MemoryReservation}}/{{.HostConfig.MemorySwap}}'` and `cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.swap.max` (must be `0`).
- **`Pss_File` is what mapped libraries actually cost in RAM.** Several GB of libs mapped (torch, torchvision, ctranslate2) measured 38 MB `Pss_File` against ~3 GB `Pss_Anon` — a `:slim` image is a **disk** win, never a RAM fix. Measure before recommending it.
- **Open WebUI runs whatever `webui_db.config` says, not the container env.** `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` / `WHISPER_MODEL` are Dockerfile build-time leftovers — `start.sh` reads only `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`. Read the real engines from the DB (query in the reference file); here embeddings and reranking are external and **local STT is the one genuinely in-process model**. Do not `cat`/`tail` `ai/.env` — grep keys only.
- **Report before you gate: diagnosis → what changed → verification → what is left open, in the message body. Never open a post-work confirmation form (`clarify`) while the report is still unwritten** — the owner reads that as «ты не дал мне плана и результата работ». Present the remediation plan as one point per item — what to do / why / whether it is actually needed (and why not) / consequences — name the ruled-out look-alike suspects (inert Dockerfile env vars, an external client polling the UI; silence on a look-alike reads as an unfinished investigation), and ask the confirmation gate *inside that same message*.
- **Do any data-touching change on a restored copy first, then live.** Keep the copy until the live result is verified, and tell the owner exactly what it is before asking to drop it (`dropdb webui_migtest`) — otherwise «что за БД ты собрался сносить?» is the answer you get.
- **`document_chunk` costs ~20 KB per chunk = a static allocator footprint, **not** a leak; never propose a restart cron for it. Split `Pss_Anon` vs `Pss_File` in `/proc/<pid>/smaps_rollup`, then histogram the anonymous regions by size: many ~64 MiB regions on a 64 MiB stride are **glibc malloc secondary arenas** (default max `8 × ncores`, driven by the process's thread count — an in-process runtime that spawns its own thread pool is the usual trigger). Fix with `MALLOC_ARENA_MAX=2` in the container env; the loader reads it at process start, so it needs a container **recreate**, not a live change. Pair it with a `mem_limit` so a spike kills that container instead of an innocent host process.
- **File-backed libraries cost almost no RAM.** With several GB of libraries mapped (torch, torchvision, ctranslate2), `Pss_File` measured 38 MB total while `Pss_Anon` was ~3 GB — so moving to a `:slim` or otherwise smaller image is a **disk** win, not a memory one. Never present an image swap as a RAM fix; measure `Pss_File` first.
- **Open WebUI's effective RAG/STT config lives in `webui_db.config`, not in the container env.** Persistent config overrides env, and the image's `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` are build-time Dockerfile leftovers that `start.sh` never reads (it reads only `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`). Read the real engines from the DB instead: `sudo -u postgres psql -d webui_db -Atc "select key||' = '||left(value::text,140) from config where key ~ 'rag|embedding|rerank|stt|whisper' and key not like '%api_key%' order by key;"`. Typically embeddings/reranking are external (`rag.embedding_engine=openai`, `rag.reranking_engine=external`) and **local STT is the one genuinely in-process model** (`audio.stt.engine=""` + `audio.stt.whisper_model`, which also downloads the faster-whisper cache).
- **`document_chunk` costs ~20 KB per chunk, almost independent of chunk text size** (measured: 9.6 KB index + 8.7 KB TOAST vector + 1.3 KB row for `vector(1536)`). So DB growth is driven by **chunk count, not source megabytes**. Normal prose (~1000-char chunks) amplifies ~20×; a CSV/JSONL that splits one chunk per line (~178 B each) amplifies ~145× — that is how a 1.8 MB CSV became 263 MB. To size an ingest, multiply expected chunk count by ~20 KB, don't look at the file size.
- Before uploading anything big, know the ceiling: at 61 GB free the disk hit the 85% alert after ~2.4M chunks (~2.2 GB of prose, or only ~430 MB of line-per-chunk tabular data). Disk alerts (`DISK_WARN=85`/`DISK_CRIT=95`, cron `*/10`) fire long before a surprise. Disk is NOT the exposure — RAM is.
- **Deleting an ingested file through the Open WebUI API is the only correct way to reclaim space.** `DELETE /api/v1/files/<id>` cascades (file row, `chat_file`/`knowledge_file` refs, `document_chunk` rows for collection `file-<id>`, and the physical upload) — deleting rows or the file by hand leaves orphans. Login needs the **admin email**, which `UI_USERNAME` in `ai/.env` is NOT (it's a short non-email handle); read it from the DB: `select email from "user" where role='admin' limit 1`. `GET /api/v1/files/` returns a paginated `{items, total}` dict, not a bare list.
- **The freed space does not come back until `VACUUM FULL`.** After deleting 10 181 chunks the table stayed at 263 MB with `n_dead_tup=10526`; `VACUUM (FULL, ANALYZE) document_chunk` (5 s, 3 519 rows) took it to 76 MB and `webui_db` 393 → 206 MB. Plain `VACUUM` only marks space reusable, not returned to the OS — use `VACUUM FULL` when you actually need the disk back.

### Chat-image bloat: base64 living in `webui_db` (the second disk eater)

Opposite of the chunk story: growth here is **bytes per row**, not row count. A chat tool that emits an image as `data:image/...;base64` in its `files` event makes Open WebUI persist that base64 **twice** — in `chat_message.files` and again in the whole-history JSON `chat.chat`. Measured: 36 images = 133 MB base64 → 266 MB of a 593 MB `webui_db`, individual messages 8–19 MB.

Sizing query (the two tables plus TOAST):

```bash
sudo -u postgres psql -d webui_db -Atc "select c.relname, pg_size_pretty(pg_total_relation_size(c.oid)), pg_relation_size(c.oid), s.n_live_tup, s.n_dead_tup from pg_class c join pg_stat_user_tables s on s.relid=c.oid where c.relkind='r' order by pg_total_relation_size(c.oid) desc limit 15;"
sudo -u postgres psql -d webui_db -Atc "select count(*) filter (where files::text like '%data:image%') base64_msgs, pg_size_pretty(sum(pg_column_size(files))::bigint) files_bytes from chat_message;"
sudo -u postgres psql -d webui_db -Atc "select pg_size_pretty(sum(case when chat::text like '%data:image%' then length(chat::text)-length(regexp_replace(chat::text,'data:image/[^\"]*','','g')) else 0 end)::bigint) from chat;"
```

- **`chat` (the JSON history) mirroring `chat_message.files` is the tell** — when both tables hold nearly the same base64 total, one payload is stored twice and only a rewrite of both helps.
- **Fix = compact base64 into file storage, not delete it.** `scripts/compact-webui-images.py` (idempotent, report-and-commit) decodes each `data:image` entry, writes the bytes to `UPLOAD_DIR`, inserts the `file` + `chat_file` rows, and rewrites the URL to `/api/v1/files/<id>/content` in **both** `chat_message.files` and (by string replace) `chat.chat`. Result on this box: `webui_db` 593 → 224 MB, `chat` 271 → 51 MB, `chat_message` 200 → 51 MB, images still render; run it as a container-internal one-liner so it uses the app's own `DATABASE_URL` and `UPLOAD_DIR`:
  ```bash
  docker exec -i open-webui python -c "import os; os.environ['UPLOAD_DIR']='/tmp/migtest_uploads'; exec(open('/tmp/compact-webui-images.py').read())"   # DSN defaults to DATABASE_URL
  ```
- **The storage side was never the problem** — `/app/backend/data` is a bind mount to `/home/ai_service/webui_data` and uploads land in `uploads/`. Do not propose "bind a volume" as the fix; the bug is that the tool never called `upload_image`, so say so.
- **Patch the tool that writes the base64, or it comes straight back.** Tool code lives in `webui_db.tool.content` (not on disk), and OWUI loads the registry at startup: write the row **and restart open-webui**, then confirm the stored code compiles (`docker exec -i open-webui python -c "exec(open('/tmp/tool.py').read())"`). Snapshot the old content to a file first — it is the only way back.
  - The durable shape: the tool takes `__request__` / `__user__` (OWUI injects them by name), calls `open_webui.models.users.Users.get_user_by_id` + `open_webui.routers.images.upload_image`, emits `{'type': 'image', **image_file}` and keeps the data URL only as a fallback. To keep "edit the last result" working, resolve `/api/v1/files/<id>/content` back to base64 from `UPLOAD_DIR` (`open_webui.config.UPLOAD_DIR`) by globbing `<id>_*`.
- Content-embedded base64 from **user uploads** (`chat_message.content` parts) stays — a few hundred KB, and OWUI needs it as a data URL when calling vision models. Only the generated-image `files` arrays are worth rewriting.
- The tool also keeps a third copy in `data/generated_images` (disk, ~83 MB here) with no retention; and `litellm_db` grows separately (`LiteLLM_SpendLogs` ~254 MB + daily aggregates ~127 MB, no auto-retention in the pinned version — only manual SQL prunes it). Name both as untackled, separate from the webui fix.

## Model provenance in Open WebUI (ghost models)

Admin → Settings → Models is a **merged** list, so an entry can be visible with **no row in `webui_db.model`**. `Models.svelte` renders `getModels` (DB rows **+ everything the connections advertise**) then appends `getAllModels` (DB only). Three provenance classes:

1. **Connection model** — comes from a connection's `/v1/models`. In `GET /api/models` it carries `"connection_type": "external"` and a `urlIdx`; its tag names the group. The UI offers **Reset** (`canResetModel` = not a preset + present in the merged list), никогда Delete.
2. **DB model** — a row in `webui_db.model` (workspace preset or plain custom model); the UI offers **Delete**. `webui_db.model` has **no `access_control` column** in 0.12 — the «Частное»/Private badge means "no public read grant" (`access_grants`); views filter on `private`/`public`, `enabled`/`disabled`.
3. **Ghost** — a name a connection advertises that has no backend at all.

Diagnose (admin token = `POST /api/v1/auths/signin` with the **email** from `select email from "user" where role='admin'` — `UI_USERNAME` is NOT an email — plus `UI_PASSWORD` from `ai/.env`):

```bash
curl -s 127.0.0.1:8080/api/models -H "Authorization: Bearer $TOKEN"      # merged: shows connection_type / urlIdx / tags
curl -s 127.0.0.1:8080/api/v1/models/base -H "Authorization: Bearer $TOKEN"  # DB rows only
```

Connections all point at `litellm:4000/v1`; the **index into `openai.api_base_urls` is the `urlIdx`**, and `openai.api_keys` at the same index is the LiteLLM virtual key that selects the model group:

```bash
sudo -u postgres psql -d webui_db -Atc "select value::text from config where key='openai.api_base_urls';"
```

Delete a DB model with the API (it cascades `model_history`; a hand-written `DELETE` must remove `model_history` rows in the same transaction — see the cleanup subsection below):

```bash
curl -s -X POST 127.0.0.1:8080/api/v1/models/model/delete -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"id":"<model-id>"}'
```

**A ghost cannot be deleted from Open WebUI — fix it at the source.** Worked example: `hermes/thinkingmachines/inkling:free` showed in the admin list as `external`/`urlIdx 5`/tag `hermes` while having no `webui_db.model` row, no `litellm_db."LiteLLM_ProxyModelTable"` row and no `/v1/model/info` (master-key) entry. Cause: **LiteLLM echoes a virtual key's `models` allowlist verbatim in `/v1/models`, even for names that do not exist**. The key `OpenRouter Hermes` still carried the dead name:

```bash
curl -s "127.0.0.1:4000/key/info?key=$KEY" -H "Authorization: Bearer $LITELLM_MASTER_KEY"
curl -s -X POST 127.0.0.1:4000/key/update -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H 'Content-Type: application/json' -d '{"key":"<KEY>","models":["hermes/deepseek-v4.1-flash"]}'
```

`$KEY` = plaintext value from `webui_db.config` key `openai.api_keys` at that `urlIdx`. Open WebUI re-reads connection models on its own (its cache expires) — **no container restart needed**, verify with the two `curl` calls above. Always snapshot the row (`select row_to_json(m) from model m where id=...`) and the key's old `models` list before changing anything.

### Dead / disabled model cleanup (DB presets)

**Never retype a model id from tool output into an API call.** Model names that contain `claude-…` are redacted in tool output (printed as `anthropic/` + nothing), so a copy-pasted `key/update` payload silently writes a truncated, non-existent name and can drop the real entries. Build every payload programmatically from `webui_db` / `/v1/models` in one Python process and print only counts and `md5()` prefixes for verification.

**The definitive liveness probe is Open WebUI's own endpoint, not LiteLLM.** `POST 127.0.0.1:8080/api/chat/completions` with `max_tokens=1` tests exactly the path a user takes: OWUI resolves a DB preset to its `base_model_id`, and refuses ids no connection advertises with `{"detail":"Model not found"}`. A direct LiteLLM probe gives false answers in both directions — it 400s on the `<connection_tag>.<model>` alias rows that OWUI serves fine, and it 400s on `opencode/*` groups that are alive but demand an `x-opencode-session` header (treat `MissingSessionID` as alive). Run the sweep concurrently (6 workers) — serial takes ~10 min for 100 rows.

`GET /api/v1/models/base` can return more rows than `/api/models` shows in the chat selector: stale alias rows left by older LiteLLM configs (`chat.opencode/*`, `aider.*`, `*.tokenator/*`, `other.*`, `img.openrouter/*`) linger in the DB, appear in Admin → Settings → Models, and answer `Model not found`. They are safe to delete; presets that carry a `system` prompt (`image-generator`, `video-generator`) are custom models — never sweep those, the user's rule is «кастомные не трогать».

`webui_db.model` marks a hidden model with **`is_active=false`** — there is no `enabled` column (that word only appears in the UI/badge text). `GET /api/v1/models/base` returns DB rows as a plain list, while `GET /api/models` returns a **dict** `{"data": [...]}`.

**Disabled ≠ dead: prove liveness with a real completion — but probe through Open WebUI, not LiteLLM.** POST `127.0.0.1:8080/api/chat/completions` with `{"model": <id>, "messages":[{"role":"user","content":"hi"}], "max_tokens":1, "stream": false}` and the admin token. That is the exact path the UI takes, so it is the only probe whose verdict matches what the user sees:
- `200` → alive; if the row is `is_active=false` it is merely switched off — **keep it and say so** instead of deleting.
- `{"detail":"Model not found"}` → no connection advertises the id (nor its `base_model_id`) → ghost, dead.
- a LiteLLM error body passed through verbatim → dead, **except** `MissingSessionID` / `Request is missing x-opencode-session`: those groups are **alive** (opencode-backed and needing a session header the plain probe cannot send). Never delete on that error.
- **A direct master-key POST to `127.0.0.1:4000/v1/chat/completions` is NOT a valid liveness test for an Open WebUI id.** It gives false verdicts in both directions: Open WebUI strips the connection tag from alias rows (`aider.anthropic/` answers because LiteLLM has `anthropic/`), resolves presets through `base_model_id`, and its registry can hold ids LiteLLM rejects. Judge only by the Open WebUI answer. `/v1/models` stays unusable as a liveness source either way — LiteLLM echoes dead names from virtual-key allowlists and can serve groups it does not list.

**Audit the `model` table, not the API listings.** In one pass `GET /api/models` returned 59 ids, `/api/v1/models/base` 100, while `webui_db.model` held 123 — DB-only rows are invisible in the chat selector yet still listed in Admin → Settings → Models, and they are exactly the stale aliases left behind by previous LiteLLM configs (`chat.opencode/*`, `aider.*`, `*.tokenator/*`, `other.*`, `hermes.opencode/*`). Enumerate with `select coalesce(json_agg(json_build_object('id',id,'base',base_model_id,'active',is_active)),'[]') from model;` and probe every row. **Parallelise (≈6 workers, 60 s timeout)** — 123 sequential probes with long upstream timeouts take over 10 minutes.

**A ghost that lives only in a key allowlist has no DB row at all.** It surfaces as `<connection_tag>.<model>` (e.g. `chat.chat/qwen3-coder-…`) because LiteLLM echoes the key's `models` list into `/v1/models`. Compare every key's list against `/v1/models` and repair with `key/update` — see the provenance section above.

Ready-made probe (report-only by default; `--delete` snapshots the rows and removes the dead ones): `scripts/audit-dead-models.py`.

Order of operations:
1. Snapshot every row you are about to delete — the whole dead set, not only the disabled ones: `select coalesce(json_agg(row_to_json(m)),'[]') from model m where id in (...);` → `/home/ai_service/ai-stack/backups/webui_dead_models_<ts>.jsonl` (chown `ai_service`). A curated preset can carry a long system prompt in `params`, so the backup is the only way back.
2. Check the merged list (`/api/models`) for the same id with `connection_type=external` — a DB-only id can be deleted safely; an id a connection also advertises would reappear as a live connection model after deletion.
3. Delete through `POST /api/v1/models/model/delete` (cascades `model_history`).
4. **Some ids the API refuses with `401 "We could not find what you're looking for"`** — typically junk rows whose id ends in a provider tail like `tokenator/` or `paid/anthropic/…`, and rows absent from `/api/v1/models/base`. Finish those in SQL, deleting history first in one transaction:
   ```sql
   begin;
   delete from model_history h using model m where h.model_id=m.id and md5(m.id) in ('<md5>',...);
   delete from model m where md5(m.id) in ('<md5>',...);
   commit;
   ```
   Target by **`md5(id)`, not by literal id**: long ids get visually truncated in tool output, so a pasted id silently deletes nothing (`DELETE 0`). Collect `md5(id)` from psql and pass those.
5. Verify: dead count in DB and via `/api/models`, `select count(*) from model_history h where not exists (select 1 from model m where m.id=h.model_id)` = 0, and re-probe a sample of the kept models through `/api/chat/completions` to confirm they still answer 200.

When the user says «удали мёртвые», delete only the ones that fail the probe — a disabled-but-working model is a config choice, not garbage. Report counts (dead removed / alive kept), the backup path, and the surviving disabled entries.

## Open WebUI DB growth: base64 chat images

- **The dominant bloat source is base64 images inside `chat_message.files`, duplicated into `chat.chat`.** OWUI stores a chat's whole history as one JSON blob in `chat.chat` *and* per-message rows in `chat_message`, so an image saved as a `data:image/...;base64,` URL costs **twice**. Measured: 36 images = 133 MB in `files` + 133 MB in `chat.chat` = 266 MB of a 593 MB `webui_db`; single messages reached 19 MB, one image 8.8 MB base64. Diagnose with `pg_column_size(files)` per message and by summing the base64 substrings: `select count(*) filter (where chat::text like '%data:image%'), pg_size_pretty(sum(case when chat::text like '%data:image%' then length(chat::text)-length(regexp_replace(chat::text,'data:image/[^"]*','','g')) else 0 end)::bigint) from chat;`
- **`n_dead_tup` near 0 means the growth is real data, not autovacuum bloat** — plain `VACUUM` will not help; only removing the payload (or `VACUUM FULL` after doing so) returns space.
- **The `:main` image persists base64 only because a workspace tool emits it.** `litellm_image_reference_generator_hy_image_3_5` (DB `tool.content`) emitted `{'type':'image','url': data_url}` in its `files` event; OWUI's own `/images/generations` path instead calls `upload_image()` and returns `/api/v1/files/<id>/content`. Same for images surfacing via `extract_base64_images` on tool results.
- **Fix the tool, not just the DB** — patched to v1.5.0: it calls `upload_image(request, raw, mime, {}, user)` via injected `__request__`/`__user__` and emits the returned file entry, falling back to the data URL if that fails. Two extra pieces are required for it to keep working: `_file_url_to_data_url()` (globs `UPLOAD_DIR` for `<id>_*`) so "improve the last image" can still use stored files as references, and MIME sniffing by magic bytes because LiteLLM labels JPEG payloads `image/png` (19 of 36 files were mislabeled → the `/content` response header lied; browsers sniff, but just be correct).
- **Migrating existing base64 → files is safe and scripted.** For every `data:` URL in a message's `files`: write bytes to `/app/backend/data/uploads/<uuid>_generated-image.<ext>`, insert a `file` row (`meta.data` = `{}`, `hash` = sha256, `path` absolute), insert a `chat_file` row so the file dies with the chat, replace the URL with `/api/v1/files/<uuid>/content`, then string-replace the same data URL inside `chat.chat` (base64 chars need no JSON escaping, so a verbatim replace is exact). Result: 593 → 224 MB. 
- **Verify compaction by fetching the new URL, not by looking at the row**: `GET /api/v1/files/<id>/content` with an admin token must answer 200 + real image bytes. A pre-existing orphan file row (path missing on disk) answers 404 `We could not find what you're looking for :/` — pick an id whose `path` exists before concluding the migration failed.
- **Nightly guards installed**: `webui-compact-images.{service,timer}` (04:00 UTC, runs `/usr/local/bin/webui-compact-images.sh` → copies `/usr/local/lib/webui-compact/compact_images.py` into the container, and only when it moved something does it `VACUUM FULL` `chat`/`chat_message`; silent no-op otherwise, log `/var/log/webui-compact-images.log`) and `litellm-spend-retention.{service,timer}` (04:30 UTC, deletes `LiteLLM_SpendLogs` older than 30 days, **never touches `LiteLLM_Daily*Spend` aggregates**, plain `VACUUM` every run + `VACUUM FULL` only when dead tuples exceed 30 % of live rows; log `/var/log/litellm-spend-retention.log`). Test a timer by `systemctl start <service>` and reading the log, not by waiting for the calendar.
- **Remaining known growth**: `document_chunk` (~20 KB per chunk, RAG), `generated_images/` inside the container data dir (a third on-disk copy the tool writes on purpose, ~2.6 MB/image), and `LiteLLM_SpendLogs` (~13 MB/day from `messages`/`response` JSONB, now capped by retention).
- **`generated_images/` retention**: `webui-generated-images-retention.{service,timer}` (04:15 UTC) deletes image files in `/home/ai_service/webui_data/generated_images` older than 14 days by mtime, only at `-maxdepth 1` and only for image extensions. It cannot break chats: history renders from `/api/v1/files/<uuid>/content`, and reference resolution prefers those URLs — the disk copy is only the tool's recent-fallback. Safe to purge. Tested via `WEBUI_GENERATED_IMAGES_DIR=<scratch dir> <script> [--dry-run]` (dry-run prints the count/size, real run deletes and logs to `/var/log/webui-generated-images-retention.log` only when it removed something).

## User administration & signup approval (Open WebUI API)

- **Admin auth for scripts:** `POST /api/v1/auths/signin` with the email from `select email from "user" where role='admin'` plus `UI_PASSWORD` from `ai/.env` (`UI_USERNAME` is NOT an email; grep the key, never print it). JWT lives `auth.jwt_expiry`, default `4w` (`JWT_EXPIRES_IN`, `-1` = never) — cache the token in memory and re-signin on 401 instead of inventing a long-lived credential.
- **`GET /api/v1/users/all` returns `{users:[…], total:N}`** (an object, not a bare list). Each item has `id, email, name, role, is_active, last_active_at, groups, bio, status_*` but **no `created_at`** — track "already notified" by id in the caller's own state file. `GET /api/v1/users/` is a different shape (`UserGroupIdsListResponse`); `/api/v1/users/search` is paginated and open to non-admins.
- **Approve / delete a registration:** approve = `POST /api/v1/users/{id}/update` with `{"role":"user"}` (admin; emits `user.role.updated`); delete = `DELETE /api/v1/users/{id}` (admin, returns bool). There is no `/auths/update/role` and no dedicated approve endpoint in 0.12 — a hand-written SQL role `UPDATE` skips the event and any cached role, so always go through the users router.
- Signup policy is persistent config, not env: `ui.enable_signup` and `ui.default_user_role` (`pending` here). Count the queue authoritatively in SQL: `select count(*) from "user" where role='pending'`. When reading through the API, filter the returned list by `role` and confirm the pending row is actually present before trusting the API path end-to-end (0.12 keeps pending accounts in the same `user` table but the list endpoint was not exercised against a live pending row here).
- **Native event webhooks cannot reach a listener on this host.** 0.12 defines `auth.signup` / `user.*` events plus event webhooks, but `utils/webhook.py::validate_url` rejects loopback and private-IP targets, so the URL must be publicly resolvable → an nginx path with TLS and a secret token. Since a Telegram flow needs inline buttons and callback handling anyway, a local poller + `getUpdates` is the smaller build; name the webhook route only when instant delivery is a hard requirement.
- **One `getUpdates` poller per bot token.** `server-monitor-bot.service` already long-polls `BOT_TOKEN`, so a second service on the same token dies with `409 Conflict`; either extend that service's loop (add a `callback_query` branch and persist `offset`) or take a separate bot token for the new flow.

## Pitfalls

- **Open WebUI RAM is dominated by glibc malloc arenas, not by models.** Measured 2026-10: `Pss_Anon` 2.97 GB vs `Pss_File` 38 MB — i.e. the bundled torch/torchvision/ctranslate2 files cost ~nothing resident, so **switching to the `:slim` image frees disk (~800 MB of 6.37 GB), not RAM**. The real footprint was **24 anonymous rw regions of exactly 64 MiB at 64 MiB stride** = glibc secondary arenas (`HEAP_MAX_SIZE` = 64 MiB; glibc 2.39 allows up to `8 × nproc` = 32 arenas) accumulated by the 38 threads of the uvicorn process. Fix = `MALLOC_ARENA_MAX: "2"` in the service `environment:` (needs container recreate; the value is read by the loader at process start). Result: RSS 3012 → 866 MB, arenas 24 → 1, host `used` 5.5 → 3.3 GiB, process `VmSwap` 148 MB → 0. Diagnose the pattern with: `awk '/^[0-9a-f]+-[0-9a-f]+ /{split($1,a,"-"); sz=(strtonum("0x"a[2])-strtonum("0x"a[1]))/1048576; hdr=$0} /^Rss:/{if(hdr ~ /rw-p 00000000 00:00 0/ && sz>=63 && sz<=65) c++} END{print c}' /proc/<pid>/smaps`. Two traps: (1) `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` in the image env are Dockerfile build-time leftovers — `start.sh` only reads `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`, so the real engines come from the **persistent config in `webui_db.config`** (here external: `rag.embedding_engine=openai`, `rag.reranking_engine=external`); changing the env vars changes nothing. (2) **STT is genuinely local** (`audio.stt.engine=""` + `audio.stt.whisper_model=small`, cache `data/cache/whisper/models` 462 MB, plus `rag.content_extraction.supported_media_mime_types=["audio/*"]` which transcribes audio at ingest) — do NOT claim local speech models are unused just because embeddings are external. Expect RSS/threads to rise on the first audio transcription (torch/ctranslate2 import lazily) — but with `MALLOC_ARENA_MAX` set the growth is bounded.
- **`ai/backup-databases.sh` must be called by ABSOLUTE path.** It does `cd "$(dirname "$0")"` and then reads `ENV_FILE="$(dirname "$0")/.env"`; invoked as the relative `ai/backup-databases.sh` the second `dirname` yields the relative `ai` and, after the cd, resolves to `ai/.env` → dies with `Нет ai/.env` (exit 1) and no dump is written. Use `sudo -u ai_service /home/ai_service/ai-stack/ai/backup-databases.sh`.
- `/home/ai_service/ai-stack/ai/backup-databases.sh` must stay **755 root:root** — `postgres-backup.service` runs `User=ai_service`, and a restrictive mode (e.g. 711) makes the nightly run die with `Permission denied`, `status=126` while the timers still look healthy. After any permission/ownership change on that script, verify with `systemctl start postgres-backup.service` and check `Result=success`.
- **Two independent gotchas bite the restore check, and both are silent.** (1) `sudo` resets the environment (`env_reset`), so `subprocess.run([..., "sudo", "-u", "postgres", "pg_restore", ...], env={"PGOPTIONS": ...})` has NO effect — put `env` *inside* the sudo command: `sudo -u postgres env PGOPTIONS='-c maintenance_work_mem=512MB' pg_restore ...`. (2) The default `maintenance_work_mem` is 64 MB and pgvector index builds need more, so `webui_db` restore dies with `memory required is 65 MB, maintenance_work_mem is 64 MB` — hence `VERIFY_MAINTENANCE_WORK_MEM = "512MB"` applied through `PGOPTIONS` on both restore branches (split and whole-file). After any change to `_restore_into_temp_db`, run the real thing — a green unit test suite mocks the commands and will not catch either failure.
- The restore check only runs under a user that can `sudo -u postgres`. `server-monitor-bot.service` runs as **root**, so `/backups` works; the same code invoked as `ai_service` fails with `sudo: a password is required` (that sudoers NOPASSWD list is read-only commands only). Run `verify_backups`/`_restore_into_temp_db` as root during testing, or the result is a false failure that has nothing to do with the code.
- Verify dumps by restoring into a throwaway DB (`createdb verify_restore_webui` → `pg_restore -d ...` → `dropdb`). NEVER restore a dump over a live database. `/backups` does this automatically; `pg_restore` needs to read the dump, so pipe split parts via stdin (root-owned temp files under `/root/...` are unreadable by the `postgres` user — `Permission denied`).
- `monitor.py backup` splits dumps > 45 MiB adaptively and deletes the parts after upload; the join message carries the part names/sizes, the `cat` command and the expected SHA-256 of the whole dump, and aborts that message to a warning if any part failed to upload.
- `send_document` compares Telegram's reported `file_size` with the local size — a mismatch raises, so a truncated upload cannot pass as success.
- Tests in `/home/ai_service/notifications/test_monitor.py` MUST stay off the network: the module patches `send_telegram`, `send_document` and `send_long_message` at import. Mocking only `send_long_message` is not enough — `notify_backup` sends the digest via `send_telegram` and attachments via `send_document`, so fixtures leak to the real bots when the suite runs. Sanity check: run the suite with `urlopen` patched to raise; it must still pass.

- **`Error upserting deployment <name>: LLM Provider NOT provided` in the LiteLLM boot log is a pre-existing broken DB deployment, not a regression from the upgrade you just applied.** Deployments created through the UI/API live in `litellm_db."LiteLLM_ProxyModelTable"` (params are encrypted there, so you cannot read the model string back) and are re-validated at boot; a row whose params lack a provider prefix warns on every start. Before blaming the new version, check the row's `created_at` (`select model_name, created_at from "LiteLLM_ProxyModelTable" where model_name like '%<name>%'` — column is `created_at`, not `"updatedAt"`) and whether the group ever served traffic (`select model_group, count(*) from "LiteLLM_SpendLogs" where model_group like '%<name>%' group by 1`). Predates your change + zero spend = dormant entry, report it as a side note, do not "fix" it inside an upgrade task. **It does not stay in the boot log.** With `STORE_MODEL_IN_DB=True` the DB→router sync re-runs on a timer, so the same warning repeats **every 30 s** — count it with `docker logs litellm --since 24h | grep -c 'Error upserting'` (~2.9k/day here). Each cycle re-registers the router's deployments and raises a fresh traceback, which makes this a standing memory-churn source too, not just log noise. Remove such a row with the admin API, not SQL, so the in-memory router drops it immediately: `POST 127.0.0.1:4000/model/delete -d '{"id":"<model_id>"}'` (dump the row to `backups/litellm_orphan_row_<ts>.json` first; verified 2026-10-19: the `aider.opencode/grok-4.7` orphan disappeared and `grep -c 'Error upserting'` went to 0 within 30 s).
- **NEVER dedupe `LiteLLM_ProxyModelTable` by `model_name`.** ~120 rows for ~42 names is BY DESIGN: one `model_name` = a model group, and each row is a separate deployment with its own key/`litellm_credential_name`. The owner calls these «группы, с разными ключами» and forbids touching them; only a row that is a genuine orphan (created once, never updated, absent from `/v1/models` while its name-mates are served) is removable, and only with explicit approval for that single `model_id`.
- **`docker exec` with a heredoc needs `-i`.** `docker exec open-webui python - <<'PY' …` exits `0` with **empty output** because stdin is not attached — an empty result is a missing stdin, never a silent success; use `docker exec -i`.
- **`psql -c "stmt; stmt"` runs as ONE transaction**, so a `VACUUM (FULL, …)` bundled with other statements dies with `VACUUM cannot run inside a transaction block` — pass exactly one statement per `-c`.
- **A copy restored with `pg_restore --no-owner --no-privileges` is owned by `postgres`**, so the app role hits `permission denied for table chat_message`; on the copy run `grant all on schema public to webui; grant all on all tables in schema public to webui;` before exercising any script against it.
- **`POST /api/chat/completions` is not an end-to-end probe for an Open WebUI tool.** Non-stream answers `finish_reason: tool_calls` and expects the client to execute the tool, so the stored assistant row comes back empty with `files=null` — nothing was persisted and no tool ran. Exercise the tool in-process instead: `docker exec -i open-webui python` → `exec(open('/tmp/tool.py').read())`, instantiate `Tools`, and call the async helper with a dummy request object whose `.app.url_path_for(name, **kw)` returns the content path. That proves upload + `file` row + reverse URL→base64 resolution in seconds, with a 1×1 PNG and a cleanup of the row and the file.
- **`404 {"detail":"We could not find what you're looking for :/"}` on `/api/v1/files/<id>/content` means the row is missing or the bytes are not at `path` — not an access failure.** Long-lived DBs carry rows whose `path` died with a container layer, and they answer exactly like a bogus id; `ls` the path before suspecting permissions or ownership.
- **Sniff image MIME from magic bytes; do not trust the media type LiteLLM declares** — `image/png` came back for JPEG payloads in 19 of 36 files. Browsers render it anyway, but store the sniffed type, and prefer `upload_image(request, raw, sniffed_or_declared, {}, user)` over hand-building the `file` row.
- **Never `cat` an env file just to get a DSN** — build derived values in-process: `os.environ['DATABASE_URL'].rsplit('/', 1)[0] + '/<db>'`. Same for `UI_PASSWORD` (grep the key, never print the value).
- Do NOT `cat`/`tail` `ai/.env` — grep keys only.
- `deploy.sh` restores DBs by default; use `--skip-restore` when you must not touch data.
- Postgres is host-level (systemd), not a compose service — restart via `systemctl`, not `docker`.
- **Measure before reporting a performance anomaly.** A backup+notify pair that finishes implausibly fast is not evidence of a short-circuit — check the uplink first (`dd if=/dev/zero bs=1M count=100 | curl -s -o /dev/null -w '%{time_total}' -X POST --data-binary @- https://speed.cloudflare.com/__up`). This host pushes ~80 MiB/s, so a 140 MiB dump in ~4 s is normal and a 73 MiB dump in 9 s was the slow case, not the fast one. Announcing "suspiciously fast, probably broken" without measuring produces a false alarm you then have to retract.
- **A dump that jumps in size is usually real data, not bloat.** `webui_db` dumps can double overnight because `document_chunk` (pgvector embeddings) grows with every ingested file — one file contributed 10 181 chunks at a time. Confirm with `pg_total_relation_size` per table plus `n_dead_tup` (all near 0 ⇒ autovacuum is fine and the growth is genuine); only large `n_dead_tup` indicates bloat needing `VACUUM`. Report the cause rather than the symptom.
- `systemctl start` on a unit whose file changed on disk prints «unit file … changed on disk. Run 'systemctl daemon-reload'». Harmless for a oneshot that then runs correctly, but mention it — the unit on disk and the one systemd has cached are out of sync.

- **An automated incident→triage→fix pipeline on this stack needs a noise filter and dedup BEFORE it dispatches anything.** Every container here carries a restart policy (`always` / `unless-stopped`, see `docker inspect <c> --format '{{.HostConfig.RestartPolicy.Name}}'`), so a failing container self-heals in seconds and produces an event *storm*, not a single "down" event — and the lyria workers' boot `AMQPConnectionError` traceback is expected. Dedup by hash of the traceback with a TTL, and keep known-benign signatures on a whitelist, or the fixer gets woken for a non-event. Redact secrets too: litellm / open-webui / postgres tracebacks commonly carry `LITELLM_MASTER_KEY` and DB passwords, and the traceback travels into a delegated agent's context as well as into Telegram.
- **Never let a delegated fixer touch the stack directly** — `deploy.sh` restores databases by default. It works in a git worktree and emits a diff; the deploy stays with the owner.

See `references/operations.md` for status/logs/restart/backup commands, and `references/memory-troubleshooting.md` for the container memory-attribution procedure (leak vs static footprint, glibc arena signature, open-webui config precedence) and §7 for LiteLLM's retained-heap breakdown and growth triggers.
