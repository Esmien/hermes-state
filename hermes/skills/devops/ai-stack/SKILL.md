# AI Stack (this VPS)

## When to Use

Load this skill whenever the task touches the AI service stack on this VPS — LiteLLM, Open WebUI, SearXNG, open-terminal, **the music bot (lyria)**, the host PostgreSQL, Nginx/Certbot TLS, `deploy.sh`, or the `backups/` dumps. It tells you where the stack lives and how to operate it.

LiteLLM / Open WebUI / SearXNG / open-terminal on PostgreSQL 17 + pgvector (host) behind Nginx+Certbot. **The music bot (lyria) is a separate deployment** — own containers, own Postgres, not covered by `deploy.sh` or the `postgres-backup` timers → [references/music-bot-lyria.md](references/music-bot-lyria.md). **Its code is off-limits:** state checks, test runs and commits/pushes of what is already in the tree only; report defects as a list, fix on an explicit separate instruction. Git as `ai_service` → [references/repo-hygiene.md](references/repo-hygiene.md).

## Location — IMPORTANT

The stack lives at **`/home/ai_service/ai-stack`** on the host. Owner: user `ai_service`.

- The host root is mounted **directly as `/`** — this agent runs on the host root, NOT in a container with a bind. **`/mnt/host` does not exist on the host**; never prefix host paths with it.
- **`/mnt/host` exists only inside `open-terminal`**, and recreating a stack container from that shell with `/mnt/host` paths mounts an auto-created empty directory over a file (`IsADirectoryError` loop) → [references/operations.md](references/operations.md).

## Domains → backend

Both zones run in parallel until the owner moves the family, so old and new names point at one backend (`esmien.qd.je` = free DNS with failing authoritatives, see `vpn-entry-stack`; `esmien.ru` = owned, on Cloudflare). **Read the actual state off disk before trusting this:** on 2026-11-09 `grep -rl qd.je /etc/nginx/{sites-enabled,conf.d}` returned nothing and `deploy.sh` targeted `.ru` only, i.e. the `qd.je` half was already dead there:

```
ai.esmien.ru    -> 127.0.0.1:8080  (open-webui — единственный вход) | ai.esmien.qd.je
app.esmien.ru   -> 301 на ai.esmien.ru (не второй вход)          | —
llm.esmien.ru   -> 127.0.0.1:4000  (litellm)      | llm.esmien.qd.je
bot.esmien.ru   -> 127.0.0.1:8000  (music bot)    | bot.esmien.qd.je
mon.esmien.ru   -> 127.0.0.1:8090  (beszel hub)      | mon.esmien.qd.je
vpn.esmien.ru:8443 (VPN entry)                    | vpn.esmien.qd.je:8443
```

- **`app.esmien.ru` is not a second entry, it is a `301`** to `ai` (path + query kept, no proxying, no limits) — two names for one WebUI = two cookie sessions.
- **The orange cloud is a two-sided switch — read its state from the zone, never from this file** (последнее состояние: `ai`/`app` серые — оранжевый эксперимент прямой путь не починил и снят по просьбе владельца, разбор идёт пакетным замером). Grey fixes the tunnel path but leaves the owner's ISP to reach the origin on 443 itself, so «вебуи не открывается БЕЗ впн» arrives within days; orange fixes the direct path but the edge can challenge our own exits. Read the zone (`proxied` + `modified_on`) and the request sequence in `access.log` (a reload loop = flaky path, not a broken app) **before** touching nginx. Never add a WAF skip «на всякий случай»: measure first — dial the host from a socks client built on the `p15`/`p17` outbounds, and `200` through the edge means no rule is needed. Un-oranging is **two** actions — drop the `if ($deny_direct) { return 403; }` gate first, then `PATCH {"proxied":false}` → [references/cloudflare-proxy.md](references/cloudflare-proxy.md).
- Vhost edits: `write_file` refuses `/etc/nginx` (stage in scratch, `cp`); after `systemctl reload nginx` the first `curl` may still hit the old worker — repeat it, don't roll back.
- New name: grey A record answering from two resolvers (orange ⇒ HTTP-01 `530`), cert via port-80 ACME stub + `certbot certonly --webroot`, then a vhost copied from an existing one, verify `200 cert=0`. Procedures and rollback → [references/cloudflare-proxy.md](references/cloudflare-proxy.md).

## Cross-cutting rules and the expensive traps

- **Начало согласованной работы — действие, а не отчёт о проверке.** Выполняй разрешённые шаги и проверки до завершения оговорённого этапа; останавливайся только на реальном блокере или отдельном гейте владельца. Проверка сама по себе не равна реализации. Если владелец просит сохранить прогресс перед продолжением, сначала запиши актуальное состояние, проверенные результаты, незавершённые проверки и точку отката в план, а затем продолжай работу. Для визуальной приёмки WebUI владелец предпочитает Chromium, реальную тестовую учётную запись и проверку скриншота зрением; разрешённая им JWT-инъекция проверяет авторизованный интерфейс, но не парольный вход. До отправки сообщения сверь выбранный пресет с разрешённой моделью, чтобы случайно не расходовать дорогой маршрут → `references/owui-internals.md`.

- **Ключи не перевыпускать и не ротировать — никогда, в том числе ради теста.** У одного OWUI-ключа (`webui_db.api_key`, одна строка на юзера) несколько потребителей сразу: кастом-провайдер Hermes (`HERMES_CUSTOM_127_0_0_1_8080_API_KEY` в `/root/.hermes/.env`) и обогатитель музыкального бота (`ENRICH_TOKEN` в `/root/deploy/music_bot/.env`). `POST /api/v1/auths/api_key` не «показывает» ключ, а перевыпускает его и аннулирует старый — после этого Hermes и бот получают `401`, и владелец справедливо считает это поломкой. Для тестов достаточно прочитать ключ из БД; если ротация всё-таки случилась — записать новый в оба файла, пересоздать `bot`/`enricher-worker` и перезапустить Hermes. Детали и порядок восстановления — `references/owui-internals.md`.

- **Сломался внешний вызов (сервис вернул `None`/500/timeout) — сначала найти, кто владеет конфигом, и починить ТОЛЬКО мёртвый указатель** (URL, имя модели, ключ). Промпты/политики живут у владельца фичи (pipe-функция в OWUI, модель в LiteLLM), а не в вызывающем коде: перенос промпта в бота «чтобы починить» владелец откатывает и считает поломкой архитектуры. Порядок: найти по стеку, кто отдаёт это поведение (`search_files` по коду/конфигам, затем `function`/`model` в `webui_db`) → проверить живость указателя → заменить указатель → сквозной тест.
- **Never put `/dev/null` as a destination** in a symlink/`install`/`ln -sfn` one-liner while cleaning up: it silently unlinks the device node host-wide (every service writing to `null` fails). Restore is `rm -f /dev/null && mknod -m 666 /dev/null c 1 3`; verify with `ls -l /dev/null` → `crw-rw-rw- 1 root root 1, 3`.
- **Git is the record:** `sudo -u ai_service env HOME=/home/ai_service git -C /home/ai_service/ai-stack …` (**no remote** — branch `master` is local-only, so nothing gets pushed and `git commit -a` sweeps unrelated working-tree edits into your commit: stage files by name); `ai/.env`, `backups/`, `backup-deploy/`, `*.bak*`, logs ignored on purpose; `ai/.env.example` holds the key names with `CHANGE_ME`. `runbook.md` is tracked and owner-facing — update it when a recovery procedure changes.
- **DB restore applies `backups/postgres/<db>_*.dump` — but the dumps are `.dump.enc`**, so an unchanged mask silently finds nothing and the deploy continues on an empty database.
- **UI from a foreign machine = SSH tunnel only** (`-L 8080:127.0.0.1:8080 -L 4000:127.0.0.1:4000`) → [references/operations.md](references/operations.md).
- **Docker events miss "Up+healthy, traffic dead"**: `litellm-watchdog.py` + `litellm-watchdog.{service,timer}` (60 s, alerts via Bot API) covers it → [references/backups-notifications.md](references/backups-notifications.md).
- **Misquoted facts** (aliases vs unique models, `edge-tts` orphan, «Failure» wall = scanners, empty `bot_db`) → [references/pitfalls.md](references/pitfalls.md).
- **Tool calls in an Open WebUI chat live in `message.output[]` as `{type:"function_call"}`**, not in `tool_calls` (that field is absent). Reading only `content`/`tool_calls` makes an agent-heavy session look like a plain chat with fabricated verification — grep the stored chat JSON for `"function_call"` and count names (`run_command`, `write_file`, `execute_code`, `view_knowledge_file`) before concluding a model had no hands. `chat` is a `json` column in `webui_db` (postgres on the host, not in docker); `jsonb_typeof(chat->…)` fails on it, cast instead (`(chat::jsonb)->'messages'`).
- **Файловая память WebUI — Filter и Tool включены в обычных пользовательских чатах.** Filter пропускает только фоновые задачи (не админа), валидирует персональную привязку и добавляет Tool к имеющемуся списку tool_ids и для `user`, и для `admin`; явный `tools` API не перезаписывать. **AGENTS.md у песочниц не править вручную: его держит provisioner управляемым блоком `<!-- managed:begin/end -->` и перезаписывает блок каждый прогон (таймер 60 с), сохраняя только текст снаружи.** Новые правила для всех — через шаблон в provisioner и его прогон, с проверкой по файлам, а не по счётчику `--dry-run`. Разбор личной памяти конкретного пользователя (дубли, факты не на своём месте) — только по показанному плану и с отдельным выбором степени сжатия: что переезжает в PROFILE, что сливается, сколько знаков станет; бэкап — `tar` только `.agents`. Порядок — `references/owui-internals.md` § Гигиена пользовательской памяти, аудит — `scripts/audit-memory-files.py`. Детали и грабли — `references/owui-internals.md` § AGENTS.md. Встроенная память выключена: `memories.enable=false` и `memories.system_context.enable=false` в `config` плюс рестарт, строки таблицы `memory` оставлены как откат (удалять только по согласованию). Provisioner обслуживает роли `user` и `admin`, у админа своя песочница `ot-u-black-walf16`. Миграция на Terra: админ 7 записей/1327 знаков, пользователь 24/4202; честное сжатие с сохранением фактов даёт лишь ~5-6%. Terra: пользователям доступен `chat.openai/gpt-6.1-terra`, `service.openrouter/gpt-6.1-terra` — только admin/master key; в UI модель выбирать по точному id, имена «GPT-6.1 Terra» у нескольких записей одинаковы. Подписочная нога `openai/gpt-6.1-terra` при исчерпании квоты отдаёт текст «Subscription Sharing usage limit» прямо в тело ответа, а не в ошибку — не принимай его за ответ модели. `/openrouter/alpha/decisions` на Terra отдаёт 400, решения остаются на `pplx-decider-v1.2`. Поле `config.value` имеет тип `json`: `row_to_json` возвращает boolean, поэтому сверяй с `True`, а не со строкой `'true'`. В установленной версии `POST /api/v1/tools/id/<id>/update` не меняет права: для грантов нужен `/access/update`, затем отдельное чтение и сверка. Права Tool public read опираются на серверную проверку идентичности и каталога. На Chromium подтверждено: выключение `chat.system_prompt` запрещает редактирование, но сохранённый пользовательский системный промпт всё равно уходит в запросе. После согласования владельца два сохранённых пользовательских значения, побайтно сверенных с PROFILE, очищены из БД одной транзакцией с проверкой исходных значений; откатные данные лежат в `/var/backups/file-memory-step2/user-prompts-before-clear.json` (0600). DB-проверка: у обычных пользователей значений нет, админское не менялось. Не обещай, что уже открытые вкладки немедленно забыли закэшированные настройки; проверяй на новой загрузке. Админский промпт не меняй без явного запроса. Актуальное состояние и откат — `/root/.hermes/tasks/docs/owui-file-memory.md`.

- **Модельные системные промпты — не трогать.** `model.params.system` (20 из 80 моделей) — установки администратора, владелец считает их необходимыми; не предлагать чистку и не менять без прямого указания. Встроенная память (`memories.*`) и пользовательские промпты (`chat.system_prompt`) остаются выключенными.
- **Права OWUI: группы перекрывают дефолт.** `config.user.permissions` — только база; действующие права даёт `group.permissions`. Проверять все группы (`select name, permissions::jsonb->'chat' from "group"`): в этом стеке у группы «Ограничения» `chat.system_prompt` стоял `true`, то есть поле было доступно, хотя дефолт `false`. Изменённые права видны после перелогина — они кэшируются в сессии.
- **Проактивное сохранение памяти — правило в шаблоне provisioner.** Без него модели сохраняли только по прямой просьбе. Теперь в управляемом блоке AGENTS.md есть раздел «Сохранение по своей инициативе»: сначала читать нужный файл, потом добавлять; болтовню, эмоции и догадки не писать; не дублировать. Проверено: фактическая реплика → `memory(list)` у Terra и DeepSeek, болтовня → без вызова тула. Изменения шаблона разъезжаются прогоном provisioner; пилотные аккаунты он не трогает — там править вручную.
- **Id компонентов памяти: `file_memory_filter` (global Filter) и `file_memory_tool` (Tool).** Приставка `pilot` снята 14.11.2026: созданы новые объекты с переносом valves и грантов, старые выключены и удалены; бэкап — `/var/backups/file-memory-step2/rename-to-release/`. Valve `tool_id` в Filter смотрит на `file_memory_tool`; переименование id в OWUI — это create+delete, а не rename, чаты, включившие Tool вручную, отваливаются молча.
- **Лимит MEMORY — 10000 символов, запись — 400** (с 14.11.2026; было 5000 и 260). Цифры живут в трёх местах: `MEMORY_LIMIT` и текст инструкции в Filter, `LIMIT`/`RECORD_LIMIT` в Tool, строка «до N символов» в шаблоне provisioner — менять синхронно, фикстуры тестов строить от констант, а не от литералов. После правки: rebuild (`build_plugins.py`) → deploy фильтра и Tool → сверка живого контента → шаблон provisioner + прогон (пилотные аккаунты он не трогает, им — `sed` вручную) → обычный ход чата (упавший Filter ломает все чаты). Канон — `/root/vps-infra/assets/stack/webui-tools/{file_memory_tool,file_memory_filter}.py` (зеркало `ai-stack/ai/webui-tools/`, рабочая копия `/root/.hermes/tasks/file-memory-step3/` — не путать с rsync-зеркалом в `/var/lib/hermes-state/repo`). Деплой — `POST /api/v1/functions/id/<id>/update` и `/api/v1/tools/id/<id>/update` с токеном `HERMES_CUSTOM_127_0_0_1_8080_API_KEY` из `/root/.hermes/.env`; OWUI держит модуль функции в кэше по хешу `content`, поэтому рестарт `open-webui` не нужен, а совпадение живого контента с `built/` проверяется чтением из `webui_db`. Тесты памяти требуют `pydantic`, которого нет в python Hermes: гонять их в одноразовом venv (`uv venv` + `uv pip install pydantic`), иначе падает импорт `memory_filter` до первого теста.
- **Проактивное сохранение памяти нигде не предписано — это поведение модели, а не механика.** В контракте описано только *куда* и *как* писать; правила «сохраняй важное сам» нет, поэтому инициатива зависит от модели (Terra сразу зовёт `memory(append)`, DeepSeek сначала `memory(list)`). Не обещай владельцу, что факт запомнится без просьбы. Проверять выбор Tool дёшево и без записи на диск: `POST /api/chat/completions` тулы не исполняет — модель возвращает `message.tool_calls` (там и видно, что она выбрала бы), файлы при этом не меняются; сверять счётчики PROFILE/MEMORY до и после. Если нужна предсказуемость — правило добавлять в управляемый блок AGENTS.md через шаблон provisioner, а не в код.
- **Удаление пользователя OWUI не убирает все хвосты.** Отдельно проверять: каталог `/home/ai_service/sandbox/users/<slug>` может остаться без аккаунта, запись в `/home/ai_service/sandbox-users/state.json`, строки `access_grant` и созданные под тест `model`. Чистить в порядке: бэкап (model/grants/state/tar каталогов) → гранты и модель → каталоги → ключи в state.json → прогон provisioner и ход чата для проверки.
- **`checked` в `.memory-state.json` ключуется хешем текста записи.** Та же формулировка второй раз не классифицируется. В e2e-прогонах давать маркеру уникальный суффикс, иначе тест молча не проверяет раскладку и выглядит как поломка механизма.
- **Бэкап строк БД от имени postgres не пишется в `/var/backups`** (0700 root): снимать откат через `sudo -u postgres psql -XA -tA -c "select json_agg(…)" > файл` от root и сразу `chmod 600`.
- **Оформление файлов памяти.** Каждая новая запись — один пункт Markdown в одну строку: `- **Ключ:** текст`. Tool отклоняет абзацы, записи с переносом строки и пункты без жирного ключа (`_check_entry`), поэтому разметку гарантирует код, а не инструкция в AGENTS.md; внутренние переносы (перенос унаследованных записей фильтром) идут с `strict=False`. Парсер (`_records`) считает записями каждый пункт `- ` и каждый абзац, а `## ` и `<!-- … -->` пропускает — старые записи-абзацы остаются читаемыми и удаляемыми, но новые так не пишутся. Не собирать список в один абзац без пустых строк: пункты без разделителей склеиваются в одну запись. **Гарантию держит код, не промпт:** владелец считает дублирующие правила в AGENTS.md лишними («запись же функция делает») — при жалобе на формат правь `_check_entry` в Tool и оставляй в шаблоне одну фактическую строку, а не абзац требований. Это про детерминизм файла; поведенческие правила (что и когда сохранять) по-прежнему живут в шаблоне AGENTS.md, потому что код их не заменит. Файлы `.agents` переписывай атомарно (`os.replace`) от root с `chmod 644`: `_read` требует `st_uid==0` и `st_nlink==1`, иначе целый файл памяти перестаёт читаться и Filter уходит в WARNING. После любой конвертации или рассылки шаблона прогоняй `scripts/audit-memory-format.py` (берёт парсер и `RECORD_FORMAT` из канонического Tool, код 1 = есть записи не в формате); для крупных переписываний — сверять не только формат, но и сохранность фактов спот-чеком по 3–4 характерным строкам каждого файла. **Правя шаблон AGENTS.md в provisioner, держи два инварианта:** новый файл создаётся как `AGENTS_HEADER + AGENTS_TEMPLATE` (без `# AGENTS` заголовка повторный прогон меняет файл — ловится `test_provisioner_staged`), и `<!-- managed:end -->` обязан стоять на своей строке, иначе маркер приклеивается к тексту последнего правила и попадает в его запись. Пункты внутри управляемого блока парсер считает записями — это нормально, `#`-заголовки и строки-комментарии он пропускает.
- **Противоречия в памяти.** Детектор `_find_conflicts` (Terra) идёт параллельно с классификатором, сравнивает новые записи с противоположным файлом и кладёт пару в `.memory-state.json` → `conflicts`. Filter прикладывает в outlet детерминированное уведомление с двумя записями и просьбой «оставить 1/2»; ответ разбирает `_ask_keep` (десижн-модель), проигравшая запись удаляется, при `unclear` — ничего. Модели запрещено дублировать вопрос своими словами. E2E: Москва/Краснодар → выбрали 2 → MEMORY очищена. Ход с новыми записями ~6 с, обычный ~4 с.
- **Автоматическая раскладка памяти (новая механика).** Назначение файлов: AGENTS — инструкции и стиль поведения (сюда же системный промпт пользователя), PROFILE — факты о человеке, MEMORY — заметки и проекты. Правка = новая запись + удаление старой (`replace` в Tool работает так). Filter после чтения файлов берёт записи, которых нет в `.memory-state.json` → `checked`, отправляет одной пачкой в `service.openrouter/gpt-6.1-terra` (JSON с `sure`) и переносит только однозначные между MEMORY и PROFILE, максимум 3 за ход; AGENTS автоматически не меняется. Классификатору нужен отдельный `classifier_key` (мастер-ключ LiteLLM): ключ `/openrouter/alpha/decisions` на `/v1/chat/completions` даёт 401. Деплой: сначала content функции, потом valves — иначе новые поля молча не сохраняются. Молчаливые сбои смотреть в `place_error` внутри `.memory-state.json`. E2E: запись «У неё двое сыновей…» переехала MEMORY→PROFILE в реальном ходе.
- **Файловая память WebUI — подробности реализации и проверки.** Прочитать `/root/.hermes/tasks/docs/owui-file-memory.md`, учитывая более поздние решения владельца: `.agents` целиком исключить из LRU; только `MEMORY.md` ограничивать ориентиром 10000 символов с исследуемым мягким переполнением; `PROFILE.md` и `AGENTS.md` не ограничивать по общему размеру; для записи в MEMORY ориентир 200 символов, жёсткий предел 400; формулируй записи максимально компактно с сохранением смысла, а не заполняй лимит ради лимита. В PROFILE ограничения длины одной записи нет. При согласованной миграции встроенной памяти сначала сохрани оригиналы и метаданные с возможностью отката, затем подготовь компактное саммари каждой записи. Сверь существенные факты и условия, длину каждой записи и суммарный размер по пользователям; не разбивай текст по символам посреди мысли, поскольку удаляемые записи должны оставаться понятными самостоятельно. Положительный вердикт модели-проверяющего не доказывает точность саммари; инструкцию формулировать компактно не выдавай за гарантию краткости. Если всё не помещается в мягкий лимит без потери смысла, не урезай дополнительно без согласования и не отключай источник до подтверждённого переноса. Владелец принимает риск большого PROFILE и готов разбираться по факту. При нехватке места показывать пронумерованный список записей без пагинации, предлагать удалить floor(25% количества), пользователь выбирает текстом несколько; перед удалением перечитать файл и сверить выбор. Владелец отказался от автоматического удаления после игнорирования. В пилоте запись, пересекающая мягкий предел MEMORY, сохраняется целиком; последующее увеличение блокируется, сокращение и выбранное удаление разрешены. Сверяй ответы модели с фактическими результатами Tool: модель может ошибочно заявить об обрезании, даже если файл сохранён целиком. При отказе и повторных игнорах ничего не удалять; напоминать до освобождения места. Не считать пилот окончательной приёмкой. После изменения показать записи и спросить «Оставляем или есть правки?», после подтверждения — «Сохранено, можем продолжить разговор». Для decision владелец выбрал `perplexity/pplx-decider-v1.2` через OpenRouter; проверяй решение модели по фактическим файлам и стадиям, а не по её обещаниям. Пилот не принят. Владелец отменил автоматическое удаление и изучает мягкое переполнение и отложенные напоминания; эксперимент с вызовом Tool из Filter откатан и не должен возвращаться. Подробности — `/root/.hermes/tasks/docs/owui-file-memory.md`. Если память не удалось прочитать или привязку пользователя подтвердить, отвечать без памяти с заметным предупреждением, не использовать чужой каталог. Проверять Decisions API отдельно от обычного chat completions и не считать модель подключённой без успешного сквозного вызова. Контролируемая архитектура: отдельный Tool выполняет добавление и удаление с проверкой лимитов; Filter подставляет память в префикс и контролирует состояние переполнения, а выбранная владельцем decision-модель классифицирует ответы и проверяет семантические границы файлов на каждом ходе. Владелец принял риск редкой гонки и потерянного изменения: сложную защиту от параллельной записи пока не строить и не обещать целостность. При отказе записи результат Tool должен отражать отказ без отдельной инструкции модели уведомлять или скрывать его. Не рассчитывать на inlet как перехват произвольной терминальной записи: закрыть прямую запись в `.agents` песочнице и оставить запись доверенному Tool. Вложенный read-only bind mount `.agents` внедрён в персональных песочницах: проверяй чтение и запрет записи, а защиту от переименования — на синтетических данных; Tool и Filter прошли пилотный сценарий записи, чтения, изменения и удаления тестового факта; это не приёмка всей системы и не доказательство полноценной межпользовательской изоляции → `references/sandbox-terminal.md`. До внедрения проверить изоляцию, доверенный путь записи и хранение состояния; не выдавать инструкции модели за гарантию. При переполнении Tool сообщает модели о необходимости чистки; если она не предложила её сразу, Filter повторяет указание на следующем ходе. Приёмку веди на синтетических данных через реальные многoходовые чаты: сверяй поток, сохранённый ответ, вызовы Tool, файлы и этап состояния после каждого хода — unit-тест автомата не доказывает, что модель выполнила изменение или показала список. Проверяй показ полного списка непосредственно в ответе на запись, пересёкшую предел, затем короткое напоминание на игнор и повторный полный список по просьбе: вызов другого инструмента может прервать выдачу, а многократное повторение списка мешает разговору. Флаг добавления списка в outlet не доказывает его прочтения: после отключения клиента сохрани напоминание и возможность снова запросить список. Не выдавай событие или сохранённый текст за проверку экрана; проверяй, не вывела ли модель сокращённый дубль перед точным списком Filter: тест на наличие полного списка этого не ловит. По решению владельца перед каждым полным списком Filter обозначай его как автоматическое уведомление, не ответ модели, и указывай выбирать только записи из списка ниже; краткие напоминания без списка не удлиняй. Проверь в Chromium первый и повторный список, список после удаления и отсутствие пометки в кратком напоминании; сравни фактически удалённые записи с выбранными, потому что пометка уменьшает путаницу, но не гарантирует правильность действий модели. Для детерминированного Markdown от Filter отделяй текст после нумерованного списка пустой строкой и проверяй скриншот и DOM (`p` вне `li`): иначе рекомендация или вопрос попадут внутрь последнего пункта. Испытай отключение клиента до ответа: отправка события или сохранение в истории не доказывают доставку предупреждения пользователю. Проверяй отображение отдельно от сохранённого outlet-ответа: outlet не переписывает уже отправленный поток. При изменении правил обновляй тесты старого поведения и отдельно разбирай новые ошибки; не считай выборочный зелёный набор полной приёмкой. Для этой задачи владелец исключил замер cache hit и пока разрешил пропустить бэкапы файлов памяти и проверку восстановления; явно отмечай их отсутствие в отчёте. Проверяй политику лимитов PROFILE отдельно в Tool и в provisioner на синтетическом промпте больше 5000 символов: согласованное отсутствие лимита в Tool не доказывает, что миграция не заблокирована старой проверкой. Provisioner должен создавать недостающие файлы до запуска и переносить промпт в новый PROFILE без обрезания и перезаписи существующего; на изолированном длинном синтетическом промпте сравни перенесённый текст целиком, затем повтори инициализацию и проверь неизменность файлов. Перед отключением пользовательских промптов проверь не только полное совпадение PROFILE с исходным промптом, но и то, что Filter и Tool доступны в обычных чатах затронутых пользователей: пилотная модель не покрывает остальные чаты, и иначе контекст может пропасть. Проверь фактическое поведение существующих настроек после изменения разрешения: запрет редактирования не доказывает, что сохранённый промпт перестал подмешиваться. Исходники до проверки нового пути не очищай; переключение и очистка БД требуют согласования. Основной админский промпт пока оставлять включённым; промпты моделей не трогать. Основные правила разделения файлов и согласованный приоритет при конфликте явно задавать для существующих и новых профилей и проверять реальным конфликтным запросом в Chromium: порядок блоков и один успешный API-прогон не гарантируют поведения модели. При проверке семантического переноса отдельно проверь конфликтующие записи: предложение переноса не должно подменять приоритетное значение противоречащим без уточнения и согласия. Заголовки файлов поясняют их назначение. Семантический перенос выполняет фильтр памяти сам, без подтверждения: новая запись в нужном файле и удаление старой; инструкции (включая системный промпт пользователя) живут в AGENTS.md, факты о человеке — в PROFILE, заметки и проекты — в MEMORY; из AGENTS автоматически ничего не убирается. При противоречии двух записей фильтр спрашивает пользователя, что оставить, и удаляет проигравшую только по его ответу. Тексты промптов не выводить; путь к полю, ограничения разрешения и проверка миграции — `references/owui-internals.md`. Проверить привязку пользователя и изоляцию, защиту `.agents` от LRU, срок жизни при удалении аккаунта и бэкапы; согласовать изменения рабочего стека отдельно. Изменение шапки влияет на кэш, удаление из файла не удаляет факт из истории или бэкапов. Не добавлять Git, субагентов, сервисы или форк WebUI вместо согласованных точек расширения.

## Answering the owner

A question like «подходит ли эта модель под задачу», «какой уровень достаточен», «стоит ли брать X» wants a **verdict first**: what fits, what does not, and the one trade-off that decides it. Do not open the stack to answer it — no probes, no log digging, no spend queries. Measure only when the ask is explicitly «проверь», «прогони», «сравни».

- **«Проверил?» про механизм — отвечай перечнем проверенного, а не «да».** Называй по пунктам, что именно прогнано (чтение, запись, переполнение, UI, изоляция), и отдельно — чего не проверял. Если проверен только happy path, так и скажи; иначе владелец считает отчёт заявкой на полную приёмку.

- «почему медленно» → measure first (per-URI `rt` from nginx, then `docker stats`/`load`); two standing causes (LiteLLM admin bundle, one WebUI worker + avatar burst); never propose trimming the model list → [references/ui-latency.md](references/ui-latency.md).
- **Браузер для WebUI: `web.loader.engine=playwright` + `web.loader.playwright_ws_url=ws://playwright:3000`** в `config` (тип `json`, строки в кавычках) — после правки строк БД нужен рестарт `open-webui`, иначе приложение не перечитывает значения. `web.search.bypass_web_loader=false`, поиск остаётся SearXNG. Проверка рендера — `POST /api/v1/retrieval/process/url` на странице, где контент появляется только после JS (`quotes.toscrape.com/js/`): ответ `content`, а не `page_content`. Отдельный Tool `web_browser` (`browse_page(url, wait_for_selector, max_chars)`) ходит в тот же сервер по WS; он привязан через `model.params.tool_ids` к моделям `chat.*` (26) — API `chat/completions` выполняет тул только в UI-пайплайне, поэтому при проверке через API ждать `message.tool_calls`, а не готовый ответ. Tool без привязки к модели доступен из панели Tools в чате. Откат: `tool_ids` убрать, `web.loader.engine=''`, `docker compose rm -sf playwright`; бэкапы — `docker-compose-before-playwright.yml`, `models-chat-params-before-tool.json`.
- «поиск получше» → page fetching, not the model; engines never chain → [references/web-search-architecture.md](references/web-search-architecture.md).
- **«Аватарки моделей пропали»** — не искать потерянные файлы: картинка лежит в `model.meta.profile_image_url`, `/api/models` вырезает это поле намеренно, а статус `302` на `/api/v1/models/model/profile/image?id=…` = подмена на дефолтный логотип (у connection-строк `chat.*`/`aider.*`/`hermes.*`/`other.*` картинки нет вообще). Частая причина «всё пропало» — гонка на холодном старте: батч `401`, затем те же id `200`, а SPA уже поставил заглушку и не повторяет запрос. Сначала статусы по id из `access.log`, потом вывод → [references/model-provenance.md](references/model-provenance.md).
- **Жалоба на качество модели («дипсик галлюцинирует», «врёт», «городит лишнее»)** — не соглашаться и не защищать модель по памяти: открыть сам чат в `webui_db` и **посчитать `function_call` в `message.output[]`** (не `tool_calls` — этого поля в чате нет). Нулевой счёт = выдуманная проверка; любой найденный вызов = речь про качество ревью, а не про галлюцинации. Рецепт, толкование и что с этим делать (привязать терминал) → [references/owui-chat-forensics.md](references/owui-chat-forensics.md).
- **Не путать «чат» с «харнессом»**: Open WebUI + модель — это тонкий нативный tool-loop, у него нет лимитов шагов, политик, трейса и стоимости прогона; отсюда и предложения «собрать свой OpenCode». Прежде чем соглашаться на второй оркестратор, проверить, что уже работает (Hermes на этом же хосте = полноценный харнесс), и называть цену: 3–6 недель до паритета. Полезная часть такой идеи — изолированный терминал и трейсинг+evals, а не второе ядро.
- **Чужой разбор нашего стека (экспорт Gemini/GPT, чужой агент) проверять по хосту пункт за пунктом** и отдельно называть то, чего его автор видеть не мог: он смотрел один контейнер и не знал про харнесс на хосте. Не поддакивать красивой формулировке и не опровергать её без проверки — оба направления ошибаются одинаково дорого.
- **«сделай нормально, костыли мне не надо»** — не предлагать второй вход на высоком порту, отдельное имя, ручной обход или «пока попробуй так»: владелец считает это костылём и злится сильнее, чем на нерешённую задачу. Работающая ветка — замер (лог → пакеты) и устранение причины; он готов сам потыкать, пока идёт capture, поэтому просить именно воспроизведение, а не тесты.
- **Не предлагать «запатчим апстрим» или «форкнем» как ответ на чужое узкое место** — «ты предлагаешь патчить чужой недокументированный код, так себе план». Порядок ответа: родная ручка апстрима (env/конфиг/флаг) → измерение → и только по его слову дериватив образа (тот самый `webui-branding/Dockerfile`, который мы уже собираем ради брендинга). Лицензия — тоже аргумент: у Open WebUI BSD-3 с пунктом о брендинге (не больше 50 юзеров за 30 дней без разрешения), поэтому наш ребрендинг легален пока нас 8, а «станет продуктом» — уже разговор с ними.
- **«Модель / Image Generator не видит прикреплённое фото»** — почти всегда маршрут, а не OWUI и не инструмент. Диагностика в два счёта: `api_base` в `LiteLLM_SpendLogs` (какая нога ответила) и `prompt_tokens` одного и того же запроса с картинкой и без (сотни против 13–19 = картинка доехала / не доехала). Слепая нога молчит, потому что группа всё равно объявляет `supports_vision: true`. **Боевой порядок группы `openai/gpt-6.1-terra`: `order=1` белая SIWC-нога (`host.docker.internal:4010`), `order=2` OpenRouter (`openrouter/openai/gpt-6.1-terra`, credential `Openrouter LiteLLM`, цены 1e-6/5e-6), `order=3` серая `chatgpt/`** — подписка основная; OpenRouter сдвинут выше серой ChatGPT-ноги по решению владельца (2026-11-13), группа-фолбэк в `router_settings.fallbacks` для terra убрана по решению владельца (2026-11-13) — приоритет живёт только в `order` ног группы; мост научен пробрасывать `input_image` (`/root/siwc/gateway.py`, копия в `vps-infra/assets/host/siwc/`). Вложения-документы — отдельная ось: при `capabilities.file_context=false` OWUI вырезает `files` из сообщения и RAG даже не вызывается. И `base_model_id` кастомной модели обязан быть видимым id соединения (`<prefix>.<группа>`, напр. `other.service.openrouter/gpt-6.1-terra`), а видимость задаётся списком `models` у LiteLLM-ключа → [references/media-pipeline.md](references/media-pipeline.md), skill `openai-siwc-gateway`.
- «защищён / бэкапы / восстановлю за 30 минут» → verdict + evidence per claim, skill `vps-posture-assessment`; restore proof is `/backups` and `monitor.py verify`, not the digest, and secrets do have an offsite copy → [references/backups-notifications.md](references/backups-notifications.md).
