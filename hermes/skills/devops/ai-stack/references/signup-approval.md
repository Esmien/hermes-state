# Signup approval and user administration

> Loaded from the `ai-stack` skill. Read this when pending signups, the Telegram approver, user roles via the API.

## Signup approval bot (pending users → Telegram)

- **`owui-signup-approver.service`** (root, `Restart=always`, enabled) runs `/usr/local/bin/owui-signup-approver.py`: every `TICK_SECONDS` (120) it reads `select id, name, email, created_at from "user" where role='pending'` straight from `webui_db` and sends the owner (`TG_OWNER=214062001`) a message with `✅ Принять` / `🗑 Удалить`; the same process long-polls `getUpdates` (`allowed_updates=["callback_query"]`) so presses act immediately. Config `/root/.config/owui-signup-approver/env` (600: token, owner, DSN — DB/OWUI passwords are read from `ai/.env` at runtime, not duplicated), state `/var/lib/owui-signup-approver/state.json` (600, offset + notified ids), log `/var/log/owui-signup-approver.log` (logrotate weekly ×8). CLI: `--check`, `--once`, `--whoami`, `--approve <id>`, `--reject <id>`.
- **A systemd timer cannot receive button presses** — callbacks only arrive through a long-poll, and two pollers on one bot token return `409 Conflict` (that is why this bot is separate from `server-monitor-bot`/`BOT_TOKEN`). One process doing tick + long-poll is the correct shape.
- **Approve = SQL, reject = admin API, deliberately.** `UPDATE "user" SET role='user'`, not the API: role is loaded per request from the DB (Redis caches only token revocations), so it applies instantly and needs no JWT. Reject goes through `DELETE /api/v1/users/{id}` because only 3 FKs cascade from `"user"` (`api_key`, `group_member`, `oauth_session`) while ~40 tables (`chat`, `file`, `memory`, `folder`, …) hold `user_id` with no FK — a raw `DELETE` would orphan rows and uploads.
- **Do not expect OWUI webhooks to reach a local listener.** `utils/webhook.py::validate_url` blocks loopback/private targets, so an `auth.signup` webhook would need a public nginx path. Polling the DB avoids that entirely.
- **Pending users have no content**: `get_verified_user` rejects `role='pending'` with 401, so a rejected signup never leaves chat/file orphans. OWUI sends them nothing either — no SMTP configured, no email verification; the bot only ever messages `TG_OWNER`, and every callback checks `from.id`.
- **Every callback and long-poll batch is now logged** (2026-10-23): `callback: action='r' uid=… from=… message_id=…`, `delete confirmation requested/cancelled for …`, `getUpdates: N update(s)`, and a `poll loop was stalled for Ns` warning when an iteration takes >90 s. Before this the `🗑 Удалить` branch wrote nothing on success, so a press that never arrived and a press that was handled looked identical in the log — when the owner says «кнопка не работает», read these lines FIRST and only then suspect the code. A one-off «подвисло и раздуплилось» is consistent with a stuck `urlopen` on the 25 s long poll; a repeat will now leave a timestamped stall line.
- Verify end-to-end by creating a throwaway signup (`POST /api/v1/auths/signup`, returns `role=pending`), forcing a scan (`systemctl restart`), then driving the code path in-process (`importlib` + `handle_callback` with a synthetic `callback_query`) — a real press cannot be automated; `answerCallbackQuery` will 400 `query is too old` on synthetic ids, which is expected. Clean up with the same admin `DELETE`.

## Turnstile gate on signup (2026-11-05)

- **`turnstile-gate.service`** (root unit, runs as `nobody`, 127.0.0.1:8099) is the `auth_request` backend for `POST /api/v1/auths/signup`: nginx sends the `cf-turnstile-response` header to `/verify`, the service calls CF `siteverify`, and denies on 403. Keys live in `/etc/turnstile-gate.env` (root:nogroup 640 — a 600 root file makes the unit crash with `PermissionError`, that was the first failure).
- **The gate is inert without keys**: empty `TURNSTILE_SITEKEY`/`TURNSTILE_SECRET` → `/verify` answers 200 and `/config` reports `enabled:false`, so registration works exactly as before. `siteverify` being unreachable also answers 200 (fail-open on infrastructure failure, deliberate).
- **Widget is injected by our own script**, not upstream: `ai/webui-branding/turnstile-gate.js` is COPY'd into `/app/build/static/` and a `<script>` tag is sed-inserted after the `custom.css` link in `index.html`. The script asks `/_turnstile/config` for the sitekey, renders the widget into the signup form (`input[autocomplete="new-password"]` is the marker), and attaches the token to `fetch`/XHR on `/api/v1/auths/signup`. OWUI 0.13.0 still has zero native captcha support.
- **`auth_request` subrequests arrive as GET**, so the verifier serves `/verify` on both GET and POST — a POST-only handler yields `auth request unexpected status: 404` and nginx turns it into **500**.
- **Test the whole chain with Cloudflare's dummy keys**, never with the live ones: sitekey `1x00000000000000000000AA` + secret `1x0000000000000000000000000000000AA` always pass; swap them into `/etc/turnstile-gate.env`, restart the unit, run a Playwright signup, then restore and delete the probe user with `owui-signup-approver.py --reject <id>`. Headless Chromium cannot solve a real managed challenge (token stays empty) — that is the expected "bot" result, not a broken widget.
- **Origin is Cloudflare-only for `ai.esmien.ru`:** the 443 vhost returns 403 unless `CF-Connecting-IP` is present (`map "$is_via_cf:$is_acme_path" $deny_direct` in `/etc/nginx/conf.d/01-cf-client-ip.conf`, because nginx will not accept two adjacent variables in one `if`). The ACME path is exempt by map, so HTTP-01 still works directly; the wildcard cert used by the vhost renews via DNS-01 anyway (`certbot renew --dry-run --cert-name esmien-wildcard` passes).
- **Proxy in front changes what nginx sees:** with `ai.esmien.ru` proxied through Cloudflare, `$remote_addr` is the CF edge, so limits must key on `map $client_ip` (`CF-Connecting-IP`, else `$proxy_protocol_addr`) — see `/etc/nginx/conf.d/01-cf-client-ip.conf`. The realip module does not fix this chain.
- CF-side layers that are cheap on the free plan: a WAF custom rule blocking `POST /api/v1/auths/signup` without `Mozilla` in the UA, and Bot Fight Mode (dashboard only — API tokens get `Method not allowed for this authentication scheme`). Free-plan rate limiting is useless (10-second window, 10-second mitigation).

## Auth hardening: fail2ban jail, security headers, MFA (2026-11-05)

- **fail2ban cannot use iptables here.** Behind Cloudflare every TCP peer is a CF edge IP, so banning the real client with iptables/drop does nothing. The `owui-auth` jail (`/etc/fail2ban/jail.d/owui-auth.local`, filter `nginx-owui-auth`, action `nginx-deny-ip`) instead writes `/etc/nginx/owui-blocks/<ip>.conf` and reloads nginx; `map $client_ip $owui_banned_ip` (in `01-cf-client-ip.conf`) feeds it, and only the `/api/v1/auths/signin|signup` locations consult it (`if ($owui_banned_ip) { return 403; }`) — a ban therefore never locks the whole site. Verified end-to-end with `fail2ban-client set owui-auth banip <own-ip>` (signin 403, `/auth` still 200) and `unbanip`.
- **`limit_req` zones are per-endpoint:** `webui_signup` 3 r/min and `webui_signin` 10 r/min, both keyed on `$client_ip`. A referenced zone that is not defined fails the config with `zero size shared memory zone` — check both files when editing.
- **Security headers live in the ai vhost** (`Strict-Transport-Security includeSubDomains`, `X-Frame-Options SAMEORIGIN`, `X-Content-Type-Options nosniff`, `Referrer-Policy`). No CSP on purpose: the Svelte SPA relies on inline styles and blob workers, a policy would need real iteration against the UI.
- **MFA in OWUI is global and mandatory.** `is_mfa_required()` in `utils/mfa.py` returns True for every password login as soon as `auth.mfa.enable` is true — there is no per-user opt-in, so flipping it forces every existing user to enrol a TOTP app on their next sign-in. Do not enable it on a shared instance; it was enabled once here, hit exactly that, and rolled back to false. Admin-only TOTP needs an external gate (nginx `auth_request` + own TOTP check), not this switch.
- **`POST /api/v1/auths/api_key` ROTATES the key**, it does not return the existing one. Calling it to "get a key" silently invalidated the key Hermes itself uses for the Open WebUI provider (`HERMES_CUSTOM_127_0_0_1_8080_API_KEY` in `/root/.hermes/.env`), and every OWUI-backed auxiliary call (vision, extraction) started returning 401 until the gateway was restarted. Read the key from the approver env or the DB instead; if rotation already happened, copy the new key into both places and restart the gateway.
- **The Turnstile widget must be scoped to the signup form.** `input[autocomplete="new-password"]` also exists on Settings → Account (password change), so the old selector dropped a widget there as a visible artifact. The script now requires `location.pathname` in `''`/`/auth` (never `/settings*`, `/workspace*`), no `current-password` field in the form, and an email field; it also removes the widget when the form disappears.
- **The injected JS is cached by Cloudflare for ~4h** (`/static/*.js` → `cf-cache-status: HIT`, `max-age=14400`), while the certbot DNS token has no cache-purge rights (`401 Authentication error` on `/purge_cache`). Any change to `turnstile-gate.js` therefore needs a version bump in the Dockerfile's `?v=N` on the script URL; plain rebuilds look fixed on origin and stay broken through the edge.
- **MFA:** OWUI 0.13 supports it, but the switch is **the DB row** `auth.mfa.enable` (`Config.get_many` in `utils/mfa.py`), not the env var — and `from open_webui.config import ENABLE_MFA` still prints `False` after the row is true, so verify with `asyncio.run(get_mfa_config())` inside the container, not with the module attribute. The value is read per request, so flipping the row takes effect without a restart (existing enrolled users keep their secret in storage but are no longer challenged while the flag is false).
- **The approver must not use password signin once MFA is on for the admin.** `owui-signup-approver.py` prefers `OWUI_ADMIN_API_KEY` (its `env`) and falls back to the password only when the key is absent. **Never mint that key with `POST /api/v1/auths/api_key`** — the endpoint *regenerates* the admin key and the previous one dies on the spot, so every consumer breaks at once: Hermes' own Open WebUI provider (`HERMES_CUSTOM_127_0_0_1_8080_API_KEY` in `/root/.hermes/.env`) starts returning `401 {"detail":"Your session has expired or the token is invalid"}` on aux calls (`vision_analyze`, compression) while the main provider keeps answering. Read the existing key instead — it is stored in clear in `select api_key from "user" where role='admin'` — or mint once and immediately propagate it to *all* consumers (Hermes `.env`, approver env).
- **A rotated/changed key needs a gateway restart.** Hermes reads its env at process start and keeps it in memory, so fixing `/root/.hermes/.env` does not un-break the running process; the owner restarts (`systemctl restart hermes-gateway`) — an agent cannot restart its own gateway mid-session. Prove the key before blaming Hermes: `GET /api/v1/models` with `Bearer <key>` must return 200 and a model count.
- `--whoami` on the approver checks the Telegram bot, NOT the OWUI admin auth — prove admin auth with a real admin call such as `GET /api/v1/users/all` (expect 200).
- **`secrets-offsite-backup.py` had a fixed list of `.env` paths** and missed `/etc/turnstile-gate.env` and `/root/.config/owui-signup-approver/env`. Both are now in `SOURCE_PATTERNS`; any new credentials file has to be added there or it silently stays host-bound.

## User administration & signup approval (Open WebUI API)

- **Admin auth for scripts:** `POST /api/v1/auths/signin` with the email from `select email from "user" where role='admin'` plus `OWUI_ADMIN_PASSWORD` from the approver env (`UI_USERNAME` is NOT an email; `UI_PASSWORD` is LiteLLM's) JWT lives `auth.jwt_expiry`, default `4w` (`JWT_EXPIRES_IN`, `-1` = never) — cache the token in memory and re-signin on 401 instead of inventing a long-lived credential.
- **`GET /api/v1/users/all` returns `{users:[…], total:N}`** (an object, not a bare list). Each item has `id, email, name, role, is_active, last_active_at, groups, bio, status_*` but **no `created_at`** — track "already notified" by id in the caller's own state file. `GET /api/v1/users/` is a different shape (`UserGroupIdsListResponse`); `/api/v1/users/search` is paginated and open to non-admins.
- **Approve / delete a registration:** approve = `POST /api/v1/users/{id}/update` with `{"role":"user"}` (admin; emits `user.role.updated`); delete = `DELETE /api/v1/users/{id}` (admin, returns bool). There is no `/auths/update/role` and no dedicated approve endpoint in 0.12 — a hand-written SQL role `UPDATE` skips the event and any cached role, so always go through the users router.
- Signup policy is persistent config, not env: `ui.enable_signup` and `ui.default_user_role` (`pending` here). Count the queue authoritatively in SQL: `select count(*) from "user" where role='pending'`. When reading through the API, filter the returned list by `role` and confirm the pending row is actually present before trusting the API path end-to-end (0.12 keeps pending accounts in the same `user` table but the list endpoint was not exercised against a live pending row here).
- **Native event webhooks cannot reach a listener on this host.** 0.12 defines `auth.signup` / `user.*` events plus event webhooks, but `utils/webhook.py::validate_url` rejects loopback and private-IP targets, so the URL must be publicly resolvable → an nginx path with TLS and a secret token. Since a Telegram flow needs inline buttons and callback handling anyway, a local poller + `getUpdates` is the smaller build; name the webhook route only when instant delivery is a hard requirement.
- **There is no built-in captcha in Open WebUI 0.12.5** — grepping the backend for `turnstile|hcaptcha|recaptcha|captcha` returns nothing, so «поставить галочку в настройках» is not an option, and a captcha cannot be added without patching the frontend build. What actually bounds signup spam: `ui.default_user_role=pending` + the approver (a bot account never gets access and leaves no content), plus the edge layer — on this host that is a Cloudflare WAF rule blocking `POST /api/v1/auths/signup` whose UA lacks `Mozilla`, plus an nginx `limit_req` of 3/min keyed on the real client IP. Cloudflare's own rate limiting is not usable on the Free plan (10-second window) and Bot Fight Mode is dashboard-only (`references/cloudflare-proxy.md`). Say plainly which layer does what: `pending` prevents damage, the edge layer prevents the noise.
- **Count the spam before building anything.** Signup attempts are in `/var/log/nginx/access.log`; `grep 'auths/signup' … | awk '{print $1, $9}' | sort | uniq -c` shows whether it is a scanner trickle or a campaign, and the pending count in SQL shows what got through. Report those two numbers instead of an opinion about whether bots are a problem.
- **Bucket `auths/signin` attempts by hour and by status before calling it an attack.** A log block of failed signins reads like credential stuffing; splitting the same lines by `\[[0-9]{2}/[A-Za-z]{3}/[0-9]{4}:[0-9]{2}` and by response code showed 54 attempts inside one minute many hours earlier, 30×`400` + 24×`429`, every one with `Referer: https://<origin-ip>/` — a scanner hitting the bare IP, already cut off by the limit. Say «было N попыток в час X, лимит срезал M» instead of «брутфорсят прямо сейчас»: a false alarm about an attack costs the owner the same trust as a missed one. Same discipline for any «нас атакуют» claim — timestamps, status codes, referer, then verdict.
- **One `getUpdates` poller per bot token.** `server-monitor-bot.service` already long-polls `BOT_TOKEN`, so a second service on the same token dies with `409 Conflict`; either extend that service's loop (add a `callback_query` branch and persist `offset`) or take a separate bot token for the new flow.
