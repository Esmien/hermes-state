# Memory, disk headroom and DB growth

> Loaded from the `ai-stack` skill. Read this when disk fills up, RAM climbs, dumps/logs/images grow; open-terminal heap floor.

## Memory & disk headroom

- **Host-level filesystem reclamation (Docker/containerd images, build cache, orphan volumes, snap revisions, journald) is a separate procedure — see the `vps-disk-reclamation` skill.** The disk-growth notes below are specific to Open WebUI DB ingest, not to the general «what eats disk» question.

- **RAM: 7.8 GB, and swap is a 4 GiB `/swapfile` (in `/etc/fstab`, `vm.swappiness=10` in `/etc/sysctl.d/99-swap.conf`).** Before this fix there was NO swap at all, and no container had a memory limit (`Memory=0`, cgroup `memory.max=max`) — so one container's spike triggered a **global** OOM kill that took down whatever the kernel picked by `oom_score`, including `open-webui` and `hermes-gateway` itself. If OOM symptoms return, check `/etc/fstab` still has the swapfile and `swapon --show` shows it active — a host reboot without the fstab line silently drops back to zero swap.
- **Attribute the RAM before naming a cause; full procedure in `references/memory-troubleshooting.md`.** Flat RSS across samples + long uptime + `RestartCount=0` = a static allocator footprint, **not** a leak — never propose a restart cron for it. Many anonymous `rw-p` regions of ~64 MiB on a 64 MiB stride in `/proc/<pid>/smaps_rollup` = **glibc malloc secondary arenas** (default max `8 × ncores`, driven by the process's thread count); fix with `MALLOC_ARENA_MAX=2`, which the loader reads at process start so it needs a container **recreate**. Add `mem_limit` at the same time.
- **LiteLLM's ~1.4 GB is retained Python heap, not a leak signature and not libraries — and the reasons are config-specific, so enumerate them instead of guessing. Full breakdown in `references/memory-troubleshooting.md` §7.** Measured here: `[heap]` ~700 MB + anonymous mmap ~650 MB, file-backed ~55 MB only, plus a separate ~50 MB Prisma query-engine child; RSS sampled flat while idle with 31 h uptime and `RestartCount=0` ⇒ static footprint, no restart cron. The triggers to name: `STORE_MODEL_IN_DB=True` with all ~120 models in `litellm_db` (plus the failing 30 s sync loop above), `prometheus_client` installed so per-model/key series accumulate and are never freed, the spend-log in-memory queue, and no Redis ⇒ auth/router/LLM-client caches live in-process. **`litellm_db` is on the HOST PostgreSQL — query it with `sudo -u postgres psql -d litellm_db`, never `docker exec lyria-postgres psql -U postgres`** (that instance's superuser is `lyria` and it does not hold this DB; it answers `FATAL: role "postgres" does not exist`).
- **LiteLLM state lives in `litellm-redis` since 2026-10-19; response caching is deliberately OFF.** `REDIS_HOST/REDIS_PORT/REDIS_PASSWORD` + `depends_on: litellm-redis: condition: service_healthy` move auth-key cache, spend/rate-limit counters and router cooldown/health state out of the process (verify: keys like `spend:user:*`, `{api_key:*}:tokens`, `{model_per_key:*}` appear via `redis-cli --scan`, `DBSIZE` grows with traffic). **Never add `litellm_settings.cache: true`** — proxy-level response caching returns a stored completion for an identical request hash, which corrupts agent tool-calls and hides fresh context; the provider-side prefix cache is what should carry that job. Also set on `litellm`: `MALLOC_ARENA_MAX=2` (the same glibc-arena trap as open-webui) and `MAX_IN_MEMORY_QUEUE_FLUSH_COUNT=5000` / `MAX_SIZE_IN_MEMORY_QUEUE=500` (upstream #12685 spend-queue limits).
- **Owner rules for the gateway — do not propose these as "gaps" again:** (1) **no cross-model fallbacks, ever** — a broken group must surface the error, switching models is forbidden (so `router_settings.fallbacks`/`routing_groups` stay empty; the comment in `litellm/config.yaml` claiming «потом падает на fallback-модель» is stale and wrong); (2) **no budgets/rpm/tpm limits on keys** — the contour is private and single-user, `0/33` keys having limits is deliberate.
- **Prometheus is NOT enabled — `/metrics` answers 404.** The image ships `prometheus_client`, but that alone exposes nothing: LiteLLM needs `litellm_settings.callbacks: [prometheus]` in `config.yaml` (then `curl 127.0.0.1:4000/metrics -H "Authorization: Bearer $LITELLM_MASTER_KEY"`). Never cite "prometheus series accumulating" as a memory cost without checking that callback first — on 2026-10-19 the callback was absent and the claim was wrong. LiteLLM metrics give per-key/team/model spend & tokens, latency histograms, request/status counts, in-flight, cooldowns; enabling needs a restart. **Owner decision (2026-10-19): keep the callback OFF and build any reporting from `LiteLLM_SpendLogs` instead** (`request_duration_ms`, `status`, tokens, spend are all there) — do not re-propose Prometheus/Grafana.
- **Failed `/v1/models` and pass-through calls ARE written to `LiteLLM_SpendLogs` as `status='failure'`** (with `model_group=''`), so raw failure counts grossly overstate real LLM errors: 7 days here showed 94 111 "failures" of 98 013 rows, but 93 686 of them were one day's `/v1/models` burst from a host-side `curl` loop (`requester_ip_address 172.18.0.1`, user-agent `curl/8.18.0`). Always exclude `call_type in ('/v1/models','pass_through_endpoint')` before reporting an error rate.
- **Memory limits on `litellm`:** `mem_reservation: 3g` (soft) + `mem_limit: 3.5g` (hard) + **`memswap_limit: 3.5g`** — set the swap limit too, or Docker silently gives the container `2 × mem_limit` (7 GB here) of swap and a memory spike becomes swap thrash rather than an OOM-kill + restart. Changing limits needs a recreate (`up -d litellm`) or `docker update --memory-swap …` live; verify with `docker inspect … '{{.HostConfig.Memory}}/{{.HostConfig.MemoryReservation}}/{{.HostConfig.MemorySwap}}'` and `cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.swap.max` (must be `0`).
- **`Pss_File` is what mapped libraries actually cost in RAM.** Several GB of libs mapped (torch, torchvision, ctranslate2) measured 38 MB `Pss_File` against ~3 GB `Pss_Anon` — a `:slim` image is a **disk** win, never a RAM fix. Measure before recommending it.
- **Open WebUI runs whatever `webui_db.config` says, not the container env.** `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` / `WHISPER_MODEL` are Dockerfile build-time leftovers — `start.sh` reads only `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`. Read the real engines from the DB (query in the reference file); here embeddings and reranking are external and **local STT is the one genuinely in-process model**. Do not `cat`/`tail` `ai/.env` — grep keys only.
- **Report before you gate: diagnosis → what changed → verification → what is left open, in the message body. Never open a post-work confirmation form (`clarify`) while the report is still unwritten** — the owner reads that as «ты не дал мне плана и результата работ». Present the remediation plan as one point per item — what to do / why / whether it is actually needed (and why not) / consequences — name the ruled-out look-alike suspects (inert Dockerfile env vars, an external client polling the UI; silence on a look-alike reads as an unfinished investigation), and ask the confirmation gate *inside that same message*.
- **Do any data-touching change on a restored copy first, then live.** Keep the copy until the live result is verified, and tell the owner exactly what it is before asking to drop it (`dropdb webui_migtest`) — otherwise «что за БД ты собрался сносить?» is the answer you get.
- **`document_chunk` costs ~20 KB per chunk = a static allocator footprint, **not** a leak; never propose a restart cron for it. Split `Pss_Anon` vs `Pss_File` in `/proc/<pid>/smaps_rollup`, then histogram the anonymous regions by size: many ~64 MiB regions on a 64 MiB stride are **glibc malloc secondary arenas** (default max `8 × ncores`, driven by the process's thread count — an in-process runtime that spawns its own thread pool is the usual trigger). Fix with `MALLOC_ARENA_MAX=2` in the container env; the loader reads it at process start, so it needs a container **recreate**, not a live change. Pair it with a `mem_limit` so a spike kills that container instead of an innocent host process.
- **File-backed libraries cost almost no RAM.** With several GB of libraries mapped (torch, torchvision, ctranslate2), `Pss_File` measured 38 MB total while `Pss_Anon` was ~3 GB — so moving to a `:slim` or otherwise smaller image is a **disk** win, not a memory one. Never present an image swap as a RAM fix; measure `Pss_File` first.
- **Open WebUI's effective RAG/STT config lives in `webui_db.config`, not in the container env.** Persistent config overrides env, and the image's `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` are build-time Dockerfile leftovers that `start.sh` never reads (it reads only `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`). Read the real engines from the DB instead: `sudo -u postgres psql -d webui_db -Atc "select key||' = '||left(value::text,140) from config where key ~ 'rag|embedding|rerank|stt|whisper' and key not like '%api_key%' order by key;"`. Typically embeddings/reranking are external (`rag.embedding_engine=openai`, `rag.reranking_engine=external`) and **local STT is the one genuinely in-process model** (`audio.stt.engine=""` + `audio.stt.whisper_model`, which also downloads the faster-whisper cache).
- **`document_chunk` costs ~20 KB per chunk, almost independent of chunk text size** (measured: 9.6 KB index + 8.7 KB TOAST vector + 1.3 KB row for `vector(1536)`). So DB growth is driven by **chunk count, not source megabytes**. Normal prose (~1000-char chunks) amplifies ~20×; a CSV/JSONL that splits one chunk per line (~178 B each) amplifies ~145× — that is how a 1.8 MB CSV became 263 MB. To size an ingest, multiply expected chunk count by ~20 KB, don't look at the file size.
- Before uploading anything big, know the ceiling: at 61 GB free the disk hit the 85% alert after ~2.4M chunks (~2.2 GB of prose, or only ~430 MB of line-per-chunk tabular data). Disk alerts (`DISK_WARN=85`/`DISK_CRIT=95`, cron `*/10`) fire long before a surprise. Disk is NOT the exposure — RAM is.
- **Deleting an ingested file through the Open WebUI API is the only correct way to reclaim space.** `DELETE /api/v1/files/<id>` cascades (file row, `chat_file`/`knowledge_file` refs, `document_chunk` rows for collection `file-<id>`, and the physical upload) — deleting rows or the file by hand leaves orphans. Login needs the **admin email**, which `UI_USERNAME` in `ai/.env` is NOT (it's a short non-email handle); read it from the DB: `select email from "user" where role='admin' limit 1`. `GET /api/v1/files/` returns a paginated `{items, total}` dict, not a bare list.
- **The freed space does not come back until `VACUUM FULL`.** After deleting 10 181 chunks the table stayed at 263 MB with `n_dead_tup=10526`; `VACUUM (FULL, ANALYZE) document_chunk` (5 s, 3 519 rows) took it to 76 MB and `webui_db` 393 → 206 MB. Plain `VACUUM` only marks space reusable, not returned to the OS — use `VACUUM FULL` when you actually need the disk back.

### Chat-image bloat: base64 living in `webui_db` (the second disk eater)

Opposite of the chunk story: growth here is **bytes per row**, not row count. A chat tool that emits an image as `data:image/...;base64` in its `files` event makes Open WebUI persist that base64 **twice** — in `chat_message.files` and again in the whole-history JSON `chat.chat`. Measured: 36 images = 133 MB base64 → 266 MB of a 593 MB `webui_db`, individual messages 8–19 MB.

Sizing query (the two tables plus TOAST):

```bash
sudo -u postgres psql -d webui_db -Atc "select c.relname, pg_size_pretty(pg_total_relation_size(c.oid)), pg_relation_size(c.oid), s.n_live_tup, s.n_dead_tup from pg_class c join pg_stat_user_tables s on s.relid=c.oid where c.relkind='r' order by pg_total_relation_size(c.oid) desc limit 15;"
sudo -u postgres psql -d webui_db -Atc "select count(*) filter (where files::text like '%data:image%') base64_msgs, pg_size_pretty(sum(pg_column_size(files))::bigint) files_bytes from chat_message;"
sudo -u postgres psql -d webui_db -Atc "select pg_size_pretty(sum(case when chat::text like '%data:image%' then length(chat::text)-length(regexp_replace(chat::text,'data:image/[^\"]*','','g')) else 0 end)::bigint) from chat;"
```

- **`chat` (the JSON history) mirroring `chat_message.files` is the tell** — when both tables hold nearly the same base64 total, one payload is stored twice and only a rewrite of both helps.
- **Fix = compact base64 into file storage, not delete it.** `scripts/compact-webui-images.py` (idempotent, report-and-commit) decodes each `data:image` entry, writes the bytes to `UPLOAD_DIR`, inserts the `file` + `chat_file` rows, and rewrites the URL to `/api/v1/files/<id>/content` in **both** `chat_message.files` and (by string replace) `chat.chat`. Result on this box: `webui_db` 593 → 224 MB, `chat` 271 → 51 MB, `chat_message` 200 → 51 MB, images still render; run it as a container-internal one-liner so it uses the app's own `DATABASE_URL` and `UPLOAD_DIR`:
  ```bash
  docker exec -i open-webui python -c "import os; os.environ['UPLOAD_DIR']='/tmp/migtest_uploads'; exec(open('/tmp/compact-webui-images.py').read())"   # DSN defaults to DATABASE_URL
  ```
- **The storage side was never the problem** — `/app/backend/data` is a bind mount to `/home/ai_service/webui_data` and uploads land in `uploads/`. Do not propose "bind a volume" as the fix; the bug is that the tool never called `upload_image`, so say so.
- **Patch the tool that writes the base64, or it comes straight back.** Tool code lives in `webui_db.tool.content` (not on disk), and OWUI loads the registry at startup: write the row **and restart open-webui**, then confirm the stored code compiles (`docker exec -i open-webui python -c "exec(open('/tmp/tool.py').read())"`). Snapshot the old content to a file first — it is the only way back.
  - The durable shape: the tool takes `__request__` / `__user__` (OWUI injects them by name), calls `open_webui.models.users.Users.get_user_by_id` + `open_webui.routers.images.upload_image`, emits `{'type': 'image', **image_file}` and keeps the data URL only as a fallback. To keep "edit the last result" working, resolve `/api/v1/files/<id>/content` back to base64 from `UPLOAD_DIR` (`open_webui.config.UPLOAD_DIR`) by globbing `<id>_*`.
- Content-embedded base64 from **user uploads** (`chat_message.content` parts) stays — a few hundred KB, and OWUI needs it as a data URL when calling vision models. Only the generated-image `files` arrays are worth rewriting.
- The tool also keeps a third copy in `data/generated_images` (disk, ~83 MB here) with no retention; and `litellm_db` grows separately (`LiteLLM_SpendLogs` ~254 MB + daily aggregates ~127 MB, no auto-retention in the pinned version — only manual SQL prunes it). Name both as untackled, separate from the webui fix.

## Open WebUI DB growth: base64 chat images

- **The dominant bloat source is base64 images inside `chat_message.files`, duplicated into `chat.chat`.** OWUI stores a chat's whole history as one JSON blob in `chat.chat` *and* per-message rows in `chat_message`, so an image saved as a `data:image/...;base64,` URL costs **twice**. Measured: 36 images = 133 MB in `files` + 133 MB in `chat.chat` = 266 MB of a 593 MB `webui_db`; single messages reached 19 MB, one image 8.8 MB base64. Diagnose with `pg_column_size(files)` per message and by summing the base64 substrings: `select count(*) filter (where chat::text like '%data:image%'), pg_size_pretty(sum(case when chat::text like '%data:image%' then length(chat::text)-length(regexp_replace(chat::text,'data:image/[^"]*','','g')) else 0 end)::bigint) from chat;`
- **`n_dead_tup` near 0 means the growth is real data, not autovacuum bloat** — plain `VACUUM` will not help; only removing the payload (or `VACUUM FULL` after doing so) returns space.
- **The `:main` image persists base64 only because a workspace tool emits it.** `litellm_image_reference_generator_hy_image_3_5` (DB `tool.content`) emitted `{'type':'image','url': data_url}` in its `files` event; OWUI's own `/images/generations` path instead calls `upload_image()` and returns `/api/v1/files/<id>/content`. Same for images surfacing via `extract_base64_images` on tool results.
- **Fix the tool, not just the DB** — patched to v1.5.0: it calls `upload_image(request, raw, mime, {}, user)` via injected `__request__`/`__user__` and emits the returned file entry, falling back to the data URL if that fails. Two extra pieces are required for it to keep working: `_file_url_to_data_url()` (globs `UPLOAD_DIR` for `<id>_*`) so "improve the last image" can still use stored files as references, and MIME sniffing by magic bytes because LiteLLM labels JPEG payloads `image/png` (19 of 36 files were mislabeled → the `/content` response header lied; browsers sniff, but just be correct).
- **Migrating existing base64 → files is safe and scripted.** For every `data:` URL in a message's `files`: write bytes to `/app/backend/data/uploads/<uuid>_generated-image.<ext>`, insert a `file` row (`meta.data` = `{}`, `hash` = sha256, `path` absolute), insert a `chat_file` row so the file dies with the chat, replace the URL with `/api/v1/files/<uuid>/content`, then string-replace the same data URL inside `chat.chat` (base64 chars need no JSON escaping, so a verbatim replace is exact). Result: 593 → 224 MB. 
- **Verify compaction by fetching the new URL, not by looking at the row**: `GET /api/v1/files/<id>/content` with an admin token must answer 200 + real image bytes. A pre-existing orphan file row (path missing on disk) answers 404 `We could not find what you're looking for :/` — pick an id whose `path` exists before concluding the migration failed.
- **Nightly guards installed**: `webui-compact-images.{service,timer}` (04:00 UTC, runs `/usr/local/bin/webui-compact-images.sh` → copies `/usr/local/lib/webui-compact/compact_images.py` into the container, and only when it moved something does it `VACUUM FULL` `chat`/`chat_message`; silent no-op otherwise, log `/var/log/webui-compact-images.log`) and `litellm-spend-retention.{service,timer}` (04:30 UTC, deletes `LiteLLM_SpendLogs` older than 30 days, **never touches `LiteLLM_Daily*Spend` aggregates**, plain `VACUUM` every run + `VACUUM FULL` only when dead tuples exceed 30 % of live rows; log `/var/log/litellm-spend-retention.log`). Test a timer by `systemctl start <service>` and reading the log, not by waiting for the calendar.
- **Remaining known growth**: `document_chunk` (~20 KB per chunk, RAG), `generated_images/` inside the container data dir (a third on-disk copy the tool writes on purpose, ~2.6 MB/image), and `LiteLLM_SpendLogs` (~13 MB/day from `messages`/`response` JSONB, now capped by retention).
- **`generated_images/` retention**: `webui-generated-images-retention.{service,timer}` (04:15 UTC) deletes image files in `/home/ai_service/webui_data/generated_images` older than 14 days by mtime, only at `-maxdepth 1` and only for image extensions. It cannot break chats: history renders from `/api/v1/files/<uuid>/content`, and reference resolution prefers those URLs — the disk copy is only the tool's recent-fallback. Safe to purge. Tested via `WEBUI_GENERATED_IMAGES_DIR=<scratch dir> <script> [--dry-run]` (dry-run prints the count/size, real run deletes and logs to `/var/log/webui-generated-images-retention.log` only when it removed something).


## open-terminal memory behaviour

> **open-terminal memory:** single Python process whose anonymous heap ratchets to a high-water mark and is never returned to the OS (CPython + glibc arenas; per-session output is capped at 64 KB, so it is not live sessions). Measured 2026-10: a 191 MB `/files/read` took RSS 85 MB → 592 MB and it stayed there; a second identical read and a 50 MB read reused those blocks without growth — the floor equals the biggest single request ever served, not a cumulative leak. At `mem_limit: 1g` that turned into a memcg OOM-kill 7 min after start; now `mem_limit/memswap_limit: 2g` plus `MALLOC_TRIM_THRESHOLD_=131072`, `MALLOC_MMAP_THRESHOLD_=131072`, `MALLOC_ARENA_MAX=2`, `PYTHONMALLOC=malloc` (verified effective in fresh container processes: 400 MB bytearray alloc/free returns RSS to 9 MB — but it does not shrink the server's already-established floor). That is why `open-terminal-restart.timer` exists: nightly `docker restart open-terminal` at 04:40 UTC (07:40 MSK) via `/usr/local/bin/open-terminal-restart.sh` — the script touches `/var/lib/docker-autorecover/pause` so the incident detector stays quiet, waits for `healthy` (max 120 s) and logs rss_before/rss_after to `/var/log/open-terminal-restart.log` (measured 592 MB → 85 MB). It drops open terminal sessions by design; a manual `docker restart` does not increment `RestartCount`. Its port 8000 is NOT published: test the API with `docker exec open-terminal curl -H "Authorization: Bearer $OPEN_TERMINAL_API_KEY" http://127.0.0.1:8000/...` (host `127.0.0.1:8000` belongs to `lyria-bot`).
