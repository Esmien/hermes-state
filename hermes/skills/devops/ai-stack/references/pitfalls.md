# Pitfalls (AI stack)

> Loaded from the `ai-stack` skill. Read this when something behaves in a way the docs do not explain.

## Pitfalls

- **Open WebUI RAM is dominated by glibc malloc arenas, not by models.** Measured 2026-10: `Pss_Anon` 2.97 GB vs `Pss_File` 38 MB — i.e. the bundled torch/torchvision/ctranslate2 files cost ~nothing resident, so **switching to the `:slim` image frees disk (~800 MB of 6.37 GB), not RAM**. The real footprint was **24 anonymous rw regions of exactly 64 MiB at 64 MiB stride** = glibc secondary arenas (`HEAP_MAX_SIZE` = 64 MiB; glibc 2.39 allows up to `8 × nproc` = 32 arenas) accumulated by the 38 threads of the uvicorn process. Fix = `MALLOC_ARENA_MAX: "2"` in the service `environment:` (needs container recreate; the value is read by the loader at process start). Result: RSS 3012 → 866 MB, arenas 24 → 1, host `used` 5.5 → 3.3 GiB, process `VmSwap` 148 MB → 0. Diagnose the pattern with: `awk '/^[0-9a-f]+-[0-9a-f]+ /{split($1,a,"-"); sz=(strtonum("0x"a[2])-strtonum("0x"a[1]))/1048576; hdr=$0} /^Rss:/{if(hdr ~ /rw-p 00000000 00:00 0/ && sz>=63 && sz<=65) c++} END{print c}' /proc/<pid>/smaps`. Two traps: (1) `USE_EMBEDDING_MODEL_DOCKER` / `USE_RERANKING_MODEL_DOCKER` / `RAG_EMBEDDING_MODEL` in the image env are Dockerfile build-time leftovers — `start.sh` only reads `USE_SLIM_DOCKER`, `USE_OLLAMA_DOCKER`, `USE_CUDA_DOCKER`, `WEB_LOADER_ENGINE`, so the real engines come from the **persistent config in `webui_db.config`** (here external: `rag.embedding_engine=openai`, `rag.reranking_engine=external`); changing the env vars changes nothing. (2) **STT is genuinely local** (`audio.stt.engine=""` + `audio.stt.whisper_model=small`, cache `data/cache/whisper/models` 462 MB, plus `rag.content_extraction.supported_media_mime_types=["audio/*"]` which transcribes audio at ingest) — do NOT claim local speech models are unused just because embeddings are external. Expect RSS/threads to rise on the first audio transcription (torch/ctranslate2 import lazily) — but with `MALLOC_ARENA_MAX` set the growth is bounded.
- **`ai/backup-databases.sh` must be called by ABSOLUTE path.** It does `cd "$(dirname "$0")"` and then reads `ENV_FILE="$(dirname "$0")/.env"`; invoked as the relative `ai/backup-databases.sh` the second `dirname` yields the relative `ai` and, after the cd, resolves to `ai/.env` → dies with `Нет ai/.env` (exit 1) and no dump is written. Use `sudo -u ai_service /home/ai_service/ai-stack/ai/backup-databases.sh`.
- `/home/ai_service/ai-stack/ai/backup-databases.sh` must stay **755 root:root** — `postgres-backup.service` runs `User=ai_service`, and a restrictive mode (e.g. 711) makes the nightly run die with `Permission denied`, `status=126` while the timers still look healthy. After any permission/ownership change on that script, verify with `systemctl start postgres-backup.service` and check `Result=success`.
- **Two independent gotchas bite the restore check, and both are silent.** (1) `sudo` resets the environment (`env_reset`), so `subprocess.run([..., "sudo", "-u", "postgres", "pg_restore", ...], env={"PGOPTIONS": ...})` has NO effect — put `env` *inside* the sudo command: `sudo -u postgres env PGOPTIONS='-c maintenance_work_mem=512MB' pg_restore ...`. (2) The default `maintenance_work_mem` is 64 MB and pgvector index builds need more, so `webui_db` restore dies with `memory required is 65 MB, maintenance_work_mem is 64 MB` — hence `VERIFY_MAINTENANCE_WORK_MEM = "512MB"` applied through `PGOPTIONS` on both restore branches (split and whole-file). After any change to `_restore_into_temp_db`, run the real thing — a green unit test suite mocks the commands and will not catch either failure.
- The restore check only runs under a user that can `sudo -u postgres`. `server-monitor-bot.service` runs as **root**, so `/backups` works; the same code invoked as `ai_service` fails with `sudo: a password is required` (that sudoers NOPASSWD list is read-only commands only). Run `verify_backups`/`_restore_into_temp_db` as root during testing, or the result is a false failure that has nothing to do with the code.
- Verify dumps by restoring into a throwaway DB (`createdb verify_restore_webui` → `pg_restore -d ...` → `dropdb`). NEVER restore a dump over a live database. `/backups` does this automatically; `pg_restore` needs to read the dump, so pipe split parts via stdin (root-owned temp files under `/root/...` are unreadable by the `postgres` user — `Permission denied`).
- `monitor.py backup` splits dumps > 45 MiB adaptively and deletes the parts after upload; the join message carries the part names/sizes, the `cat` command and the expected SHA-256 of the whole dump, and aborts that message to a warning if any part failed to upload.
- `send_document` compares Telegram's reported `file_size` with the local size — a mismatch raises, so a truncated upload cannot pass as success.
- Tests in `/home/ai_service/notifications/test_monitor.py` MUST stay off the network: the module patches `send_telegram`, `send_document` and `send_long_message` at import. Mocking only `send_long_message` is not enough — `notify_backup` sends the digest via `send_telegram` and attachments via `send_document`, so fixtures leak to the real bots when the suite runs. Sanity check: run the suite with `urlopen` patched to raise; it must still pass.

- **`Error upserting deployment <name>: LLM Provider NOT provided` in the LiteLLM boot log is a pre-existing broken DB deployment, not a regression from the upgrade you just applied.** Deployments created through the UI/API live in `litellm_db."LiteLLM_ProxyModelTable"` (params are encrypted there, so you cannot read the model string back) and are re-validated at boot; a row whose params lack a provider prefix warns on every start. Before blaming the new version, check the row's `created_at` (`select model_name, created_at from "LiteLLM_ProxyModelTable" where model_name like '%<name>%'` — column is `created_at`, not `"updatedAt"`) and whether the group ever served traffic (`select model_group, count(*) from "LiteLLM_SpendLogs" where model_group like '%<name>%' group by 1`). Predates your change + zero spend = dormant entry, report it as a side note, do not "fix" it inside an upgrade task. **It does not stay in the boot log.** With `STORE_MODEL_IN_DB=True` the DB→router sync re-runs on a timer, so the same warning repeats **every 30 s** — count it with `docker logs litellm --since 24h | grep -c 'Error upserting'` (~2.9k/day here). Each cycle re-registers the router's deployments and raises a fresh traceback, which makes this a standing memory-churn source too, not just log noise. Remove such a row with the admin API, not SQL, so the in-memory router drops it immediately: `POST 127.0.0.1:4000/model/delete -d '{"id":"<model_id>"}'` (dump the row to `backups/litellm_orphan_row_<ts>.json` first; verified 2026-10-19: the `aider.opencode/grok-4.7` orphan disappeared and `grep -c 'Error upserting'` went to 0 within 30 s).
- **NEVER dedupe `LiteLLM_ProxyModelTable` by `model_name`.** ~120 rows for ~42 names is BY DESIGN: one `model_name` = a model group, and each row is a separate deployment with its own key/`litellm_credential_name`. The owner calls these «группы, с разными ключами» and forbids touching them; only a row that is a genuine orphan (created once, never updated, absent from `/v1/models` while its name-mates are served) is removable, and only with explicit approval for that single `model_id`.
- **`docker exec` with a heredoc needs `-i`.** `docker exec open-webui python - <<'PY' …` exits `0` with **empty output** because stdin is not attached — an empty result is a missing stdin, never a silent success; use `docker exec -i`.
- **`psql -c "stmt; stmt"` runs as ONE transaction**, so a `VACUUM (FULL, …)` bundled with other statements dies with `VACUUM cannot run inside a transaction block` — pass exactly one statement per `-c`.
- **A copy restored with `pg_restore --no-owner --no-privileges` is owned by `postgres`**, so the app role hits `permission denied for table chat_message`; on the copy run `grant all on schema public to webui; grant all on all tables in schema public to webui;` before exercising any script against it.
- **`POST /api/chat/completions` is not an end-to-end probe for an Open WebUI tool.** Non-stream answers `finish_reason: tool_calls` and expects the client to execute the tool, so the stored assistant row comes back empty with `files=null` — nothing was persisted and no tool ran. Exercise the tool in-process instead: `docker exec -i open-webui python` → `exec(open('/tmp/tool.py').read())`, instantiate `Tools`, and call the async helper with a dummy request object whose `.app.url_path_for(name, **kw)` returns the content path. That proves upload + `file` row + reverse URL→base64 resolution in seconds, with a 1×1 PNG and a cleanup of the row and the file.
- **`404 {"detail":"We could not find what you're looking for :/"}` on `/api/v1/files/<id>/content` means the row is missing or the bytes are not at `path` — not an access failure.** Long-lived DBs carry rows whose `path` died with a container layer, and they answer exactly like a bogus id; `ls` the path before suspecting permissions or ownership.
- **Sniff image MIME from magic bytes; do not trust the media type LiteLLM declares** — `image/png` came back for JPEG payloads in 19 of 36 files. Browsers render it anyway, but store the sniffed type, and prefer `upload_image(request, raw, sniffed_or_declared, {}, user)` over hand-building the `file` row.
- **Never `cat` an env file just to get a DSN** — build derived values in-process: `os.environ['DATABASE_URL'].rsplit('/', 1)[0] + '/<db>'`. Same for `UI_PASSWORD`=LiteLLM / `OWUI_ADMIN_PASSWORD`=WebUI; see `references/owui-admin-auth.md`.
- Do NOT `cat`/`tail` `ai/.env` — grep keys only.
- `deploy.sh` restores DBs by default; use `--skip-restore` when you must not touch data.
- Postgres is host-level (systemd), not a compose service — restart via `systemctl`, not `docker`.
- **Measure before reporting a performance anomaly.** A backup+notify pair that finishes implausibly fast is not evidence of a short-circuit — check the uplink first (`dd if=/dev/zero bs=1M count=100 | curl -s -o /dev/null -w '%{time_total}' -X POST --data-binary @- https://speed.cloudflare.com/__up`). This host pushes ~80 MiB/s, so a 140 MiB dump in ~4 s is normal and a 73 MiB dump in 9 s was the slow case, not the fast one. Announcing "suspiciously fast, probably broken" without measuring produces a false alarm you then have to retract.
- **A dump that jumps in size is usually real data, not bloat.** `webui_db` dumps can double overnight because `document_chunk` (pgvector embeddings) grows with every ingested file — one file contributed 10 181 chunks at a time. Confirm with `pg_total_relation_size` per table plus `n_dead_tup` (all near 0 ⇒ autovacuum is fine and the growth is genuine); only large `n_dead_tup` indicates bloat needing `VACUUM`. Report the cause rather than the symptom.
- `systemctl start` on a unit whose file changed on disk prints «unit file … changed on disk. Run 'systemctl daemon-reload'». Harmless for a oneshot that then runs correctly, but mention it — the unit on disk and the one systemd has cached are out of sync.

- **An automated incident→triage→fix pipeline on this stack needs a noise filter and dedup BEFORE it dispatches anything.** Every container here carries a restart policy (`always` / `unless-stopped`, see `docker inspect <c> --format '{{.HostConfig.RestartPolicy.Name}}'`), so a failing container self-heals in seconds and produces an event *storm*, not a single "down" event — and the lyria workers' boot `AMQPConnectionError` traceback is expected. Dedup by hash of the traceback with a TTL, and keep known-benign signatures on a whitelist, or the fixer gets woken for a non-event. Redact secrets too: litellm / open-webui / postgres tracebacks commonly carry `LITELLM_MASTER_KEY` and DB passwords, and the traceback travels into a delegated agent's context as well as into Telegram.
- **Never let a delegated fixer touch the stack directly** — `deploy.sh` restores databases by default. It works in a git worktree and emits a diff; the deploy stays with the owner.
