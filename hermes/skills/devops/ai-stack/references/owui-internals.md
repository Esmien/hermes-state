# Open WebUI internals: где живёт состояние и как его читать/править

Глубина к `ai-stack` SKILL.md: карта хранения состояния OWUI (`webui_db` + контейнер) и грабли, которые стоят лишних десяти инструментов. Схема песочниц — `sandbox-terminal.md`, обновление образа — `updates.md`.

## Карта состояния

| Что | Где |
|---|---|
| настройки инстанса (в т.ч. `terminal_server.connections`, `tool_server.connections`, `ui.*`, `task.*`) | таблица `config`, ключ → JSON в `value` |
| workspace-инструменты (Python-тулзы, «Image Ref Generator» и пр.) | таблица `tool`: `content` (исходник) + отдельная колонка `valves` (значения полей формы) |
| pipe-функции (модели-пайпы, напр. `enricher`) | таблица `function`: `content` (код) + `valves` (JSON с моделью/URL/ключами); в таблице `model` такая модель есть, но с **пустым `base_model_id`** и без `params->>'system'` |
| чаты | таблица `chat`, поле `chat` — JSON (id, title, models, messages, history, files, tags) |
| файлы/вложения | таблица `file` + диск `/app/backend/data/uploads` (в контейнере) |
| состояние сессии/выбора в UI | **не в БД** — `localStorage` браузера |

Читать БД: `sudo -u postgres psql -d webui_db -tAc "…"`.

## Никогда не выбирать значение целиком

`select value from config where key='ui.default_interface_settings'` вернул 227 КБ: внутрь JSON вшит `backgroundImageUrl` как base64-JPEG. То же у `settings` пользователя и у `tool.valves`.

Правило: сначала структура, потом точечное значение.

```sql
select jsonb_object_keys(value::jsonb) from config where key='ui.default_interface_settings';
select jsonb_object_keys(valves::json) from tool where id='<tool_id>';
select length(content), content like '%<маркер версии>%' from tool where id='<tool_id>';
```

Секреты (ключи в `valves`, токены в конфигах) в чат не выводить — только имена ключей и наличие.

## Персональный системный промпт и миграция

При инвентаризации промптов проверяй `user.settings::jsonb -> 'ui' ->> 'system'`, выводя только агрегаты по роли и длину, не тексты. Например: `select role, count(*), min(length(settings::jsonb->'ui'->>'system')), max(length(settings::jsonb->'ui'->>'system')) from "user" where coalesce(settings::jsonb->'ui'->>'system','') <> '' group by role;`. JSON null не является объектом: перед `jsonb_object_keys` проверяй `jsonb_typeof(...)='object'`.

При переносе в файлы сопоставляй `user.id` с `state.json` и проверяй принадлежность каталога, а не email; admin и pending могут не иметь песочницы. Сначала проверь полный перенос каждого промпта без обрезания и перезаписи существующего профиля, затем согласованно отключай пользовательские промпты и только после проверки очищай исходные значения. Не затрагивай админские промпты моделей в `model.params` и проверяй итоговый порядок системных инструкций на реальном запросе. `chat.system_prompt` — разрешение интерфейса/сохранения настроек; не считай его доказанной блокировкой system-сообщений через API. Источник: https://docs.openwebui.com/features/authentication-access/rbac/permissions

## AGENTS.md: управляемый блок и дословный вывод памяти

- Шаблон AGENTS.md держать управляемым блоком `<!-- managed:begin -->`…`<!-- managed:end -->`: provisioner при каждом прогоне заменяет только блок, а текст, дописанный пользователем снаружи, сохраняет. Файл без маркеров, но с канонической первой строкой прежнего шаблона заменять целиком — иначе старое правило остаётся висеть рядом с новым. Идемпотентность проверять на синтетике: `merge(merge(x)) == merge(x)`, текст после END и произвольный текст без маркеров не теряются.
- **Первый прогон новой схемы дублирует блок, если старый текст остался вне маркеров.** Замена «между маркерами» на файле вида «legacy-текст + только что добавленный блок» ничего не удаляет: старое правило висит над новым, и после рассылки это видно почти у всех аккаунтов. Merge обязан вычищать строки, совпадающие с любой известной версией шаблона, где бы они ни лежали — сравнение по множеству нормализованных строк, а не по первой строке/префиксу, — и сохранять только пользовательские строки. Пользовательский текст может сам совпасть со строкой шаблона: удалять такую строку внутри управляемого блока и не удалять за его пределами.
- Рассылку делать прогоном самого provisioner (таймер 60 с), а не ручным обходом каталогов: он пишет через temp + `os.replace` и сохраняет 0644 root:root.
- **`--dry-run` не показывает обновления AGENTS.md**: `ensure_memory_files` вызывается только при `not dry_run`, поэтому «изменений: 0» и неизменённые sha не означают, что правка не разъехалась — таймер мог применить её раньше. Проверять по файлам (наличие маркера и новой строки), а не по счётчику изменений.
- Перед рассылкой сохранять только `.agents`: `cd /home/ai_service/sandbox/users && tar -czf <backup>/agents-only.tar.gz */.agents`. `cp -a` всего каталога пользователей копирует рабочие каталоги и занимает гигабайты впустую.
- После рассылки сверять: у всех есть маркер и новая строка, а MEMORY.md и PROFILE.md побайтно не изменились, права и владелец прежние.
- В блок входит правило: показывать записи памяти дословно, байт в байт, по одной в строке и с нумерацией `1. <запись>`; не пересказывать, не сокращать, не объединять, не переставлять, не дополнять; уже выведенный Filter список не дублировать. Проверка — засеять три записи с кавычками-ёлочками, двойными пробелами и длинным тире, попросить показать, распарсить строки `^\d+\.\s` и сравнить с файлом точно. Совпадение доказывает следование инструкции, но гарантии не даёт: детерминированный список даёт только Filter.
- `memory_tool._records(text, name)` принимает ключ (`'MEMORY'`), а не имя файла (`'MEMORY.md'`); имя файла даёт ложное «Неизвестный формат файла памяти» и уводит отладку в сторону.
- Проба с кодом на уровне модуля (логин, запуск e2e) исполняется при `import`: держать helpers в отдельном модуле или под `if __name__ == '__main__'`, иначе импорт запускает чужой сценарий и портит состояние.

## Pipe-функция = модель без базовой модели

Модель с пустым `base_model_id` и пустым `params->>'system'` — это не «сломанный пресет», а pipe: поведение (и промпт) лежит в `function.content`, параметры — в `function.valves`. Смотреть так:

```sql
select id, type, is_active, length(content) from function order by length(content) desc;
select coalesce(valves::text,'<null>') from function where id='<pipe_id>';
```

`valves` содержат ключи провайдеров — печатать только имена полей и значения, не являющиеся секретами (модель, URL, лимиты, таймаут).

**Правка valves — только через API, не SQL-ом:** `GET /api/v1/functions/id/<id>/valves` читает, `POST /api/v1/functions/id/<id>/valves/update` пишет (POST на `/valves` без `/update` отвечает `405`). API перезагружает значения в памяти процесса; правка строки в БД без рестарта контейнера не подхватится. Тело шлём целиком тем же объектом, что вернул GET (иначе теряются остальные поля).

**Аутентификация для этих ручек:** bearer = API-ключ админа из таблицы `api_key` (`select key from api_key where user_id='<admin uuid>';`) — он там в открытом виде. Не считай произвольно подписанный JWT рабочей сессией: проверяй конкретный токен на `/api/v1/auths/` и сравнивай возвращённый user id, не выводя токен. Для пользовательского UI подходит принятый сервером JWT тестового аккаунта; это не проверка входа по паролю.

### Ключ OWUI — прод-секрет, а не тестовый креденшл

`api_key` — одна строка на юзера, и её читают сразу несколько внешних клиентов: кастом-провайдер Hermes (`HERMES_CUSTOM_127_0_0_1_8080_API_KEY` в `/root/.hermes/.env`) и обогатитель музыкального бота (`ENRICH_TOKEN` в `/root/deploy/music_bot/.env`, три контейнера). Поэтому:

- **`POST /api/v1/auths/api_key` — это РОТАЦИЯ**, а не чтение: старый ключ аннулируется мгновенно, Hermes и бот начинают получать `401`, в чате это выглядит как «ты сломал мне ключи». Для чтения — `select key from api_key where user_id=…` в БД; `GET /api/v1/auths/api_key` отдаёт замаскированное значение.
- Если ротация уже произошла: записать новый ключ `sed`-ом в оба файла (не печатая его), пересоздать `bot`/`enricher-worker`/`generation-worker` (env читается только при старте) и перезапустить Hermes — он держит старую копию в памяти процесса.
- Проверка живости — не `/api/v1/models` (он отдаёт `200` и при урезанном доступе), а реальный вызов: `POST https://ai.esmien.ru/api/v1/chat/completions` с `model: enricher` и этим токеном.

**Внутренние ручки ≠ OpenAI-совместимые.** `/api/chat/completions` и прочие `api.chat.*`-эндпоинты требуют живой человеческой сессии и на automation-токен отвечают `403`; для скриптов и проб использовать OpenAI-совместимый `/api/v1/chat/completions` (и `/api/v1/models`), который принимает тот же bearer.

### Кастомная модель = соединение + id в LiteLLM

Строка `model` в OWUI хранит `base_model_id` как `<prefix_id>.<model_name>` — префикс берётся из соединения (`openai.api_base_urls`/`api_keys`, поле `prefix_id`), а хвост обязан совпадать с `model_name` в LiteLLM. Префикс срезается перед вызовом, поэтому одна и та же группа живёт под несколькими id: `openai/…`, `other/…`, `chat./…`, `aider./…`. Отсюда две частые ошибки: правка маршрута «не подействовала», потому что модель смотрит в другую группу; и модель не видна, потому что группы нет в списке `models` у LiteLLM-ключа (у нас — ключ с алиасом `Other`). `capabilities.file_context=false` дополнительно вырезает вложения-документы до RAG, а `vision` не влияет на то, видит ли нога картинки — это свойство ноги, не модели.

**Восстановление удалённой строки `model`:** бэкап — `select to_jsonb(m) from model m where id='<id>'`. При вставке обратно `params` и `meta` приезжают **строками**, и если закастить их в `jsonb` как есть, внутрь ляжет JSON-строка: `params->>'system'` вернёт пусто, а модель будет выглядеть «без промпта». Перед вставкой `json.loads` → `json.dumps` → `::jsonb`.

**psql на хосте:** `su - postgres -c "psql -d webui_db -Atc \"select (params::jsonb)->>'system' …\""` ломается на вложенных кавычках и скобках. Писать SQL в `/tmp/q.sql` и звать `psql -f /tmp/q.sql` — тот же приём уже используется для длинных UPDATE.

## Минифицированный фронт не grep'ать широко

`grep -r` по `/app/build` даёт сотни килобайт кода в одном ответе и режет контекст. Инвентарь строк — только `-o` с узким шаблоном, остальное искать в бэкенде:

```bash
docker exec open-webui sh -c "grep -rhoE '\"[a-zA-Z_]*Term[a-zA-Z_]*\"' /app/build | sort | uniq -c | sort -rn | head -25"
docker exec open-webui sh -c "grep -rho '.\{160\}selectedTerminalId.\{200\}' /app/build | head -5"
```

Для API-поверхности терминал-сервера источник истины — `GET /openapi.json` из самого контейнера, а не бандл: там видно, что отдачи байтов файла нет (`/files/read` → JSON, `/files/display` → `{path, exists}`).

## Правка workspace-инструмента

Тул живёт в БД, а не в образе: при пересборке/откате образа он сохраняется, при восстановлении из чистой базы — нет. Для ограниченного пилота сначала сохрани текущие Tool и Filter отдельно с правами 0600; обновляй через `/api/v1/tools/id/<id>/update` и `/api/v1/functions/id/<id>/update`, явно передавая `id`, `name`, `content`, `meta` и для Tool исходный `access_grants`. После каждого обновления перечитай точный объект и сверь код, права, активность и неглобальность; при ошибке восстановления не скрывай, какой компонент не откатился. Не публикуй содержимое секретных valves. Синхронизируй утверждённый исходник с recovery-репозиторием. Для других способов правки порядок:

1. Скопировать текущий `content` в файл-бэкап (`/root/owui-tool-<name>-<версия>.py`).
2. Правку держать в файле репо (`ai-stack/ai/webui-tools/<name>.py`) — это единственная копия для восстановления; править и БД, и файл.
3. Заливать в БД одним `psql -f` с уникальным dollar-tag (`$pyfile_9f3c$…$pyfile_9f3c$`) — контент содержит `$`, кавычки и regex, обычный `-c` с quoting ломается.
4. Проверить: `length(content)` вырос ровно на патч, `content like '%<новая строка>%'` = t, `valves` не тронуты (их не перезаписывать — там ключи).
5. Синтаксис проверять на хосте `python3 -m py_compile` до заливки; в контейнере — `docker cp` + `python3 -c 'import importlib.util…'`, чтобы прогнать чистые функции (например резолв каталога) без вызова модели.

Сборка и тесты собранных Filter/Tool требуют pydantic (зависимости OWUI): системный `python3` падает с `ModuleNotFoundError`. Запускать тем venv Hermes, где он есть (`/root/.hermes/installs/*/environments/*/venv/bin/python` — найти через `search_files` по `site-packages/pydantic`), а не ставить пакеты в системный Python.

Тул исполняется **в контейнере open-webui под root** (`.Config.User = 0:0`). Всё, что он пишет в пользовательские каталоги, требует (а) bind-mount этого каталога в compose open-webui и (б) `os.chown(path, 1000, 1000)` после записи — иначе пользователь песочницы не сможет файл ни открыть, ни удалить. Для генераторов файлов прежний fallback пользователей без песочницы (админ, аноним) — `/app/backend/data`. Для персональной файловой памяти такой fallback запрещён: при неподтверждённой привязке отвечать без памяти с заметным предупреждением, не подставляя общий или чужой каталог.

## Лимиты памяти и переименование компонентов

Константы живут в трёх местах и обязаны совпадать: `MEMORY_LIMIT` в Filter (общий размер MEMORY.md),
`LIMIT`/`RECORD_LIMIT` в Tool, строка «до N символов в MEMORY» в шаблоне provisioner (её видят модели).

Порядок правки: исходники в `tasks/file-memory-step3` → `build_plugins.py` → деплой Filter, затем Tool →
сверить живой контент через `GET /api/v1/functions/id/<id>` и `/api/v1/tools/id/<id>` → прогнать обычный ход
чата. Filter исполняется в общем пайплайне: ошибка в нём ломает ВСЕ чаты, а не один, поэтому проверка
ходом чата обязательна, а не опциональна. Фикстуры тестов строить от констант (`m.LIMIT`, `m.RECORD_LIMIT`),
не от литералов — иначе тест переполнения тихо перестаёт проверять границу и падает там, где «ничего не меняли».

Переименование id (rename в OWUI нет, только create+delete; чаты с ручным включением старого Tool отваливаются молча):

1. Бэкап: `GET /functions/id/<old>` + `/valves`, `GET /tools/id/<old>` + `/valves`, в файл 0600.
2. Создать Tool с новым id (`/tools/create`), перенести valves (`/valves/update`) и гранты
   (`/access/update`, поле `access_grants`; публичный доступ = `principal_id: "*"`, `permission: read`).
3. Создать Filter с новым id, valves перенести, поправив `tool_id` на новый Tool.
4. Прочитать созданное и **только при необходимости** звать `toggle`/`toggle/global`: это ПЕРЕКЛЮЧАТЕЛИ,
   а не установка значения — вызов на уже включённом выключит его.
5. Сквозная проверка: запрос без инструментов возвращает факт из памяти (инъекция жива), запрос про список
   даёт вызов `memory(...)` (Tool резолвится по новому id).
6. После проверки — выключить и удалить старые (`DELETE /functions/id/<id>/delete`, `/tools/id/<id>/delete`).

Пилотные аккаунты (`file-memory-pilot-*`) provisioner не обслуживает: правку шаблона им применять отдельно
(toчечной правкой файла), иначе они тихо остаются на старой формулировке.

## Filter: проверка области действия и сообщений

Проверяй глобальный Filter отдельно на обычном пользовательском ходе и фоновых задачах: служебные вызовы не должны без необходимости подмешивать память или запускать decision-модель. Сначала изучи реальные серверные метаданные установленной версии; не предполагай, что отсутствие или наличие `chat_id` само по себе надёжно определяет тип вызова.

Встраивай память как отдельно помеченный заменяемый блок и сохраняй остальное содержимое системного сообщения: WebUI может объединять сообщения. Включай собственный разделительный пробел или переводы строк в заменяемую область — иначе они накапливаются при повторном `inlet` и меняют префикс. Проверяй повторный прогон на точное равенство сформированного блока и на синтетическом реальном запросе — отсутствие дублей, сохранение админского промпта и границы блока. Детерминированное содержимое запроса не гарантирует, что модель использует факт, и не доказывает cache hit — последнее измеряется отдельно.

Для `inlet`/`outlet` проверь конкретный обработчик установленной версии и реальное отображение как streaming-, так и non-streaming-ответа: момент фильтрации, тело HTTP и уже отданные клиенту чанки — разные вещи. Проверь обрыв подключённого Socket.IO до ответа, затем новый подключённый чат с тем же пользователем: сравни события и сохранённую историю и убедись, что ожидающее напоминание не исчезло. Сохранённый outlet и отправленное событие не доказывают, что человек увидел или прочитал сообщение. Для сквозного теста вызова Tool используй streaming-запрос `/api/chat/completions` с сохранённым `chat_id`, `message_id`, клиентской сессией и `tool_ids`; дождись окончания задачи и проверь `message.output[]` и фактические файлы: non-stream ответ с `tool_calls` сам по себе не подтверждает исполнение. Для проверки доставки outlet подключи Socket.IO с аутентификацией тестового пользователя, сопоставь `chat:outlet` и `message_id`, затем сверь сохранённый ответ и обработчик фронтенда; событие и код обработчика — не визуальная проверка браузера. Не обещай гарантированное предупреждение в начале сообщения только на основании инструкции модели или вызова `outlet`. Когда версия сохраняет изменения outlet, меняй и `message.content`, и текстовые части `message.output` (`type: message` → `content[]` → `type: output_text`): UI может показывать именно `output`. Проверяй синхронизацию в UI, сохранение после обновления и прямой streaming API отдельно; outlet после генерации не меняет уже отправленные чанки. Для детерминированного предупреждения проверь штатный `stream` hook на реальных событиях до их отправки: в пилотном маршруте он заменил текстовые чанки и подавил противоречивый текст, а `outlet` сохранил предупреждение. Это доказано только для проверенного маршрута, не для всех форматов событий или обрывов; сверяй содержимое Socket.IO по собранным чанкам и сохранённому ответу, не выдавая обработчик за визуальную проверку. Если ради безопасности скрываются обычные ответы пользователя или меняется автоматическое удаление, отдельно согласуй этот компромисс до боевого включения.

До установки исполняй синтетический исходник в установленном контейнере Open WebUI и проверяй `open_webui.utils.tools.get_tool_specs(Tools())`: убедись, что схема генерируется и серверный `__user__` не стал аргументом модели. Если Filter и Tool собираются в самостоятельные файлы с копией общих helpers, тестируй именно собранный Filter: создай синтетические файлы и вызови его `inlet` и `outlet`, включая пути ошибки и переполнения. `py_compile` и тесты исходных модулей не обнаруживают helper, забытый во встраиваемом namespace. Для Filter проверь через `open_webui.utils.filter.get_filter_params(inspect.signature(filter.inlet), ..., extra_params)` передачу `__user__` и `__metadata__`; такой unit-прогон проверяет интерфейс, но не заменяет реальный запрос, фоновые задачи и клиентскую приёмку. Временные данные не должны содержать пользовательскую память или ключи. При проверке записи и отдельного состояния имитируй ошибку после записи файла: результат операции не должен ложно утверждать, что данные не сохранены, а следующий запрос должен восстанавливать необходимость напоминания по фактическому содержимому. Очищай синтетические данные через `finally` и сверяй восстановление с исходными байтами и состоянием.

Проверяй связку Filter → Tool отдельно от модельного tool-loop: в установленной версии Filter получает `__request__` и `__user__`, а внутренний `open_webui.utils.tools.get_tools` способен загрузить разрешённый Tool и вызвать его на синтетическом пользователе. Подтверждай вызов по серверному событию и результату, а не по словам модели; после временной диагностической вставки восстанавливай Filter и сверяй содержимое. Это внутренний API, не стабильный публичный контракт: проверяй после обновлений и не внедряй инициирование изменения или удаления без отдельного согласования архитектуры. Для разрушительного автоматического действия перечитай и сверь точные выбранные записи через Tool; если результат не подтверждён, останови процесс без автоповтора — исключение могло произойти уже после записи. Тестируй отказ пользователя, недостаточное число записей и сбой после возможной записи отдельно; декларируемый model prompt не заменяет эти проверки.

## Визуальная приёмка чата в Chromium

1. Выдели тестового пользователя и сохрани его исходные файлы и состояние с закрытыми правами; восстанови их в `finally` и проверь побайтно. Не тестируй записью в память настоящего пользователя.
2. Если владелец разрешил JWT-инъекцию, проверь имеющийся токен запросом `/api/v1/auths/` и совпадением id, не выводя секрет. Открой origin в изолированном профиле Chromium и установи `localStorage.token` через CDP, затем загрузи страницу. Не выдавай это за проверку формы входа по паролю.
3. Запусти Chromium с `--headless=new --no-sandbox --remote-debugging-address=127.0.0.1 --remote-debugging-port=<свободный порт> --user-data-dir=<scratch>`; проверь `/json/version`, управляй целевой вкладкой по CDP и снимай экран через `Page.captureScreenshot`, затем проверяй изображение через vision. Не выводи JWT в аргументах команд, логах или ответе. Заверши только собственный процесс браузера.
4. Перед каждым отправлением выбери пилотный пресет в UI и сверь его `base_model_id` с дешёвой разрешённой моделью: дефолт интерфейса может быть дорогим и не соответствовать пилоту. Выбирай пункт по точному id, а не по подписи: одно отображаемое имя («GPT-6.1 Terra») носят несколько записей, и клик по первому совпадению уводит на другую ногу. В выпадающем списке пункт — листовой `div` с текстом без вложенных элементов, поэтому матчь точное равенство текста ожидаемому, а после выбора перечитай выбранную модель в DOM и только потом отправляй. Отправляй через реальный UI, проверяй снимки первого ответа, последующего напоминания, перезагрузки и подтверждения, а также фактические файлы и state. Визуально отделяй ошибки интерфейса от поведения модели и от сохранённой истории.
5. Проверяй Markdown после списков: отделяй рекомендацию и вопрос подтверждения пустой строкой, иначе renderer включает их в последний `li`, хотя сырой текст выглядит корректным.

## Гигиена пользовательской памяти: дубли и смешение файлов

Признак, что файлы пора разобрать: записей много, но почти все — личное (семья, животные, биография, история отношений), а не проект; одна и та же история рассказана кусками; факты, которые не меняются (день рождения, город, привычки, состав семьи), лежат в MEMORY. Проверять без вывода содержимого: число записей, суммарные длины, пары с Jaccard ≥0.6 по нормализованным словам, счётчики упоминаний по темам. Модель-диагност полезна как второй взгляд, но её вердикт «faithful» не доказывает, что факты не потеряны.

Порядок разбора:

1. Разделить записи на два ведра: устойчивые факты → PROFILE (там нет лимита на длину записи и общий размер владелец принимает), события/планы/медицина/текущий статус/просьбы → MEMORY, повторы → слить.
2. Сверить предлагаемые факты PROFILE с существующим текстом профиля: часть уже там, дубли не добавлять.
3. **Не переписывать личную память молча.** Показать план: что переносится, что сливается, сколько знаков станет в каждом файле, — и отдельным вопросом спросить степень сжатия нарратива (слить только явные повторы / сжать историю в хронику). Владелец выбирает; подробности личной истории он ценит выше компактности, пока не сказал обратное.
4. Применять только после ответа: бэкап `tar` именно `.agents` (не `cp -a` всего каталога пользователей), запись через temp + `os.replace`, затем аудит `scripts/audit-memory-files.py` и побайтовая сверка нетронутых файлов.

## Клиентское состояние ≠ серверное

Выбор терминала, темы, вкладок живёт в `localStorage`; в чате `terminal_id` не хранится вовсе (`select count(*) from chat where chat::jsonb ? 'terminal_id'` → 0). Отсюда: «включить всем» через БД нельзя, а серверная привязка есть только у модели (`meta.terminalId`). Подробности и последствия — `sandbox-terminal.md` § Binding a model.

## Патчи апстрима (фронт/бэкенд) — последний шаг

Родная ручка (env/конфиг/флаг) → замер → и только по слову владельца дериватив `webui-branding/Dockerfile`. Патч бандла или upstream-Python переживает обновление базового образа только если применён в сборке и **валит сборку** при несовпадении строки — иначе тихо ломает UI после бампа. Цена и формулировка для владельца — в SKILL.md «Answering the owner».

Инжект в `index.html` — единственный способ добавить своё поведение на фронте без правки минифицированных чанков: `COPY <script>.js /app/build/static/` + `sed` в тег перед `</head>` с `grep -q` в том же `RUN`. Статика из `/app/build/static` при старте копируется в `/app/backend/open_webui/static`, поэтому проверять надо оба пути и `curl /static/<file>.js` снаружи.

**Скрипт на загрузке страницы ≠ «после входа»:** вход в SPA не перезагружает документ, токен появляется в `localStorage` уже внутри приложения. Всё, что зависит от токена (свой fetch, выбор терминала, персональные запросы), должно опрашивать его появление; иначе у нового пользователя код не сработает ни разу, а в тесте с заранее засеянным токеном — сработает, и разница будет невидима. Симптом на скриншоте владельца: в `localStorage` нет флага скрипта вовсе.
