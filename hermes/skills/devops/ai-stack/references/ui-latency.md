# "Почему UI/API медленно" на этом хосте — измерение и два штатных виновника

Когда владелец говорит «медленно грузится / тормозит», нужен ответ с цифрами и одной причиной, а
не список идей. Порядок: измерить на сервере → исключить ресурсы → найти всплеск запросов →
включить кэш. Каждый раз это одни и те же два виновника.

## 1. Латентность берётся из логов nginx, не из ощущений

| Хост | Файл | Формат |
|---|---|---|
| `ai.esmien.ru` (WebUI) | `/var/log/nginx/access.log` | `cfkomb`, есть `rt=` и `cf=` |
| `llm.esmien.ru` (LiteLLM UI) | `/var/log/nginx/llm.access.log` | дефолтный combined, **без `rt`** — по нему время не померить, только счётчики; для этого хоста время снимать `curl -w '%{time_total}'` |

Агрегировать по URI скриптом (python, не awk по полям — формат `cfkomb` не совпадает с дефолтным):

```python
pat = re.compile(r'"GET (\S+) HTTP[^"]*" (\d{3}) (\d+) rt=([\d.]+)')
# печатать n / avg / median / p95 / max / maxKB на путь, сортировка по avg
```

`rt` — это серверное время (nginx + приложение), клиент и сеть в него не входят. Если `rt` высокий,
виноват не Cloudflare и не «сервер тормозит вообще», а конкретный эндпоинт.

**Перед агрегацией выбросить `101` и `/ws/socket.io`.** У вебсокета `rt` равен времени жизни
соединения (медиана ~72 с, в пике бывало 346 с), и он в одиночку раздувает среднее за минуту до
секунд. Считать только обычные запросы; сокеты смотреть отдельно по кодам ответа.

**В `log_format cfkomb` добавлен `urt=$upstream_response_time`** (`/etc/nginx/conf.d/01-cf-client-ip.conf`)
— так время приложения отделяется от времени nginx. Правя `log_format`, вставлять поле **до**
закрывающей кавычки литерала: наивный append после строки рвёт кавычки, `nginx -t` падает, а
`systemctl reload` не выполняется — сервис продолжает отдавать старый конфиг, и правка выглядит
применённой, хотя её нет. Всегда `nginx -t && systemctl reload nginx` плюс проверка эффекта в
ответе/логе, а не только `systemctl is-active`.

**`.js.map` в логах (по ~500–600 мс) — признак, что у владельца открыт devtools.** Source maps
грузятся только при открытой панели разработчика, и она сама тормозит SPA. Увидел `.map` — сначала
попроси закрыть devtools и перемерить, и только потом что-то менять на сервере.

## 2. Ресурсы — быстрая отбраковка

`docker stats --no-stream` + `free -m` + `uptime`. Показательные цифры с этого хоста при жалобах на
скорость: `open-webui` CPU 1.5 %, 892 MiB, load average 0.3 — то есть compute и память ни при чём,
и дальше копать надо в сторону количества запросов.

## 3. Виновник №1 — админка LiteLLM

28 JS-чанков / 2.97 MB, `Cache-Control` нет, `gzip_types` в `nginx.conf` был закомментирован → каждый
визит тянул всё заново несжатым. Исправлено (`location ^~ /ui/_next/static/` + immutable + gzip);
подробности, цифры и способ правки `/etc/nginx/*` — `references/litellm-admin-auth.md`.

## 4. Виновник №2 — Open WebUI: один воркер и пачка аватарок

- WebUI запущен как `uvicorn … --workers 1` (видно в `/proc/1/cmdline`). Аутентифицированный
  API-вызов стоит **~250–320 мс** (без авторизации тот же путь — 70–100 мс): это не работа, а
  очередь внутри единственного процесса.
- Одна загрузка страницы = `/api/models` ×24, десятки `/api/v1/users/*` и **~124 запроса
  `/api/v1/models/model/profile/image`** (по одному на каждую модель, независимо от того, есть ли
  у неё картинка).
- Обработчик (`routers/models.py`, `get_model_profile_image`) ставит только `ETag`, **без
  `Cache-Control`**, поэтому браузер перепроверяет все картинки на каждый заход.

Лечение — кэш в браузере, а не воркеры:

```nginx
# в server с listen 127.0.0.1:9443 (НЕ в порт-80 редиректе!), перед location /api/
location = /api/v1/models/model/profile/image {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    add_header Cache-Control "private, max-age=3600" always;
}
```

**Ловушка вставки:** в `ai.esmien.ru.conf` первым идёт `server { listen 80; … }` с редиректом.
Если вставить локацию перед первым `location / {`, она попадёт в редирект-сервер: `nginx -t`
пройдёт, reload пройдёт, а заголовка в ответе не будет — проверять надо именно `https`-запрос.
Признак правильной вставки — `grep -n 'profile/image'` показывает строку внутри блока с
`listen 127.0.0.1:9443`. Проверка без токена: 401-ответ должен нести `cache-control`
(для этого и нужен `always`).

## 5. Второй воркер WebUI: что даст и почему пока нет

`UVICORN_WORKERS` читается из env без проверок (`env.py`: `max(int(os.getenv('UVICORN_WORKERS','1')), 1)`),
то есть включить можно, но:

- выигрыш только на очереди: пачка из ~124 запросов делится между воркерами. После кэша аватарок
  p95 = 8 мс и очереди не видно — делить нечего, реальный выигрыш ≈ 0;
- без `WEBSOCKET_MANAGER=redis` каждый воркер держит **свой** реестр сокетов: событие из воркера A
  не доедет до сокета на воркере B, и чат/статусы «залипают» до перезагрузки страницы — тот же
  симптом, что и 502 на `/ws/socket.io`;
- цена: второй процесс ≈ +0.6–0.9 GB RSS (один сейчас 892 MiB) плюс отдельный redis для WebUI
  (чужой `litellm-redis` не занимать — правило ниже) и проверка sticky-поведения сокетов.

Ответ владельцу одной фразой: «второй воркер лечит очередь, а очереди у нас нет; понадобится —
сначала свой redis для WebUI, потом `UVICORN_WORKERS=2`, потом проверка сокетов и памяти».

## 6. Cloudflare — это пол, а не баг

`ai.esmien.ru` за CF (оранжевый), `llm.esmien.ru` — серый (DNS-only). Замер с хоста: через CF TTFB
**71–134 мс**, напрямую в origin **7 мс** — то есть CF добавляет ~60–130 мс на каждый запрос, и это
штатная плата за скрытый origin и WAF. Хэшированная статика уже идёт с edge (`cf-cache-status: HIT`,
`age:` растёт), Turnstile стоит только на `signin`/`signup` и латентность приложения не трогает.
Поэтому «терпимо, если учесть CF и антибот» — правильный ответ, регрессию здесь искать не надо.
Топология, токены и ловушки: `references/cloudflare-proxy.md`.

## 7. Правила ответа владельцу

- **Не предлагать сокращать список моделей.** Ассортимент подобран вручную; множитель — всплеск
  запросов на страницу, а не количество моделей. Совет «убери модели» воспринимается как
  посягательство на его работу.
- **Не складывать параллельные задержки в «итого секунд».** 124 запроса по 300 мс идут параллельно
  и дают 1–2 с реального времени, а не 37 с. Врать арифметикой — худший способ объяснить
  тормоза; называть wall-clock или время одной пачки.
- **Не обещать, что мониторинг LiteLLM пострадает.** Он читает `LiteLLM_SpendLogs` и свои группы;
  витрина WebUI на него не влияет — это разные слои.
- **Воркеры WebUI не поднимать на LiteLLM-овом redis.** `litellm-redis` — выделенный инстанс
  256 MB `noeviction` с `requirepass`; WebUI-сессии в нём сломают запись кэша LiteLLM, а любая
  чистка ключей заденет чужое состояние. Если когда-нибудь понадобятся воркеры — отдельный
  маленький redis для WebUI.
- Отдельный диагностический сигнал, который не надо замалчивать: `/ws/socket.io` в логах отдаёт
  заметную долю `502` (например 84 из 260) — сокеты переподключаются, UI «залипает». Это отдельная
  задача, не следствие кэша; сначала смотреть nginx-таймауты/апгрейд заголовков, а рестарты
  контейнера на это влияют.

## 8. Открытие длинного диалога («сделай замер») — где время на самом деле

Профилировать по слоям, а не «добавим кэш». Скрипт копируется в контейнер и запускается
`docker exec -e PYTHONPATH=/app/backend -w /app/backend open-webui python3 /tmp/x.py` (без
`PYTHONPATH` падает `import open_webui`). Внутри `from open_webui.env import DATABASE_URL` — это
**psycopg2 sync**, `create_async_engine` на нём отказывается (берите psycopg2). В OWUI 0.13.0
таблица `chat` держит сообщения внутри jsonb `chat`, колонки `messages` нет.

Цифры с этого хоста (самый большой чат, 515 KB в БД):

| слой | время |
|---|---|
| `SELECT chat` из Postgres | 32 ms |
| pydantic `model_validate` | 0.1 ms |
| `model_dump_json` | 5–12 ms |
| `json.loads` / `json.dumps` | 4–15 ms |
| HTTP целиком (`rt`) | p50 81 ms, p95 245 ms, max 932 ms |

Читается так: **ни БД, ни pydantic не виноваты** — время уходит на объём (0.5–1.5 MB) и на 3–4
прохода по нему (jsonb → dict → pydantic → JSON). `model_validate` стоит 0.1 ms именно потому, что
`chat` объявлен обычным `dict` и валидация внутрь не спускается; не приводить его ни как «pydantic
быстрый», ни как «pydantic тормозит» без профиля.

**Ловушка замера:** `json.dumps` экранирует кириллицу, и размер, посчитанный через
`len(json.dumps(chat))`, втрое больше реального — брать `pg_column_size(chat)`, иначе вывод про
«мегабайтные диалоги» завышен в разы.

**Идея «кэшировать 3–5 последних чатов пер-юзер»:** кэш сериализованных ответов снял бы большую
часть (32 ms БД + сериализация), но инвалидация снаружи невозможна — приложение перечитывает чат
сразу после отправки сообщения, а у стандартного nginx нет purge, так что TTL-кэш отдаст старую
версию и сообщение «пропадёт». Только внутри приложения (форк `esmien/webui:local`), ценой
сопровождения патча через каждый апдейт OWUI. Не обещать это как «просто включим кэш в nginx».

## 9. «А 2–3 пользователя с длинными запросами потянем?» — считать по истории

Ответ не из общих слов, а из `LiteLLM_SpendLogs`: интервалы `startTime`/`endTime` дают исторический
максимум одновременных вызовов (на этом хосте — 4), p95 длительности (~27 s) и число вызовов дольше
таймаутов (14 > 240 s, 4 > 300 s). Отсюда: несколько параллельных стримов сервер держит (это I/O),
а реальный ограничитель — квота провайдера и `allowed_fails: 2` + `cooldown_time: 60`: после пары
429 группа уходит в карантин для всех, а не для того, кто их поймал.

Тюнинг под этот сценарий (применён): `webui_api_cf` 20 r/s, `burst=240`, `limit_conn conn_per_ip_cf
60`, `proxy_read_timeout`/`proxy_send_timeout` 600 s. Лимиты на `/v1/models` и логин не трогать —
там сидят сканеры.
