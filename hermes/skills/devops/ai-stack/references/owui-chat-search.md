# Поиск по чатам в Open WebUI (модель, токенизация, наш патч)

Глубина к `ai-stack`: как устроен поиск чатов в образе `esmien/webui:local`, что именно мы в нём правим и как проверить правку. Механика патчей образа — `owui-internals.md` § «Патчи апстрима».

## Где живёт

| Файл (в контейнере) | Что |
|---|---|
| `open_webui/models/chats.py` | `chat_search_content_query` (нормализация + вырезание `tag:/folder:/pinned:…`), `chat_search_terms` (токены), `chat_search_snippet`, `Chats.get_chats_by_user_id_and_search_text` (SQL), `Chats.get_chat_search_snippets` |
| `open_webui/tools/builtin.py` | `search_chats` — tool модели: ищет по чатам, исключая текущий, с фильтрами по `updated_at` |

Фильтр апстрима — `or_(точная фраза, and_(все термы))`: вхождение всей строки запроса (ILIKE `%…%` по title, `chat_search_message_content_match_sql` по телу) **или** все токены по отдельности. `search_terms` исключает сам фразу, поэтому однословный запрос = только фразовое совпадение. Порядок: точное фраза-совпадение, затем `updated_at desc`.

## Токенизация — главная причина «по-русски не ищет»

`chat_search_terms` апстрима резал текст по `re.findall(r'[a-z0-9]+', …)` — ASCII-only. Кириллический запрос давал **пустой** список термов, то есть работал только как поиск точной фразы: «как настроить докер» не находило «настроил Docker и докер». Наш патч меняет шаблон на `[^\W_]+` (юникодные word-символы без `_`).

- Действие шире, чем кажется: `chat_search_terms` используется и в UI-поиске, и в tool, и в `needles` для сниппетов/совпадений по заголовку → русские запросы становятся AND-по-словам везде, а не только в tool. Для английского токены те же, регрессии нет.
- Побочный эффект, который надо называть владельцу: UI-поиск по русским запросам стал шире (больше результатов, меньше точности), это следствие фикса, а не отдельная фича.

## Фолбэк в tool `search_chats`

Апстрим на conversational-запросах часто возвращает 0: если хотя бы одного слова нет в чате в этой словоформе, `and_(*term_clauses)` не срабатывает. Наш патч: **если стрикт дал ноль** — по каждому терму (длина ≥3, не больше 5) отдельный запрос, кандидаты объединяются, скор = число совпавших термов, порядок `(-score, -updated_at, id)`, обрезка до `count`. Границы: `limit = min(max(count*3, 15), 60)` на терм.

- Включается только для «простых» запросов: условие `chat_search_content_query(query) == query.lower().strip()` отсекает `tag:/folder:`-операторы, чтобы не размывать фильтры владельца.
- Сниппеты не страдают: `chat_search_snippet` перебирает `[фраза, *термы]`, поэтому найденное фолбэком тоже приходит с куском текста.
- Известные пределы (не баги, но не обещать): термы короче 3 символов игнорируются (запрос из одних «кто я» фолбэка не получит); при `count > 20` потолок 60 может вернуть меньше запрошенного; запросы идут последовательно — `asyncio.gather` срезал бы латентность.

## Проба

Скрипт — в контейнер, запуск от `/app/backend` (`PYTHONPATH` обязателен):

```python
from open_webui.models.chats import Chat, Chats, chat_search_terms
# 1) стрикт-запрос с заведомо отсутствующим словом → 0
# 2) те же термы по одному → union содержит целевой chat.id
print(chat_search_terms('Как настроить докер контейнеры?'))  # ждём 4 терма, не []
```

Первый же вывод `chat_search_terms` на кириллице отделяет «патч не доехал» от «логика не та»: пустой список = в контейнере непатченный `chats.py`. Сверь md5 файлов образа и контейнера (см. `owui-internals.md`).

Фразовые формулировки для проверки брать из реальных чатов: падежи и словоформы — именно то, на чём апстрим ломается.
