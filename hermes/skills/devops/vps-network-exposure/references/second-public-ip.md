# Второй публичный IPv4 на той же ВМ

Когда применять: провайдер выдал дополнительный адрес к той же машине («привязан к порту ВМ» в
панели), надо поднять его, проверить и решить, годится ли он как фоллбэк-вход.

## 1. Что именно выдал провайдер

В OpenStack-подобных панелях адрес привязывается к порту (`allowed address pairs`): пакеты до
него **уже приходят** на нашу NIC, но ядро их молча выбрасывает, пока адреса нет на интерфейсе.
Отсюда главный вывод: «снаружи мёртв» до настройки — **норма**, а не доказательство, что адрес не
выдан. Проверять принадлежность по панели/MAC (`ip -brief addr` → MAC ens3 должен совпадать с
панелью), а не по пингу.

```bash
ip -brief addr show <iface>            # MAC + текущие адреса
whois <new-ip> | grep -iE '^(netname|org-name|country|created)'
curl -s "https://stat.ripe.net/data/prefix-overview/data.json?resource=<new-ip>" \
  | python3 -c "import sys,json;d=json.load(sys.stdin)['data'];print(d['announced'],d['asns'])"
```

`announced: true` + наш же ASN = префикс анонсируется и маршрут до него есть. Сравни ASN нового
адреса с ASN основного: **тот же ASN — это не второй «чистый» выход**, а адрес из той же сети
(для DPI/реестра он даёт ровно то же, что и основной).

## 2. Поднять адрес

**Сначала без файлов** — `/32` на интерфейсе, при успехе уже персистить:

```bash
ip addr add <new-ip>/32 dev ens3
curl -s -o /dev/null -w '%{http_code}\n' --resolve <host>:8443:<new-ip> https://<host>:8443/
```

- **`/32`, а не `/24`.** Адрес выдан по одному; `/24` из чужого RIPE-блока создаёт on-link
  маршрут на всю сеть и уводит пакеты в ARP вместо шлюза.
- **Ничего в сервисах править не надо**, если они слушают `0.0.0.0` (`ss -lntp`) и wildcard
  (`ss -lunp`): после появления адреса nginx/hysteria отвечают и на нём.
- Обратный трафик пойдёт через тот же default gw, что и у основного — работает, если провайдер
  привязал адрес к порту (антиспуфинг на его стороне). Проверка — внешний пинг, не `ping gw`
  (шлюз обычно ICMP не отвечает).

## 3. Персистентность: отдельный файл netplan

`/etc/netplan/50-cloud-init.yaml` генерируется cloud-init и перезаписывается при загрузке
(в шапке файла это написано прямым текстом). Правка в нём не выживает ребут:

```yaml
# /etc/netplan/60-extra-ip.yaml, 0600 root:root
network:
    version: 2
    ethernets:
        ens3:
            addresses:
                - <new-ip>/32
```

`netplan generate && netplan apply`, затем проверить, что оба адреса на месте и внешняя
доступность не пропала. Файл дублировать в recovery-репо (`assets/host/etc/netplan/`), иначе
после пересборки адрес потеряется молча.

Запись в `/etc/netplan/` через инструмент записи файлов может быть запрещена (sensitive path):
писать в scratch и ставить `install -m 600 -o root -g root <src> /etc/netplan/...`.

## 4. Проверка снаружи — матрица, а не одна цифра

`check-host.net` (JSON, `Accept: application/json`, затем `/check-result/<id>` через ~15–20 c):

- `check-ping?host=<ip>&max_nodes=6` — базовая живость;
- `check-tcp?host=<ip>:<port>` по каждому публичному порту (443, 4443, 8443, 2087) — по 4 узла.

Формы ответа различаются и парсер надо писать под обе: у **ping** элемент — вложенный список
`['OK', time, ip]` / `['TIMEOUT', …]`, у **tcp** — словарь `{'address', 'time'}` или
`{'error'}`. Универсальный разбор: считать успехом `dict` с `time` либо список, где `[0] == 'OK'`.
Один-два узла из шести могут таймаутить при живом сервисе — это узел, а не адрес.

**Сквозной тест через туннель обязателен** — открытый порт доказывает только nginx:

```bash
# временный копия клиентского конфига: адрес меняем на новый, SNI/Host/путь — нет
# (streamSettings лежит на уровне outbound, а не внутри vnext!)
curl -s --max-time 25 --socks5-hostname 127.0.0.1:<socks> https://ipinfo.io/ip
curl -s -o /dev/null -w '%{http_code}\n' --socks5-hostname 127.0.0.1:<socks> https://www.gstatic.com/generate_204
```

Проверка `101` на WS-upgrade через `curl --resolve` полезна как быстрый признак, что nginx →
xray путь отвечает, но **не** доказывает авторизацию. Помни: UUID из клиентского конфига должен
принадлежать тому инбаунду, чей путь указан (`/ws` ↔ `ws-in`, `/general` ↔ `in-general`) — чужой
UUID даёт `400` на живом сервере и читается как «адрес не работает». Сверять без вывода секретов:

```python
ids = [c['id'] for c in cfg_inbound['settings']['clients']]
print(uuid_from_cli in ids)   # True/False, сам UUID не печатать
```

## 5. Переключение на него и границы

- Переключение входа = смена A-записи (TTL 300 → пять минут), сервис трогать не нужно.
- **Выход в интернет не меняется**: клиенты придут на новый адрес, а в мир по-прежнему пойдёт
  egress основного IP. Для гео/антифрода нового адреса это значит «ничего не изменилось».
- **Честный вердикт:** адрес из того же ASN спасает только от бана по конкретному IP;
  от блока по SNI, протоколу или подсети — нет.
- Временные клиентские конфиги с UUID удалять (`shred -u`), xray-клиент останавливать — в
  проде не должно остаться лишнего слушающего SOCKS.
