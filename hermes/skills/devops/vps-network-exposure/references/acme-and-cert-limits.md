# Сертификаты для VPN-входа: лимиты LE, ретрай, wildcard

## Лимит считается на «registered domain», а не на поддомен

Бесплатные домены вида `name.qd.je` не входят в Public Suffix List, поэтому
Let's Encrypt считает регистрируемым доменом сам `qd.je`. Следствие: **все
поддомены всех пользователей сервиса делят один счётчик 50 сертификатов / 168 ч**
и выпуск падает на новом имени, хотя ты не выпускал ничего.

Признак в выводе certbot:

```
too many certificates (50) already issued for "qd.je" in the last 168h0m0s,
retry after 2026-11-01 23:21:03 UTC
```

Практика: такой лимит не обходится повтором через минуту — ждать до
`retry after`, и он ещё сдвигается между попытками.

## Цикл выпуска с уважением к retry-after

- Разбирай из вывода `retry after <UTC>`, спи до `ts + 3–4 с` (не ровно в
  секунду — окно закрывается не мгновенно), при следующей ошибке перечитывай
  **новую** метку, а не исходную.
- Нет подсказки — бэкофф 20 → 120 с; общий предел 24 ч; всё писать в лог
  (`/var/log/certbot-retry.log`), иначе многомесячная тишина неотличима от смерти.
- Запускать в фоне с сохранением за сессию: пауза измеряется часами, а не секундами.
- `--webroot -w /var/www/html -d <host> --cert-name <host>` достаточно, если у
  хоста есть порт-80 server-блок с `location /.well-known/acme-challenge/ { root /var/www/html; }`.
  Редирект остального на VPN-порт не должен перехватывать `.well-known`.
- На хосте уже есть аккаунт LE без контакта — новый `certbot` не требует email,
  если переиспользовать существующий аккаунт (`--agree-tos` и без `-m`).

## Переключение на новый домен — часть выпуска, а не отдельный шаг

Оберни выпуск в скрипт: `certbot` → при успехе правит `brand.json` (`host`,
`cert_dir`) → перегенерирует nginx-конфиги и подписки → `nginx -t` →
`systemctl reload nginx` → проверяет `https://<host>:<port>/` curl'ом.
Тогда переезд происходит без владельца и без ручных шагов; до успеха всё живёт
на прежнем домене, и ничего не ломается.

## Wildcard (`*.<домен>`) — только DNS-01, только с DNS-API

- ## Wildcard через Cloudflare DNS-01 — рабочий рецепт

Когда зона живёт в Cloudflare (а не у бесплатного регистратора), DNS-01
становится дешёвым: один сертификат на все хосты, без порта 80 и без лимита «50
на домен».

```bash
apt-get install -y python3-certbot-dns-cloudflare
# токен: My Profile → API Tokens → Custom → Zone / DNS / Edit, Zone Resources = одна зона
install -d -m 700 /root/.secrets
printf 'dns_cloudflare_api_token = %s\n' "<token>" > /root/.secrets/cf.ini && chmod 600 /root/.secrets/cf.ini
certbot certonly --cert-name <zone>-wildcard --dns-cloudflare \
  --dns-cloudflare-credentials /root/.secrets/cf.ini \
  --dns-cloudflare-propagation-seconds 30 \
  -d "*.<zone>" -d <zone> --non-interactive --agree-tos -m admin@<zone>
```

- `*.zone` **не покрывает apex** и только один уровень: `*.esmien.ru` годится для
  `vpn.`/`ai.`, но не для `a.b.`. Добавляй `-d <zone>` отдельно.
- `--cert-name` задавай явно: иначе certbot положит wildcard в каталог первого
  домена и потом путает продление с per-host сертификатами.
- Токену хватает `Zone → DNS → Edit` на конкретную зону: `GET /zones?name=<zone>`
  работает, создание зон/NS/WAF — уже нет. Создание записей:
  `POST /zones/{id}/dns_records {"type":"A","name":"<sub>","content":"<ip>","ttl":120,"proxied":false}`.
- `proxied: false` (серое облако) — обязательное условие для своих vhost'ов на
  нестандартных портах: оранжевое облако терминирует TLS и ломает и 8443, и
  выпуск сертификатов.
- Продление: хук `/etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh`
  (`nginx -t && systemctl reload nginx`), `certbot.timer` уже есть.
- **`certbot renew --dry-run` может висеть минутами** — это встроенный
  `random sleep` (до ~5 мин), а не поломка. Для теста:
  `certbot renew --cert-name <name> --dry-run --no-random-sleep-on-renew`.

## Делегирование поддомена: зона должна существовать у нового NS **до** смены NS

Провайдер бесплатного поддомена при сохранении NS проверяет авторитетность и
отвечает `The external nameservers are not yet authoritative for this domain`,
если зона у нового провайдера ещё не создана. Порядок жёсткий:

1. создать зону `sub.example.com` у DNS-провайдера и получить **его** пару NS;
2. перенести записи (A для каждого хоста, TXT и пр.);
3. только теперь вписать новые NS в панели родителя.

HTTP-01 wildcard не выдаёт. Нужна запись TXT `_acme-challenge`, значит нужен
  доступ к DNS через API либо ручной прогон каждые ~60 дней.
- **Не предполагай, что у бесплатного регистратора есть DNS-API.** У DigitalPlat
  в документации прямо написано «do not assume the API can manage external DNS
  records», а эндпоинты не находятся снаружи: `domain.`/`dashboard.` хосты
  отдают 403/404 на `/api/...`, пути собираются динамически в JS-бандлах.
  Быстрая проверка `curl -H "Authorization: Bearer <token>"` по десятку
  вероятных путей ничего не даёт — не трать на это полчаса.
- Что запросить у владельца: **страницу API-документации из его панели** (там же,
  где он взял ключ) или подтверждение, что DNS-записи доступны по API. Токен без
  списка эндпоинтов бесполезен.
- Если API нет — путь B: делегировать зону (NS) провайдеру с открытым REST API
  (deSEC и подобные), **сначала переписав все текущие записи** (A для каждого
  поддомена, TXT и пр.), и только потом менять NS. Порядок важен: смена NS без
  переноса записей роняет все сервисы зоны.

## Чего не делать

- Не проверять «страну/доступность» по HTML: заглушки и рабочие страницы
  отдаются с одинаковым 200 — судить только живым клиентом и авторизацией.
- Не ставить несколько выпусков в гонку за освободившийся слот лимита: один
  фоновый цикл на домен, иначе попытки съедают друг другу квоту и путают метки
  retry-after.
