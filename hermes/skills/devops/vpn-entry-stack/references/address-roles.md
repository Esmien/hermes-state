# Адреса и роли: вход, бренд, гейт

Один хост, несколько адресов — и у каждого своя работа. Имена ниже не косметика: ими
пользуемся в чате, в ранбуке и в правилах, чтобы не выяснять каждый раз «а 85.92.158.226 —
это который?».

| алиас | адрес | роль | что на нём живёт |
|---|---|---|---|
| **brand** | `141.98.166.213` | бренд и админка | сайт, WebUI, бот, LLM-гейт, SSH из РФ |
| **edge** | адрес из пула (напр. `85.92.158.238`) | единственная точка входа VPN | nginx 443/8443/2087 + hysteria UDP/8443 |
| **gate** | `85.92.158.226` | исходящий NL для Gemini | только `freedom` + `sendThrough` |

Правило владельца: **brand — только нормальные сервисы и SSH, ни одного VPN-входа**; edge —
расходник, умер так умер; gate — не светится вообще.

## Ловушка, которая обнуляет всю схему

`listen 8443 ssl` в `vpn-*.conf` и `listen: :8443` в hysteria — это **все адреса машины**,
включая gate. То есть сегодня бан VPN-входа по адресу уносит и Gemini-гейт, хотя по замыслу
он должен молчать. Перед разведением ролей проверять `ss -lntu | awk '$5 ~ /^(0\.0\.0\.0|\*)/'`
и сузить бинды:

```nginx
listen 85.92.158.238:8443 ssl;   # только edge; [::] убрать, если IPv6 не нужен
```
```yaml
listen: 85.92.158.238:8443       # hysteria: адрес вместо `:`
```

У gate не должно остаться **ни одного** слушающего сокета — его роль только исходящая.

## Как перевезти вход на другой адрес

1. `/32` отдельным файлом netplan (`70-extra-ip-edge.yaml`, режим 600), `netplan generate &&
   netplan apply`; `50-cloud-init.yaml` не трогать — перегенерируется при загрузке.
2. Сузить `listen` в vhost'ах и hysteria до нового адреса (см. выше), `nginx -t` → `reload`.
3. A-запись входного имени на новый адрес, TTL 300 — клиенты подхватят за минуты.
4. Проверять сквозным клиентом, а не `ss`: временный `xray run -c /tmp/…json` через SOCKS,
   затем `ipinfo.io/ip` (должен быть выход, не вход) и `204`. Погасить процесс и убрать конфиг.

## Один сертификат на пул адресов — это норма

Паспорт выдаётся **имени**, а не машине. В клиентских записях пула ставится
`address = <IP>`, `sni = <имя>`, `Host = <имя>`; сертификат один на всех, потому что имя одно.
Мёртвый адрес меняется строкой в подписке. Второй серт на пул не нужен и только плодит имена.

Следствие, которым стоит пользоваться: **имени не обязательно никуда резолвиться.** Клиент
прибивает SNI сам, поэтому можно выпустить серт по DNS-01 (Cloudflare, A-запись не нужна) и
не публиковать ни одной A-записи — тогда в пассивных DNS-базах связки «IP ↔ домен» нет,
остаётся только факт выдачи в CT-логах.

Изоляция имён работает только на **другом регистрируемом домене**: `vpn2.esmien.ru` бан по
`esmien.ru` заденет. Cloudflare как регистратор — можно, прокси (оранжевое облако) — нельзя:
не пропустит VLESS/WS на наших портах, подменит TLS и нарушит их ToS.

## Пул: один /24 — одна судьба

Адрес из того же `/24` не страховка от бана подсети и от листовых листингов (UCEPROTECT L2
банит блоком). Если в этом `/24` живёт gate, входной адрес оттуда нельзя грузить общим
трафиком: любой листинг притащит гейт. Вход и запас лучше брать из **другого префикса**
(просить у провайдера явно), а внутри одного `/24` держать только «чистые» роли.

## Вторая машина в подписке — без второго мозга

Подписка — это список ссылок, который генерит `make_sub.py` на brand. Поэтому вторая машина
не копирует стек, а становится **edge**:

1. Харденинг по тому же шаблону (ключи, только 443 наружу, автообновления).
2. Серт на то же имя по DNS-01 — имя не меняется, A-запись не нужна, серт легально живёт на
   двух машинах.
3. nginx на 443 с этим сертом + xray inbound VLESS WS, **свой UUID** (отзыв отдельный).
4. Аутбаунд на основную машину (WireGuard или `vless` в наш же вход) — тогда все правила
   (Gemini → gate, `.ru` → релеи, остальное → direct) продолжают жить в одном конфиге.
5. `fallbackTag`/балансер `[туннель, direct]`: если основная машина легла, edge выпускает
   трафик сам. Без этого «запасная» машина бесполезна ровно в момент аварии.
6. В подписке — одна запись: имя, `address = <IP edge>`, `port = 443`, `sni`, `path`, UUID.
   Клиенты видят новый узел, ничего не переустанавливают.

Цена: лишний RTT «клиент → edge → brand». Пока имя общее, бан по SNI убьёт обе машины —
страховочный узел должен отличаться именем (второй домен) или транспортом.

## Чего эта схема не лечит

- **Аккаунт у провайдера**: один абуз — и уходят все адреса аккаунта разом. Только другая
  машина в чужой ASN.
- **Железо**: кернел-паника, диск, сбой хоста — лежит всё.
- **Выход наружу по-прежнему с brand**: РКН видит адрес, к которому подключается клиент (вход),
  а не тот, с которого сервер ходит в интернет. Поэтому «brand чист» достигается и без
  переезда выхода — но бан сайта по IP всё равно уносит и выход.
