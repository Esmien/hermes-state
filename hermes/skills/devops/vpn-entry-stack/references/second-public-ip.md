# Второй публичный IPv4 на той же машине

## Что он покупает и чего не покупает

- Спасает от бана **по конкретному адресу**: другое /24, в реестре и листах его нет.
- Не спасает от бана по SNI, по протоколу и по ASN/диапазону: домены, сеть и железо те же.
  Один провайдер почти всегда выдаёт адрес из своей же ASN — это отсрочка, а не страховка.
- **Egress не меняется.** Пока к адресу не привязан отдельный аутбаунд, весь исходящий трафик
  по-прежнему уходит основным адресом, и Google/антифрод видят прежний вердикт.

## Поднять адрес

1. Провайдер привязывает адрес к порту ВМ (в Neutron — второй fixed IP на том же порту, MAC не
   меняется), но на интерфейсе его нет: снаружи адрес молчит, Shodan его не знает.
2. Сначала **непостоянно**: `ip addr add <IP>/32 dev ens3`. Именно `/32` — при `/24` ядро ставит
   on-link маршрут на всю чужую подсеть, и трафик к «соседям» уходит в ARP вместо шлюза.
3. Локальная проверка: `curl -s -o /dev/null -w '%{http_code}' --resolve share.esmien.com:8443:<IP>
   https://share.esmien.com:8443/` → `302`.
4. Только после этого постоянно: **отдельный** файл `/etc/netplan/60-extra-ip.yaml` с
   `addresses: [<IP>/32]`. `50-cloud-init.yaml` перегенерируется cloud-init при загрузке — правка
   в нём не выживает.
5. `netplan generate && netplan apply`, затем `ip -4 -brief addr show ens3`: должны быть оба адреса.
6. Сервисы править не нужно: nginx слушает `0.0.0.0` (443/4443/8443/2087), hysteria `*:8443/udp` —
   после `apply` всё отвечает и на новом адресе. Новый `listen` в будущем не прибивать к одному
   IP, иначе второй адрес молча перестанет работать.
7. Файл зеркалить в `vps-infra/assets/host/etc/netplan/`: без него восстановление теряет адрес.

## Проверить, что он действительно живой

- Снаружи — check-host: `check-ping` и `check-tcp` по каждому порту. Обязательно смотреть узлы
  `ru*`: адрес нужен именно для РФ. Разбор формата ответа — питфолл в
  `ip-reputation-and-ban-risk` (результат вложенный, первый опрос отдаёт `pending`).
- Сквозной тест туннеля: временный xray-клиент на одноразовом порту, в аутбаунде меняется только
  `address` на новый IP, а `tlsSettings.serverName` и ws `headers.Host` остаются доменом. Дальше
  через SOCKS: `ipinfo.io/ip` (какой адрес вышел), `generate_204`, `www.gosuslugi.ru`.
- Ожидаемые коды на живом входе: `/ws` или `/general` по HTTP → `400` (антехкамера VLESS, не
  поломка), `101` на websocket-upgrade → путь дошёл до xray.

## Привязать исходящий трафик к адресу

- Разово: `curl --interface <IP> https://ipinfo.io/json` — видно, каким адресом машина вышла.
- В Xray: `sendThrough` работает **только на уровне аутбаунда**:
  `{"tag":"direct-ip2","protocol":"freedom","sendThrough":"<IP>","settings":{...}}`.
  Внутри `settings` поле принимается молча и игнорируется — egress остаётся прежним, и это
  выглядит как «правило есть, а Google видит старую страну». `domainStrategy` в `settings`
  устарел: Xray сам переносит его в `sockopt.domainStrategy` с предупреждением.
- Проверка механизма: SOCKS-инбаунд на одноразовом порту → этот аутбаунд →
  `curl --socks5-hostname 127.0.0.1:<port> https://ipinfo.io/ip` должен вернуть новый адрес.

## Испытать гейт, не трогая живой маршрут

Проверка «а вдруг так лучше» делается отдельным входом, который видит только владелец:

1. Снимок `config.json`, `brand.json`, `apply_brand.py` в `/root/vpn-router/backups/<метка>-<ts>/`.
2. Инбаунд-клон `in-general`: новый `tag` (`in-test`), следующий свободный порт (10084), свой
   `wsSettings.path` (`/test`), email'ы клиентов переписать на новый тег — иначе статистика сольётся.
3. Аутбаунд с `sendThrough` (см. выше).
4. Правило `{"inboundTag":["in-test"],"domain":[<весь google-чейн>],"outboundTag":"nl"}` — **строго
   до** правила с `balancerTag: bal-google`: правила матчатся сверху вниз, первое совпадение забирает
   запрос. Домены копировать из того же правила целиком, не сокращать до `gemini.*`.
5. `brand.json` обычно уже содержит `/test` в `paths`/`upstreams` (порты там исторические — сверять
   с реальным инбаундом); затем `apply_brand.py && nginx -t && systemctl reload nginx && vpn-cfg apply`.
6. Проверять живым клиентом через `/test`: cc страны, госуслуги `200` (`.ru` уходит московским
   балансером), youtube `200`, обычный egress — основной IP.
7. Узел только владельцу: дописать запись в `extra_nodes.json` его токена (`name`, `link` из
   `make_sub.vless(uid, "/test", name)`, `clash` из `make_sub.clash_proxy(...)`) и пересобрать **один**
   токен: `make_sub.build(token_dir, uid)` — не `main()`, который переписывает все подписки.
8. Откат: вернуть снимок → `vpn-cfg apply`, удалить запись из `extra_nodes.json`, пересобрать токен.

Питфоллы испытания:

- **`pkill -f <имя-файла>` убивает собственный шелл** — шаблон совпадает с командной строкой
  вызывающего процесса, и проверка обрывается на `exit -15` посреди вывода. Гасить по PID
  (`process_manage kill`) или шаблоном `[c]lient.json`.
- **Неактивный цвет после такой правки пишет «N-1 из N инбаундов»** (`vpn-cfg status`): новый порт
  есть в `config.b.json`, но контейнер `b` ещё крутит прежний конфиг и не слушает `+1000`. Это не
  поломка — следующий `apply` поднимет и его; не начинай искать причину в конфиге.

## Как он используется

- **Как вход-фоллбэк:** переключение = смена A-записи (TTL 300, пять минут), сертификат и SNI не
  меняются, клиенты переезжают сами.
- **Как гейт для Google:** только вместе с привязкой egress (см. выше), иначе cc не меняется.
  `.ru` при этом остаётся на московском выходе: с иностранного адреса госуслуги отдают `000`.
- Вердикт страны проверять по каждому адресу отдельно — один и тот же хост может отдавать два
  разных cc: `references/gemini-geo.md`.

## Адрес от ДРУГОГО провайдера — что реально можно, а что нет

Владелец рано или поздно спрашивает: «купить адрес у другого хостера и привязать к этой машине».
Ответ — **нельзя**, и объяснять надо механизмом: адрес маршрутизируется только внутри той сети,
где он выделен; объявляет его в интернет только её владелец. Чужой /32 на `ens3` чужой ВМ не
поднимется — `ip addr add` пройдёт, но пакеты до него не доедут.

Единственное исключение — **BYOIP**: свой префикс (PI-ассайнмент), своя AS, BGP-сессия с
хостингом, который согласится анонсировать; на практике это LIR-членство + AS + документы, цена
уровня бизнеса и месяцы, а не «купить адрес». Для частного контура — ноль смысла, так и сказать.

Что делать вместо — по возрастанию цены:

1. **Спросить своего хостера про адрес вне его ASN.** У многих несколько апстримов, и часть
   адресов приходит из чужих сетей; это один тикет и ноль денег. Спрашивать формулировкой «есть
   ли IPv4 из префикса, который не <ASN хостера>», а не «дайте другой адрес» — иначе выдадут
   соседнюю /24 той же сети.
2. **Дешёвый VPS в другой ASN как реле.** Адрес продаётся только вместе с машиной, поэтому
   «отдельный IP» = нано-инстанс у другого провайдера, который переливает трафик на нас (или
   наоборот — мы в него). Это одна машина, а не «плодить серверы»; держать законсервированной как
   страховку от смерти всей ASN.
3. **Статический прокси-провайдер** ($1–3 за адрес) — адрес не на машине, а как выход: обычный
   `socks`-аутбаунд в Xray плюс правило. Минусы: лишний хоп, латентность, чужая перегруженная
   сеть и свои метки у антифрода — для аварийного egress годится, для основного трафика нет.

Кандидата всё равно прогонять через `ip-reputation-and-ban-risk`: ASN (`ip.guide/<IP>`), листы и
маркер страны — иначе «свежий адрес из чужой сети» окажется той же ASN перепродавца или сразу `ru`
для Google.
