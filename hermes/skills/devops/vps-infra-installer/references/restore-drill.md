# Restore drill on a clean machine (no TLS)

Прогон полного восстановления на чистой машине: единственный способ доказать, что путь
«пустой сервер → живой стек с данными» реально проходится. Владелец считает такой прогон
обязательным и требует именно e2e, а не «поднялось на глазок».

## Форма, которую владелец принял

1. **Ничего не копируем руками, кроме секретов.** Репозиторий — `git clone` с GitHub,
   не tar/scp с живого сервера. `.env` раскладывает сам установщик из зашифрованного архива.
2. **Поднимаем всё**, включая нотификаторы, бэкаперы и всех сторожей — на **тестовых**
   токенах ботов, которые владелец выдаёт отдельно.
3. **Hermes с харнессом обязателен** (`--hermes --restore-hermes`).
4. **Пропускаем только TLS** (`--skip-tls`): у машины за NAT нет входящего адреса, а путь
   сертификатов проверяется живым продлением каждый день.

## Команда — одна, дальше уходить

На хосте (Ubuntu) готовится файл стартовых секретов `~/bootstrap.env` (GITHUB_TOKEN,
SECRETS_KEY, TG_FILE_TOKEN + тестовые токены ботов + `WEBUI_URL=http://drill.local`),
после чего весь прогон — один блок:

```bash
multipass launch 24.04 --name drill --cpus 4 --memory 8G --disk 80G \
  && multipass transfer ~/bootstrap.env drill:/tmp/bootstrap.env \
  && multipass exec drill -- bash -c 'curl -fsSL https://raw.githubusercontent.com/Esmien/vps-bootstrap/main/bootstrap.sh | sudo bash'
```

Внутри виртуалки ничего руками не клонируется и не копируется: bootstrap сам тянет приватный
репозиторий по токену, раскладывает `.env` из архива и запускает установщик со всеми флагами.
Прогресс идёт живым блоком в терминал (под заголовком шага — последние 20 строк), полный лог
— `/var/log/vps-infra-install.log`, stderr самого bootstrap дублируется в
`/var/log/vps-bootstrap.log`. По ним и проверяется ход прогона, не дожидаясь конца.

Если нужен только план — `BOOTSTRAP_DRY=1` в env-файле (пробрасывается как `--dry-run`).

`TG_FILE_TOKEN` в env-файле — именно **реальный** токен файл-бота: им скачиваются и архив
секретов, и дампы базы. Он же обязателен потому, что шаг `secrets` перезаписывает
`notifications/.env` тестовым токеном **до** шага `fetch`: без явного `--tg-token` скачивание
пойдёт тестовым ботом и упрётся в 404.

## Что считается успехом

```bash
docker ps --format '{{.Names}}' | wc -l                                    # 18
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/           # 200
curl -s http://127.0.0.1:4000/health/liveliness                            # I'm alive!
sudo -u postgres psql -d webui_db -Atc 'select count(*) from chat;'         # 265
sudo -u postgres psql -d litellm_db -Atc 'select count(*) from "LiteLLM_ProxyModelTable";'  # 80
hermes --version && ls -d /root/.hermes/skills/*/*/ | wc -l                 # 29
systemctl list-timers --no-pager | grep -cE 'watchdog|autorecover|backup'   # >=3
sha256sum /home/ai_service/ai-stack/ai/.env                                 # сверка с инвентарём
```

Числа — эталон на дату написания; расхождение по чатам/моделям нормально, расхождение по
`.env` — нет: значит шаблон потерял ключи.

## Что после восстановления выглядит «сломанным», хотя это не баг

- **Живые сессии внешних подписок не переезжают.** ChatGPT device-code login лежит в
  `/root/litellm-chatgpt/auth.json` (и `siwc/auth.json`) — это сессия, а не данные, в дампом
  она не попадает. После rebuild группа `chatgpt/*` и её `aider./hermes.`-алиасы дают
  `500 model group failed` / `ChatGPT device-code login needs a human`, пока владелец не
  пройдёт login заново. Не считать это регрессией восстановления.
- **Признак полноты дампа — не только чаты.** На восстановленном стенде сходится: 80 записей
  в `LiteLLM_ProxyModelTable`, ~52 ключа (`LiteLLM_VerificationToken`), >100k строк `LiteLLM_SpendLogs`,
  2 юзера LiteLLM; в WebUI — 11 пользователей и ~263 чата; `/model/info` отдаёт ~72 из 80
  (часть записей — алиасы без своего деплоймента, это нормально), наружу в WebUI — ~60 моделей.
  Реальные вызовы: `POST /v1/chat/completions` через LiteLLM и через `vps-admin-hermes` в WebUI
  должны вернуть 200, а не только `/health/liveliness`.
- **`Model not found` в логе Hermes** — смотреть время: записи до запуска восстановления —
  история предыдущего периода, а не текущая поломка.

## Секреты: как устроено восстановление

- Архив — набор `secrets_offsite` в реестре `file_id` (файл `<ts>.tar.gz.enc`) плюс
  `<ts>.inventory.txt` с sha256 каждого `.env` и списком имён ключей (без значений).
- `--secrets-from-bot` берёт набор из файл-бота; `--secrets-archive PATH` — локальный `.enc`
  (когда архива в боте ещё нет). Пароль — `--secrets-key`, по умолчанию
  `/root/.secrets/offsite.key`.
- Внутри архива пути абсолютные относительно `/`: `home/ai_service/ai-stack/ai/.env`,
  `home/ai_service/notifications/.env`, `root/.hermes/.env`, `root/deploy/music_bot/.env`.
  Распаковка идёт в `/`, права ставятся автоматически: `640 root:ai_service` для `/home`,
  `600` для `/root`.
- Восстановление выполняется **до** `preflight`, иначе `self.env` останется пустым и шаблон
  упадёт с «в шаблоне не заполнены: …».

## Проверка без опасности для живого хоста

`VPS_INFRA_SECRETS_ROOT=/tmp/testroot` перенаправляет распаковку архива в тестовый корень —
живые `.env` не трогаются:

```bash
rm -rf /tmp/testroot && mkdir -p /tmp/testroot
VPS_INFRA_SECRETS_ROOT=/tmp/testroot python3 install.py --only verify \
  --secrets-archive /var/lib/secrets-offsite/secrets_<ts>.tar.gz.enc \
  --secrets-key /root/.secrets/offsite.key
find /tmp/testroot -name '.env' -printf '%m %u:%g %p\n'
```

Затем сверить sha256 распакованных файлов с инвентарём — это доказывает, что архив целый,
а не «распаковался без ошибок». Аналогично `VPS_INFRA_HERMES_ENV=/tmp/.env` позволяет
проверить `--hermes-token` на копии, не подменяя токен живого агента.

## Кто за что отвечает (боты и не-боты)

Владелец путается в токенах — в ответе всегда расписывай роль каждого, а не только имя переменной.
В продакшене живут ровно три бота, и проверяются они `getMe` (печатать только `username`):

| Переменная | Бот | Роль |
|---|---|---|
| `BOT_TOKEN` | `@esmien_vps_notificator_bot` | алерты, `/health`, `/backups`, `/docker_ps` |
| `FILE_BOT_TOKEN` | `@esmien_ai_backups_bot` | **куда** новый сервер складывает бэкапы |
| `HERMES_BOT_TOKEN` | `@esmien_vps_admin_bot` | Hermes разговаривает с владельцем |

- `GITHUB_TOKEN` — не бот: клон приватного `vps-infra`, реестр `file_id` из `hermes-state`,
  бэкап харнесса. Внутри установщика та же сущность называется `GITHUB_KEY`; bootstrap
  экспортирует оба имени, а `load_config()` принимает `GITHUB_TOKEN` как fallback.
  Симптом рассинхрона имён: «реестр file_id недоступен — укажите --tg-registry».
- `SECRETS_KEY` — пароль архива `.env`, не токен. Неверный → «не расшифровалось (не тот пароль?)».
- **`TG_FILE_TOKEN` и `FILE_BOT_TOKEN` — одна и та же сущность в двух ролях:** «откуда качаем»
  и «куда пишем». В проде это один бот, в прогоне обязаны быть разными: источник — только
  реальный (у тестового нет истории файлов), приёмник — только тестовый (иначе наборы бэкапов
  тестовой машины свалятся в боевой чат).

## Грабли

- **`restore_secrets` идёт до шага `users`.** На чистой машине группы `ai_service` ещё нет,
  и `shutil.chown` падает `LookupError: no such group: 'ai_service'` (это не `KeyError` — ловить
  надо оба). Правильно: распаковать с правами `640`/`600`, запомнить пути в `self.secret_paths`
  и дожать владельца в `step_users` после создания пользователя. Ошибку `chown` на этом этапе
  делать фатальной нельзя — она штатная.
- **Публикация `bootstrap.sh` и кэш raw.** После `publish_bootstrap.py` GitHub отдаёт старый
  файл по `raw.githubusercontent.com` ещё несколько минут. Проверять содержимое через API
  (`/repos/.../contents/bootstrap.sh`) или по маркеру строки, а не по «у меня же запушено»;
  иначе следующий прогон тихо возьмёт прошлую версию.
## Как посмотреть на стенд снаружи

Оба сервиса слушают только `127.0.0.1`, и это не меняется ради удобства — смотреть через SSH-туннель:

```bash
ssh -N -L 8080:127.0.0.1:8080 -L 4000:127.0.0.1:4000 root@<host>
# WebUI → http://localhost:8080,  LiteLLM UI → http://localhost:4000/ui
```

Логин LiteLLM — `UI_USERNAME`/`UI_PASSWORD` из `ai/.env` на самой машине (`grep` ключей, значения
в чат не выводить). Публиковать 8080/4000 наружу ради просмотра нельзя: на прогоне без TLS это
немедленно открытый в интернет шлюз с мастер-ключом.

- **Повторный прогон после падения не требует ручной чистки.** `/opt/vps-infra` обновляется
  `git fetch --depth=1` + `reset --hard`, а уже распакованные `.env` перезаписываются теми же
  значениями. Достаточно повторить ту же команду.

- **Два процесса на одном токене бота крадут друг у друга обновления.** Прогон со живыми
  токенами отбирает команды у боевых ботов: живой `server-monitor-bot` начинает молча
  терять `/health`, а Hermes — свои сообщения. Всегда тестовые токены через
  `--bot-token/--file-bot-token/--hermes-token`.
- **Восстановленный харнесс Hermes тащит cron-задачи.** После прогона их надо погасить
  (`hermes cron ...`) или сразу удалить машину, иначе они начнут работать по расписанию
  внутри виртуалки и слать сообщения в тестовый бот.
- **Установщик Hermes интерактивный, но это уже не мешает:** без tty `install.py` запускает
  его с `--non-interactive` (переопределяется `HERMES_INSTALL_ARGS`). Если прогон всё же
  встал на вопросе — значит запускали с живым tty и без переменной, это не зависание.
- **`--from-bot` тянет ~1 ГБ файлов пользователя** (55 частей) сверх дампов: полный прогон
  это ~27 ГБ образов + 1 ГБ данных + сборка двух своих образов. Замер на чистой виртуалке:
  **3567 с (~60 мин)** от `bootstrap.sh` до `готово`. Первый шаг, который смотрит владелец, —
  таймер; обещать меньше часа на холодный прогон нельзя.
- **`WEBUI_URL` из архива указывает на боевой адрес.** Для прогона переопределять
  `--set WEBUI_URL=http://drill.local`, иначе интерфейс будет строить ссылки на прод.
- **Прогон через `multipass exec` может не дать tty**, и тогда живой блок прогресса честно
  откатывается к построчным строкам — это не поломка. Если нужно увидеть именно блок, запускать
  из интерактивной сессии виртуалки; отрисовку без экрана проверять
  `scripts/pty-screen-dump.py` (`references/installer-output-pane.md`).
