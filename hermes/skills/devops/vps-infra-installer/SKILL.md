# vps-infra installer (this VPS)

## When to Use

Нужно поднять инфраструктуру на чистом сервере, переехать на другой VPS,
или изменить сам установщик. Стек: PostgreSQL 17 + pgvector, LiteLLM,
Open WebUI, SearXNG, open-terminal, Redis, Nginx + Certbot, бэкапы,
Telegram-мониторинг, в конце — Hermes (хостовый режим).

Репозиторий: `github.com/Esmien/vps-infra` (**публичный**, секретов внутри нет).
План перевода установщика на модули-профили (`core` / `agent` / `full`) и карта зависимостей
стека — `~/.hermes/tasks/docs/modules-plan.md` (документы задач живут в харнессе; в `vps-infra/docs/`
остаются только доки про саму инфраструктуру); в нём же открытые вопросы, которые решает владелец, а не агент.
Публичная точка входа для `curl | bash` — отдельный репозиторий `Esmien/vps-bootstrap`,
в нём лежит только `bootstrap.sh` и README. Оба репозитория читаются без токена: клон идёт
по обычному https, реестр `file_id` берётся из `raw.githubusercontent.com`, а не из GitHub API
(у API лимит 60 запросов/час на IP и лишний 404 на чужой токен). `GITHUB_TOKEN` — только для
пуша и на случай приватности; без него прогон полноценный. Рабочая копия на этом сервере: `/root/vps-infra`. Живой стек —
`/home/ai_service/ai-stack`; его `deploy.sh` исторический и не покрывает
Hermes, бэкапы и мониторинг.

**VPN-вход в установщик не входит и входить не должен.** VLESS/WS+TLS, `vpn-router`, подписки —
самостоятельный проект `Esmien/vpn-service` (skill `vpn-entry-stack`). После переустановки сервера
`curl | bash` поднимает только AI-стек: туннель возвращается отдельным `deploy.sh`. Не обещать
владельцу «одна команда восстанавливает всё» — это две команды и два репозитория.

## Граница: харнесс или инфра

Перед тем как что-то создать, решить, где оно живёт — это правило владельца, а не вкусовщина:

- **Харнесс** (`~/.hermes`, бэкап в `Esmien/hermes-state`) — описания задач, планы, концепты,
  инструкции, скиллы, память. Это состояние агента.
- **Инфра** (`vps-infra` + `/etc` + `/usr/local/bin` + systemd) — скрипты, демоны, юниты,
  env-файлы с секретами, рантайм в `/var/lib/<name>`. Это разворачиваемое на новой машине.

Две проверки, которые решают спор за одну секунду: «переживёт ли это переустановку харнесса?» →
инфра; «это нужно агенту, чтобы понимать, как идёт работа?» → харнесс. Работающее, но лежащее в
`~/.hermes` — это и есть искомая «утечка ответственности».

Раскладка при переносе: скрипт → `/usr/local/bin/` + зеркало `assets/host/bin/`; юнит →
`/etc/systemd/system/` + `assets/host/systemd/`; токен → `/etc/vps-infra/<name>.env` (600) и в
список `secrets-offsite-backup.py`; доки → `~/.hermes/tasks/docs/`, ссылка с доски — `file:` от
`~/.hermes/`. После переезда удалять дубль-источник и проверять, что старый путь не остался ни
в юнитах (`grep ExecStart`), ни в установщике, ни в скиллах: ссылка на удалённый файл живёт
месяцами и всплывает в самый неподходящий момент.

## One-liner

**Владелец требует одну команду и уход.** Любая инструкция развёртывания подаётся как один
copy-paste блок; многошаговые «сначала склонируй, потом запусти с флагами» он отвергает
(«инструкция разворачивания ГОВНО»). Всё, что можно автоматизировать, автоматизируется в
`bootstrap.sh`, а не переносится в чат.

```bash
curl -fsSL https://raw.githubusercontent.com/Esmien/vps-bootstrap/main/bootstrap.sh | sudo bash
```

**Сколько это занимает — говорить замером, а не суммой частей.** Холодный полный прогон
(`bootstrap` → `install` на чистой машине, без TLS, с восстановлением) идёт **≈60 минут**;
повторный `--yes` на живом стеке — ~15 с. Оценки вида «30 минут» — это время отдельных шагов,
выданное за весь прогон; владелец сверяет их с таймером и ловит расхождение вдвое. Источник
цифр — не память, а сам прогон: `install.py` пишет `duration_sec` в
`/var/lib/vps-infra/state.json` и печатает `готово за N c`, `bootstrap.sh` —
`готово: HH:MM:SS UTC`; в `/var/log/vps-infra-install.log` шаги видны с метками времени, по
ним и раскладывается, что съело час (обычно apt + pull ~27 ГБ образов + сборка своих).
Если спросили «сколько займёт» — отвечать диапазоном с указанием, что входит (TLS, дампы,
webui_data), а не одним числом.

**Формат ответа во время серии падений.** Один экран: причина одной фразой → что
поправлено → та же одна команда запуска. Без пересказа пройденных шагов, без
списка «что мы уже сделали» и без инструкций из нескольких блоков — владелец в
этот момент раздражён и читает только команду и вердикт.

До запуска на машине лежит файл стартовых секретов (`/root/bootstrap.env`, иначе
`/tmp/bootstrap.env` или `./bootstrap.env`; путь можно задать `VPS_BOOTSTRAP_ENV`):

```
GITHUB_TOKEN=ghp_...        # НЕОБЯЗАТЕЛЕН: репозитории публичные, клон и реестр идут без токена
SECRETS_KEY=<пароль архива .env>
TG_FILE_TOKEN=123:AA...     # РЕАЛЬНЫЙ файл-бот: из него тянутся секреты и дампы
# необязательно:
BOT_TOKEN=... FILE_BOT_TOKEN=... HERMES_BOT_TOKEN=... WEBUI_URL=... EXTRA_ARGS="--skip tls"
```

Проверка стартовых секретов обязана ругаться **один раз и по всему списку**: показать все
отсутствующие переменные и то, какие ключи в файле фактически есть. Иначе владелец правит
файл по одной строке за прогон. Имена-синонимы принимаются: `GITHUB_KEY`=`GITHUB_TOKEN`,
`FILE_BOT_TOKEN`=`TG_FILE_TOKEN`.

`bootstrap.sh` ставит git/curl/python3/openssl → клонирует приватный репозиторий по токену
и сразу вычищает токен из `.git/config` → пишет пароль архива в `/root/.secrets/offsite.key`
(600) → запускает `install.py` с готовым набором флагов (`--yes --secrets-from-bot
--secrets-key … --tg-token … --from-bot --hermes --restore-hermes`, плюс тестовые токены и
`--set` из env-файла). Лог установщика — `/var/log/vps-infra-install.log`; `bootstrap.sh`
дублирует туда только свой stderr (`/var/log/vps-bootstrap.log`). **stdout установщика через
`tee` не прогонять:** труба лишает его tty, и живой блок прогресса молча превращается в
плоский поток строк. По умолчанию TLS пропускается; `WITH_TLS=1` включает шаг nginx/certbot, `BOOTSTRAP_DRY=1`
превращает прогон в `--dry-run`.

**Прогресс — не поток строк.** Владелец требует, чтобы под заголовком текущего шага жил блок
последних 15–20 строк вывода, старые строки уходили вверх, а заголовки пройденных шагов
оставались в истории; при смене шага блок стирается, заголовок остаётся. Это реализовано
классом `Pane` в `install.py` (ANSI-курсор, откат к построчному выводу при не-tty,
`NO_PANE=1` для отключения). Правила якорной арифметики, перехвата вывода дочерних процессов
и проверки отрисовки — [references/installer-output-pane.md](references/installer-output-pane.md);
правку панели без такой проверки не считать сделанной.

**Канон `bootstrap.sh` живёт в приватном `vps-infra`, публичная копия только для curl.**
Рассинхрон ловит `maintainer/publish_bootstrap.py` (сверяет содержимое по API и коммитит
только при отличии; `--check` — exit 1 при расхождении). Правку скрипта без публикации
считать незавершённой: владелец запускает именно публичный URL.

Проверять факт публикации **через API** (`curl -H "Accept: application/vnd.github.raw"
https://api.github.com/repos/Esmien/vps-bootstrap/contents/bootstrap.sh`), а не через
`raw.githubusercontent.com`: raw отдаёт CDN-копию до ~5 минут, и сразу после пуша там
лежит старая версия. `publish_bootstrap.py --check` при этом уже говорит «совпадает» —
верить ему, а не raw; иначе владелец запускает старый скрипт и получает уже исправленную
ошибку.

`stdin` при `curl | bash` — это труба: скрипт делает `exec </dev/tty`, иначе вопросы
`install.py` получат EOF. Для Hermes установщик вызывается с `--non-interactive`, когда
терминала нет (`HERMES_INSTALL_ARGS` переопределяет).

## Выбор флагов: TUI-чек-лист (`FlagMenu`)

Запуск без аргументов даёт не анкету вопросов, а чек-лист флагов — владелец не обязан помнить
имена ключей. Поведение: ↑/↓/j/k — курсор, пробел — галочка, Enter — экран подтверждения с
готовой командой, затем `Y` — сохранить выбор в `/etc/vps-infra/install-flags.json` и
выполнить, `n`/Enter — вернуться к списку (дефолт `n`, случайный ввод ничего не запускает),
`q` — выход с кодом 130. Строка списка — ровно в формате «Описание (--флаг)»; владелец
просил именно его, длинные пояснения в той же строке не лепить.

Реализация — сырой `termios` + ANSI-перерисовка на `/dev/tty`, без curses: stdout может быть
трубой (‑‑dry-run в тестах, пайпы), а tty открывается отдельными хендлами на чтение/запись.
Меню вызывается только при пустом `argv`: `bootstrap.sh` и вызовы с флагами идут мимо него.
Пары взаимоисключающих флагов (`--skip-restore`/`--restore`, `--yes`/`--reconfigure`) гасят
друг друга при включении. `VPS_MENU_PRINT=1` — режим самопроверки: печатает выбранный argv и
выходит, не запуская установку; только с ним TUI и можно тестировать безопасно.

**TUI проверять только pty-драйвером, а не `script`+pipe.** `printf ' \ry' | script -qec …`
висит: клавиши уходят в канонический режим до старта программы, а вывод размазан по
ANSI-перерисовкам. Рабочий способ — `pty.fork()`, `os.write` по одной клавише с паузой ~250 мс,
чтение с `select`, жёсткий таймаут и `kill` на выходе (скрипт-образец: `menu_drive.py` в
scratch; на живой прогон — `MENU_DRIVE_LIVE=1`, иначе он ставит `VPS_MENU_PRINT`).
Гонка на стрелках: ESC и `[B` приезжают раздельно, поэтому после ESC нужен `select` с таймаутом
~50 мс и дочитывание второго байта — без этого «вниз» иногда читается как «esc» и тест
показывает не тот флаг.

## Режимы

```bash
install.py                     # чек-лист флагов в TUI, затем обычный прогон
install.py --yes               # без вопросов, значения из существующих .env
install.py --reconfigure       # переспросить секреты (Enter = оставить как есть)
install.py --dry-run           # показать план, ничего не менять
install.py check               # read-only проверка живого стека
install.py export --with-data  # → /var/lib/vps-infra/vps-infra-bundle-*.tar.gz
install.py --bundle <path|url> --restore   # восстановление БД + webui_data
install.py --from-bot --restore --hermes --restore-hermes
install.py --skip tls,restore --only verify
install.py --secrets-from-bot --secrets-key /root/.secrets/offsite.key   # разложить .env из архива
install.py --secrets-archive <file.enc> --set WEBUI_URL=http://drill.local
install.py --bot-token … --file-bot-token … --hermes-token …             # тестовые боты
```

Шаги идут в фиксированном порядке, каждый идемпотентен:
`preflight → packages → users → stack → secrets → bundle → fetch → postgres →
network → images → migrate → restore → data → apps → notifications → beszel →
units → hardening → tls → verify → health → hermes → postcheck → report`.

**Перед необязательным компонентом — два шага, не один.** `health` (контейнеры, HTTP,
`webui_db`/`litellm_db`, Redis) валит прогон, если критичный сервис молчит; затем вопрос
«Установить Hermes?» с дефолтом «да» (ответ «нет» → `/root/.hermes-skip`, позже
`--only hermes --hermes`). Детали — `references/installer-pitfalls.md`.

**Финальный шаг `postcheck`.** Ставит одноразовый `hermes-postcheck.timer` (`OnActiveSec`,
по умолчанию `15min`, флаги `--postcheck-delay`/`--no-postcheck`): через 15 минут после
развёртывания `hermes-postcheck.sh` гонит `hermes chat --query-file … --oneshot -Q --yolo`
с промптом «проверь топологию» (контейнеры, HTTP, Postgres, nginx, TLS, таймеры, бэкапы,
диск, гейтвей), шлёт отчёт владельцу через `hermes send -t telegram -f report.md` и сам
себя выключает. Промпт обязан запрещать изменения (только чтение) и ограничивать отчёт
25 строками — иначе агент пришлёт простыню. Промпт не дублирует проверки текстом: он велит агенту прочитать `REPORT.md` в корне
репозитория и выполнить его раздел 1 — это единственный источник правды по чек-листу.
Правя проверки, править **REPORT.md**, а не промпт: иначе две копии чек-листа разъедутся.
`REPORT.md` — он же ручной ранбук: владелец передаёт его агенту фразой «проверь восстановление»
(раздел 2) или «проверь бэкапы» (раздел 3). Поэтому в самом `REPORT.md` обязательна оговорка:
прогон с `--skip-tls` не имеет nginx и сертификатов, такие пункты помечаются «шаг пропущен»,
а не «плохо» — иначе владелец читает дыру там, где её нет, и агент рапортует о поломке.

`--only`/`--skip` принимают имена шагов; неизвестное имя — ошибка.
`--skip preflight` вместе со `stack`/`secrets` разрешён и печатает, что
конфигурация берётся из уже существующих файлов.

**`hardening`** идёт до `tls`, ибо vhost'ы ссылаются на зоны: ставит fail2ban +
`python3-systemd`, пишет `/etc/fail2ban/jail.local` (sshd, `maxretry=4`/1ч, бан 1д,
инкремент до 4 недель, `ignoreip` включает 10/8 + 172.16/12 + 192.168/16 — иначе
забанит docker) и `/etc/nginx/conf.d/zz-ratelimit.conf` (`llm_api` 10r/s,
`webui_api` 8r/s, `conn_per_ip`) — **но 8r/s при `burst=30` мало для SPA**: одна загрузка Open WebUI стоит 40–60 запросов к `/api/`, второй F5 подряд уходит в 429 и страница выглядит «не открывается». На живом хосте поднято до `rate=20r/s` + `burst=120`; правя `install.py`, поднимай и там, иначе переустановка вернёт баг (`vps-network-exposure`, `references/fail2ban-and-rate-limits.md`). `vhost_ssl()` добавляет лимиты по порту
бэкенда: 4000 — server-level, 8080 — только `location /api/` (статика без
лимита, иначе F5 даёт 429 на чанках). Проверка: `install.py check` печатает
`fail2ban: active` и `nginx rate-limit: да`.

## Сбор секретов: интерактивный режим (v1)

`bootstrap.env` больше не обязателен. Нет файла → `bootstrap.sh` ставит `INTERACTIVE=1`,
спрашивает через `/dev/tty` токен файл-бота и пароль архива (`tty_ask`, скрытый ввод) и
запускает `install.py` **без `--yes`**, чтобы тот задал свои вопросы. Есть файл → прежний
автоматический режим (`--yes`).

`prompt()`/`confirm()` в `install.py` читают через `/dev/tty`, когда stdin не tty — иначе под
`curl | bash` они получали EOF и молча брали дефолты. `--yes` по-прежнему глушит вопросы;
интерактив включается только отсутствием `--yes`.

Финальный шаг `report` (`--no-report` отключает) собирает `.env` группами (ai / боты / Hermes),
шифрует `openssl enc -aes-256-cbc -pbkdf2 -iter 200000`, отправляет боту **документ**, затем
**ключ отдельным сообщением** с инструкцией по расшифровке и напоминанием удалить это сообщение.
Плейнтекст на диск не пишется — только в stdin `openssl`. Решения владельца: отчёт всегда
(флага «не отправлять по умолчанию» нет), отправляется после последнего шага; аудит топологии —
отдельный `postcheck`.

Осталось (не реализовано): реестр констант отдельным файлом (`constants.yaml`) с описаниями,
и первичная установка вообще без архива (сейчас минимум — архив в боте + пароль; без архива
`restore_secrets()` падает). План и открытые вопросы — `docs/installer-secrets-ux.md`.

## Правила, которые нельзя нарушать

1. **Секреты только в .env.** `install.py` генерирует внутренние ключи
   (`token_hex(32)`) и спрашивает внешние (OpenRouter, Telegram, GitHub).
   Существующие значения переиспользуются: повторный запуск не меняет
   пароли и не разлогинивает. `install.json` токенов не содержит.
   **Исключение — `UI_PASSWORD`:** прогон установщика заменил его на
   сгенерированное значение (8 → 64 символа), остальные секреты остались
   прежними. `UI_PASSWORD` — пароль админа **LiteLLM**, а не Open WebUI;
   бот `owui-signup-approver` читает его для входа в WebUI, поэтому после
   любого прогона проверяй, что «отклонить» в боте работает: `signin failed:
   HTTP 400` в `/var/log/owui-signup-approver.log` = рассинхрон пароля
   (разбор и починка — skill `credential-login-verification`,
   `references/open-webui-auth.md`).
2. **БД восстанавливаются только в «пустые» базы** или с явным `--restore`.
   Пустота определяется **по данным, а не по схеме**: шаг `migrate` идёт раньше `restore` и
   prisma-миграции LiteLLM создают ~98 пустых таблиц, поэтому проверка «есть таблицы → пропускаю»
   молча съедала восстановление (дамп не применялся ни разу, и это выглядело нормой).
   Считать строки в опорной таблице: `"LiteLLM_VerificationToken"` для `litellm_db`, `"user"`
   для `webui_db`; 0 строк → восстанавливать, >0 → только `--restore`.
   **Идентификаторы с заглавными буквами в psql обязаны быть в кавычках:** `SELECT count(*)
   FROM LiteLLM_VerificationToken` фолдится в нижний регистр и падает с `relation … does not exist`,
   так что зонд надо писать как `"LiteLLM_VerificationToken"` и вызывать с `check=False`, иначе
   отсутствующая таблица убивает прогон вместо того, чтобы дать «данных нет».
   Дамп старше 72 ч требует `--force-stale`. Bundle кладёт дампы в
   `backups/postgres/`, свежесть — по mtime.
3. **`:latest`-образы не обновляются**, если уже есть локально: повторный
   install не должен молча менять версии. **Образ сервиса, у которого в compose есть
   `build:`, не тянется из реестра — только собирается.** Такие теги (`esmien/webui:local`,
   `esmien/open-terminal-arduino:local`) в реестрах не существуют, и `docker pull` на чистой
   машине падает с rc=1. Список собираемых берётся из `docker compose config --format json`
   (`compose_build_targets()`), `pull` идёт только по внешним образам.
4. **Установщик не знает ни о каких сервисах вне репозитория.** Третий домен
   (`extra_domain`) опционален и по умолчанию пуст: он терминируется на этом же сервере
   и ведёт на open-terminal. Порт 8000 в стеке не публикуется, health open-terminal
   проверяется через `docker exec`. Если на хосте живёт сторонний сервис — это забота его
   собственного репозитория; в установщик такие упоминания не добавлять, он должен чисто
   разворачиваться на машине, где их нет.
5. Перед прогоном на живом сервере — `touch /var/lib/docker-autorecover/pause`,
   после проверки снять. Иначе детектор инцидентов поднимет агента.
6. `deploy.sh` из `/home/ai_service/ai-stack` исторический: не покрывает
   Hermes, бэкапы, мониторинг. Источник правды — этот репозиторий.
7. **Это recovery-артефакт для НОВОГО сервера, а не набор для раскатки на текущем.**
   Владелец ждёт правки в `/root/vps-infra`, а не деплой «сюда»: не предлагай
   установить новую версию установщика на живой хост по умолчанию. Если фича
   всё же требует живого изменения (например, без правки `monitor.py` бэкап не
   пишет `file_id` и автоматическое восстановление невозможно) — объясни это
   одной фразой, назови минимальный дифф и спроси разрешение отдельно, отделяя
   «что лежит в репозитории» от «что будет работать здесь».

## Переезд (проверенный порядок)

1. Одной командой: положить `bootstrap.env` (GITHUB_TOKEN, SECRETS_KEY, TG_FILE_TOKEN + тестовые
   токены ботов) и запустить `curl … | sudo bash` — режим восстановления задаётся самим файлом;
   дополнительные флаги — через EXTRA_ARGS в нём.
   `fetch` берёт последний набор дампов из файл-бота (реестр `file_id` → части →
   склейка → sha256), `hermes` + `--restore-hermes` разворачивает состояние из
   `Esmien/hermes-state` (config/SOUL/memories/skills/cron, `/usr/local/bin`,
   юниты, `/etc`, runbooks). Секреты тоже восстанавливаются: `--secrets-from-bot --secrets-key …`
   скачивает архив и раскладывает все четыре `.env` по местам; без этих флагов они спрашиваются заново.
2. Ручной путь (fallback): `install.py export --with-data` → перенос →
   `--bundle <path> --restore`.
3. DNS доменов → IP нового сервера **до** шага TLS, иначе certbot пропустит
   домен (оставит HTTP-vhost) — это не ошибка.
4. Первого админа Open WebUI на пустой БД создают через форму регистрации;
   на восстановленной БД пользователи уже есть.

### Прогон восстановления на чистой машине

Полный e2e без TLS делается на отдельной виртуалке, а не на живом хосте: Multipass с Ubuntu
24.04, клон репозитория с GitHub, `--secrets-from-bot` (архив `.env` раскладывается сам, руками
копировать нечего), все сторожа и Hermes поднимаются на **тестовых** токенах ботов.
Команды, чек-лист «что считается успехом» и грабли — [references/restore-drill.md](references/restore-drill.md).

Жёсткие правила этого класса работ: ничего не переносить руками кроме зашифрованного архива
секретов; живые токены ботов в прогон не давать (второй поллер крадёт `getUpdates` у боевого);
пропускается только TLS — остальные шаги идут как в бою.

### Бэкап БД через бота: как устроено и где ломается

- Бот **не читает свою историю чата**, поэтому единственная зацепка для
  восстановления — `file_id`, который вернул `sendDocument`. `monitor.py backup`
  пишет его в `backups/postgres/.tg-registry.json` (3 набора на базу), реестр
  уезжает в `hermes-state` как `host/backups/tg-registry.json`.
- Части дампа обязаны быть **≤18 МБ** (`TG_DOC_LIMIT = 18 MiB` в `monitor.py`):
  `getFile` отдаёт не более 20 МБ, части по 45 МБ из чата уже не скачать.
- Нет реестра — fallback `getUpdates`: переслать файлы бэкапа самому боту.
- `--from-bot` игнорирует проверку «дамп старше 72 ч» (источник выбран осознанно).
- Токен проверяется на форму `123456:AA…`: заглушка из `install.json`
  (`__stored_in_notifications_env__`) даёт понятную ошибку, а не 404 от Telegram.
- **Файлы пользователя едут отдельно от БД.** Псевдо-база `webui_data` в том же
  реестре — это tar.gz `uploads` + `generated_images` (~980 МБ, 55 частей), её
  пишет `webui-data-backup.timer` (Sun 04:00 UTC). `RESTORE_DBS` включает её
  (`webui_db`, `litellm_db`, `webui_data`), шаг `data` распаковывает архив в
  `WEBUI_DATA` (пропускает непустой каталог без `--restore`). Без этого шага
  bootstrap вернёт БД и конфиги, но не оригиналы файлов Knowledge.

### Beszel, внешний мониторинг, TLS

- **Beszel** (шаг `beszel`): hub+agent в Docker, `/home/ai_service/beszel`,
  hub только на `127.0.0.1:8090` (наружу — через `mon.` vhost), связка через
  unix-сокет `beszel_socket/beszel.sock`, вместе ~20 МБ RAM. Без UI
  настраивается целиком через PocketBase API; `KEY` — публичный ключ хаба,
  `TOKEN` — UUID из `fingerprints` (без него агент вечно ловит 401), alerts
  (Status/CPU/Memory/Disk) создаются только вручную. Команды и грабли —
  [references/beszel-and-monitoring.md](references/beszel-and-monitoring.md).
- **Внешний контур**: `.github/workflows/uptime.yml` (cron `*/10`, curl `ai.` и
  `llm.`, 3 попытки → Telegram), дрилл через `workflow_dispatch` с
  `extra_url=https://httpbin.org/status/500` (сообщение с префиксом `[ТЕСТ]`).
  GitHub гасит `schedule` в публичном репо после 60 дней без активности —
  поэтому `uptime-heartbeat.timer` раз в месяц дописывает
  `maintainer/uptime-heartbeat.txt`. Второй контур healthchecks.io:
  `deadman-ping.sh` + таймер, ping-URL в `/etc/deadman-ping.url`.
- **TLS:** один wildcard `*.esmien.ru` (плюс apex), выпущенный через **DNS-01 Cloudflare** (`esmien-wildcard`, токен `/root/.secrets/cf.ini` 0600, плагин `certbot-dns-cloudflare`, хук продления перезагружает nginx). Новый поддомен = DNS-запись + vhost, certbot больше не запускается, квота Let's Encrypt больше не упирается. Старая зона `qd.je` **выведена из эксплуатации**: её DNS-провайдер перестал отвечать, vhost'ы и сертификаты удалены — не возвращай их в `legacy_hosts` и не чини их certbot'ом. Упор в квоту был нормой для неё, самописные ретрай-таймеры не ставить (решение владельца): выпуском занимается только `certbot.timer`.

## Проверка

**Любую правку установщика проверять на самом чистом доступном субстрате** — контейнер той
же Ubuntu для путей apt/пакетов/ключей, Multipass для полного прогона — и только потом
говорить владельцу «перезапускай». Фраза «должно работать» здесь не принимается: два
последовательных падения на чистой машине уже стоили доверия к прогону.

**Прогон, который лечили руками, не считается проверенным.** Если после установки пришлось
дописать хук, починить владельца каталога или обновить юнит вручную, это не валидация
сценария — это отладка на живой машине. Число ручных правок = число причин для одного
чистого прогона с нуля; итог формулировать так: «данные восстановлены, сценарий — нет».
И наоборот: правки, сделанные в репо **после** того, как машина склонировала репозиторий,
в текущем прогоне не участвуют — перед проверкой новой версии всегда `git fetch && reset`
(это делает и `bootstrap.sh`), иначе тестируется старый коммит.

`install.py check` печатает контейнеры/health, число таблиц, локальные HTTP,
https-коды доменов и число активных таймеров, ничего не меняя.
Он покрывает только машинную часть; полноценный чек-лист приёмки (TLS, доставка уведомлений,
свежесть и восстановимость копий, периметр, Hermes) — **`REPORT.md`**, раздел 1.
Второй прогон `--yes` должен показывать «стек уже актуален / .env без изменений»
и укладываться в ~15 с; если он что-то «синхронизирует» — расхождение
репозитория и хоста.

**Проверка `--from-bot` без трафика в Telegram** — `scripts/mock-botapi.py`:
поднимается локальный Bot API (`sendDocument`/`getFile`/`getUpdates`), и тест
проходит весь путь «загрузка → реестр → скачивание → склейка → sha256», включая
отказ на части >20 МБ, не отправляя ни одного файла владельцу. Обязательные
кейсы: путь через реестр, fallback `getUpdates`, guard 20 МБ, заглушка токена.
Живой drill (настоящий Telegram) — отдельно и по разрешению: либо `--infra-dir /tmp/<name>`,
либо полноценный прогон на отдельной виртуалке (см. «Прогон восстановления на чистой машине»).

## Авто-коммит и пуш (копия логики hermes-state)

Репозиторий обновляется сам по факту правки, без таймера:

| item | path |
|---|---|
| watcher | `maintainer/vps-infra-watch.sh` → `/usr/local/bin/`, unit `vps-infra-watch.service` |
| one-shot | `maintainer/vps-infra-push.sh` → `/usr/local/bin/`, unit `vps-infra-push.service` |
| sync хоста → assets | `maintainer/sync_assets.py` (без `.env`, тестов, `__pycache__`, `_state_snapshot`, `out`) |
| lock / лог | `/var/lib/vps-infra-autopush/push.lock`, `/var/log/vps-infra-autopush.log` |

Перед коммитом push-скрипт **валидирует** дерево (`py_compile install.py`,
`bash -n bootstrap.sh`, `docker compose config -q` на фиктивных секретах) и
сканирует на секреты — при находке коммит отменяется. Коммит — только при
реальных изменениях; push с catch-up и алертом в TG (троттлинг 30 мин).

- Правка `maintainer/*.sh|service` в репо не действует, пока не сделан
  `install -m 755 … /usr/local/bin/` + `systemctl daemon-reload` (сами себя
  скрипты не копируют).
- **Обратное направление тоже забывается.** `sync_assets.py` ведёт только
  `assets/host/*`, поэтому правка живой копии `/usr/local/bin/vps-infra-push.sh`
  в `maintainer/` сама не попадёт — скопировать обратно и запушить. И не у каждого
  боевого скрипта есть зеркало в репо вообще (`kb-sync.py`, `hermes-postcheck.sh`
  отсутствуют): после правки искать `find . -name <файл>` и при отсутствии либо
  положить в `assets/host/bin/`, либо сказать вслух, что файл вне recovery-контура.
- После установки — `systemctl enable --now vps-infra-watch`; старт сервиса
  делает догоняющий пуш.
- Быстрый тест без 90-секундного дебаунса:
  `QUIET=5 WATCH_LOG=/tmp/w.log /usr/local/bin/vps-infra-watch.sh &`, затем
  тронуть любой файл, подождать ~10 с и проверить `git -C /root/vps-infra log`.
- Синхронизация идёт только host → repo. Обратно (repo → живой стек) —
  только через `install.py`; не путать.
- **«no changes — origin is up to date» не значит «не запушено».** Watcher коммитит сам в
  течение ~90 с после правки, поэтому ручной `vps-infra-push.sh` может не найти изменений.
  Прежде чем говорить владельцу про версию, смотреть `git log --oneline -3` и наличие
  правки в файле (`git show <commit> --stat` или поиск строки в файле), а не вывод пуша.
- **Ручной `git commit` не будит watcher.** inotify слушает рабочее дерево, а не `.git`,
  поэтому закоммиченное вручную изменение может лежать локально неограниченно долго:
  в логе видны только `event: MODIFY` до коммита, а `push ok` — от прошлого прогона.
  После своего коммита запускать `systemctl start vps-infra-push.service` и проверять факт
  доставки через API (`/repos/<owner>/<repo>/commits?per_page=1` и `contents/<file>`), а не
  по коду возврата. `raw.githubusercontent.com` после пуша до ~5 минут отдаёт CDN-копию.
  Прямой `git push` из `/root/vps-infra` не проходит: кредов в клоне нет, ответ
  `fatal: could not read Username for 'https://github.com'`. Пуш — только юнитом
  `vps-infra-push.service` (он ходит через askpass/токен), прямой пуш не «починить», а обойти.
- Манифест синхронизации — сами файлы в `assets/host/{bin,systemd}` и
  `assets/host/open-terminal-config`. Новый скрипт/юнит появляется в репо
  только после того, как его туда положили; удалённый с хоста файл из репо
  не исчезает (удаления не пропагируются сознательно).
- **Таймер без своего `.service` не стартует:** `systemd` пишет `Refusing to
  start, unit X.service to trigger not loaded`, а `enable --now` при этом молча
  падает (`check=False`). `step_units` теперь сам добавляет `<name>.service`
  для каждого таймера, если такой файл есть в `assets/host/systemd/`. Симптом
  после добавления таймера в `CORE_TIMERS`: `is-enabled` = enabled,
  `is-active` = inactive.
- **Скопированный юнит не значит включённый.** `install_units()` раскладывает файлы из своего
  списка, а `enable` идёт по **отдельному** явному перечню: юнит, который лежит в `HERMES_UNITS`,
  но не назван в списке включения, окажется в `/etc/systemd/system` и не запустится — таймер
  молчит, `.path` не следит, и владелец узнаёт об этом только по отсутствию сообщений. После
  добавления таймера или `.path` проверять `systemctl is-active` и `systemctl list-timers`, и
  только потом говорить, что автоматика стоит. Обратное тоже верно: юнит, которому нужен секрет,
  не создаваемый установщиком, в `CORE_TIMERS` не ставить — на чистой машине он будет падать
  с трейсбеком; его место в блоке харнесса.

## Подводные камни (самые дорогие)

- **Маска токена не должна вернуться в `.env`.** `save_config()` пишет в
  `install.json` заглушку `__stored_in_notifications_env__`, а `prompt()` брал
  значение из cfg раньше, чем из `notifications/.env` — прогон `--yes` записал
  заглушку как `BOT_TOKEN`/`FILE_BOT_TOKEN` и убил оба бота до повторного
  выпуска токенов в BotFather. Исправлено; симптом для диагностики — `Telegram
  API HTTP 404`, а длина значения в `.env` (~31 символ) не похожа на токен.
- **`notifications/.env` обязан быть `0640 root:ai_service`.** `write_file` без
  `chown` оставил `root:root`, и `postgres-backup-notify.service`
  (`User=ai_service`) падал с `PermissionError`, при этом таймер «успешно» шёл.
- **Правки `assets/` затираются `sync_assets.py`** (host → repo): пока
  `vps-infra-watch.service` активен, изменённый `assets/notifications/monitor.py`
  вернётся к живому файлу через ~90 с. Правь репозиторий при остановленном
  watcher'е и деплой живые копии до пуша. Для `assets/host/{bin,systemd}` порядок жёсткий:
  источник правды — живая копия в `/usr/local/bin` / `/etc/systemd/system`, поэтому сначала
  правится она, потом `python3 maintainer/sync_assets.py` переносит её в репо. Патч только в
  `assets/host/bin/*.sh` выглядит успешным (push проходит), но следующий sync возвращает
  старую версию — симптом: правка «исчезла» из репо без отката. Обратный порядок тоже
  обманывает: `install -m 755 assets/host/bin/x.py /usr/local/bin/` после такого синка
  ставит уже откатанную версию, и прогон «проходит» на старом коде. После деплоя проверять
  маркер в живой копии (`grep -c '<новая строка>' /usr/local/bin/x.py`), а не факт успешного
  `install`.
- **`/etc/vps-infra/install.json` помнит прошлый `--infra-dir`.** Тестовый прогон оставляет там
  путь вида `/tmp/drill-bot`, и следующий запуск без `--infra-dir` читает `.env` из пустого
  каталога: `preflight` видит пустое окружение, шаблон падает с «в шаблоне не заполнены: […]».
  Перед любым прогоном сверять `infra_dir` в этом файле с `/home/ai_service/ai-stack`.
- **Ключ, которого нет в шаблоне, при восстановлении исчезает молча.** `step_secrets` рендерит
  `.env` из `assets/templates/ai.env.tmpl`, поэтому любой ключ живого `.env` вне шаблона теряется
  (так пропадали `ENABLE_DIRECT_INTEGRATIONS` и `OPEN_TERMINAL_SANDBOX_API_KEY` — ломалась
  песочница в WebUI). Перед прогоном: рендер шаблона значениями живого `.env` и сверка набора
  ключей — расхождений быть не должно.
- **Бэкап `.env` внутри синхронизируемого дерева = секрет в репозитории.**
  `sync_assets.py` исключает ровно имя `.env`, поэтому копия вида
  `.env.bak-<повод>` фильтр проезжает и уезжает в `assets/stack/`. Дальше
  `vps-infra-push.sh` сканирует дерево и обрывает процесс с «secret-like
  string(s) in repo» — пуш не проходит (скан идёт ДО `git add`, так что в
  историю ничего не попадает), но файл с ключами уже лежит в рабочей копии.
  Правило: бэкапы секретов держать ВНЕ синхронизируемых каталогов
  (`/root/private-backups/`, 600), а исключение расширить до «всё, что
  начинается на `.env`, кроме `.env.example`». Заодно: `.env.bak-*`, созданный
  рядом с `.env` при правке через скрипт, наследует его права не всегда —
  бэкап с `644` читаем всем пользователям системы.
- **`curl | bash` забирает stdin:** bootstrap делает `exec </dev/tty` последней
  командой, иначе вопросы install.py получают EOF. Проверять tty надо в
  субшелле `( exec 3</dev/tty )`, иначе падает при запуске без терминала.
- **Секреты раскладываются до создания пользователя.** `restore_secrets()` вызывается перед
  шагом `users`, поэтому `chown` на `ai_service` там ещё невозможен: ловить `LookupError`
  (а не только `KeyError`), запоминать пути и дожимать владельца в `step_users`. На чистой
  машине падение на этом `chown` — не «сломанный архив», а порядок шагов.
- **Зонды и apt не имеют права убивать прогон.** `run(..., check=False)` на отсутствующем
  бинарнике возвращает rc=127, а не `die()`; необязательные бинарники проверять через
  `shutil.which()`. Сторонний apt-репозиторий чинится одним самовосстанавливающимся
  `apt_update()`: бинарный keyring через `gpg --dearmor`, ретраи на рассинхрон зеркала,
  чистка только своих `/var/lib/apt/lists/*pgdg*`, http вместо https при зависшем кэше
  Fastly. Диагностика и проверка в чистом контейнере —
  [references/apt-and-fresh-host.md](references/apt-and-fresh-host.md).
- **Hermes: бинарь в PATH и живой гейтвей — проверять, а не предполагать.** Установщик кладёт
  бинарь в `~/.local/bin`/`~/.hermes/...`, PATH root там пуст — линковать в `/usr/local/bin`
  (`ensure_hermes_shim()`); гейтвей поднимать только после `list-unit-files`/`pgrep`, иначе
  `systemctl --user restart` под `check=False` даёт ложное «перезапущен». Детали —
  `references/installer-pitfalls.md` → «Hermes после установки».
- **Проверка наличия и путь в сгенерированном скрипте должны совпадать.** `step_postcheck` проверял
  `shutil.which("hermes")` (на хосте это `/root/.local/bin/hermes`), а в тело `hermes-postcheck.sh`
  писал жёсткий `/usr/local/bin/hermes` — проверка проходила, скрипт падал на `No such file or
  directory`, отчёт оставался пустым и в Telegram не уходил. Правило: если генерируемый файл
  вызывает бинарь по абсолютному пути, этот же путь и резолвить при генерации
  (`hermes_bin = "/usr/local/bin/hermes" if Path(...).is_file() else shutil.which("hermes")`)
  и подставлять шаблоном; `which()` как единственный guard — не доказательство, что жёсткий путь жив.
  Симптом в готовом виде: юнит oneshot = inactive/disabled (скрипт сам себя выключил), а в
  `/var/lib/<name>/report.md` — одна строка с `No such file or directory`.
- **`set -Eeuo pipefail` + необязательная переменная = `unbound variable` в самом конце прогона.**
  `bootstrap.sh` делал `export GITHUB_KEY="$GITHUB_TOKEN"`, а токен теперь необязателен: прогон
  падал уже после клона репозитория и записи ключа архива, и владелец видел установку, оборвавшуюся
  на 157-й строке. Любая необязательная переменная читается как `${VAR:-}` — в том числе в
  экспорт-строках и в `&&`-цепочках. Проверка: исполнять фрагмент под тем же `set -Eeuo pipefail`
  и пустым окружением, а не только `bash -n` (синтаксис такой строки валиден).
- **Креды не вписывать в URL строкой `${TOKEN}@host`.** Такая строка при записи файла
  попадает под маскировку секретов и превращается в обрубок (`x-access-token:${GITH.../}`),
  файл остаётся синтаксически валидным для `bash -n`, а на чистой машине падает
  `bad substitution` при клоне. Авторизация — заголовком:
  `git -c http.extraheader="Authorization: Basic $(printf '%s' "x-access-token:$TOKEN" | base64 -w0)"`;
  проверять не `bash -n`, а исполнением фрагмента с подставным токеном.
- **Вопрос про Hermes не должен зависеть от флага `--hermes`.** Условие «спрашивать, только если
  `args.hermes is None`» означало, что `bootstrap.sh`, который всегда передаёт `--hermes`, проходил
  шаг молча — владелец видел установку агента без своего участия. Спрашивать всегда, кроме явного
  `--no-ask-hermes` (для автоматизации); ответ «нет» пишет `/root/.hermes-skip` и выходит до
  восстановления состояния. Проверка — под настоящим pty (`script -qec …`), а не в не-tty:
  без терминала `ask()` молча возвращает дефолт «да», и пропуск вопроса выглядит как норма.
- **`psql` по имени — это perl-обёртка `pg_wrapper`.** `/usr/bin/psql` →
  `/usr/share/postgresql-common/pg_wrapper`; под `sudo -u postgres` на минимальной ВМ она даёт
  `unable to execute /usr/bin/psql: Permission denied`, хотя кластер `online` и сервис `active
  (exited)`. Ходить прямо в `/usr/lib/postgresql/<ver>/bin/psql` (хелпер `pg_bin()`), иначе
  readiness-проверка и все SQL-вызовы падают на здоровой базе. При таймауте ожидания писать в
  лог `pg_lsclusters`, `systemctl status postgresql`, хвост `journalctl -u postgresql@<ver>-main` —
  по одной строке «не отвечает» причину не угадать.
- **После восстановления состояния скиллы надо сверять, а не дополнять.** Официальный
  установщик Hermes сеет десятки демо-скиллов (`slackbot`, `xurl`, `arxiv`, `automation`,
  `general`, `software`); `restore_tree` их не удаляет, и в списке рядом с нашими висят
  чужие. `quarantine_extra_skills()` после раскладки рекурсивно сверяет `~/.hermes/skills`
  с восстановленным набором и переносит лишнее в `~/.hermes/skills_removed/<дата>/` (не
  удаляет). Ожидаемый набор: 30 `SKILL.md` в 15 категориях, 5 категорий пустые; на Linux
  не показываются `apple` (macOS-only).
- **Домашний каталог `ai_service` тоже должен принадлежать ему.** `mkdir -p` для
  `/home/ai_service/ai-stack` создаёт родителя как `root`, и в списке каталогов `step_users`
  его не было: получается `700 root:root`, `postgres-backup.service` (`User=ai_service`)
  падает с `203/EXEC` на собственном скрипте, а таймер при этом «успешно» идёт — новых
  дампов просто нет. `AI_HOME` обязан идти в списке с владельцем `ai_service` и `0755`;
  проверка — `stat -c '%U:%G %a' /home/ai_service`.
- **`TimeoutStartSec` юнита не может быть короче суммарных ожиданий скрипта.**
  `hermes-boot-notify.sh` ждёт до 600 с (60 сеть + 180 гейтвей + 240 контейнеры), а юнит стоял
  на 300 с — на медленной чистой машине systemd убивал его и уведомление о загрузке не уходило.
  Складывать все sleep-циклы и брать таймаут с запасом; путь к бинарю внутри скрипта —
  с фолбэком (`command -v hermes`), а не один жёсткий `/root/.hermes/hermes-agent/...`.
- **`--only hermes` без `--restore-hermes` ничего не восстанавливает.** Флаг выставлялся
  только анкетой preflight, поэтому «дожать шаг» на уже собранной машине молча проверял
  наличие бинаря и выходил. Теперь явный `--only hermes` означает «развернуть состояние»
  (отключается `--no-restore-hermes`); в инструкции владельцу всё равно писать флаг явно.
- **Хуки из `config.yaml` после восстановления проверять обязательно.** `check_agent_hooks()`
  идёт сразу после раскладки состояния: чинит бит исполнения, CRLF и shebang, а если файла нет —
  сначала пробует шаблон, затем тянет рабочий файл из `raw.githubusercontent.com/<repo hermes-state>`.
  Отключение `fail_closed`-хука — крайний случай (нет ни файла, ни шаблона): это открывает
  доступ тем, кого гейт ограничивал, поэтому в лог и владельцу пишется явно, а `config.yaml`
  бэкапится в `config.yaml.bak-hooks`. Никогда не оставлять в `agent-hooks/` шаблон с
  `RESTRICTED_USERS = {"000000000"}`: такой гейт «активен», но не ограничивает никого.
- **`WEBUI_URL` зависит от режима TLS.** Без домена (прогон `--skip-tls`) ссылка
  `https://<ai_domain>` ведёт в никуда: установщик пишет `http://<ip-машины>:8080`, адрес берёт
  из `hostname -I`. Симптом у владельца: «url к вебуи старый/мёртвый» после восстановления.
  Живой `.env` правится точечно (`sed -i "s#^WEBUI_URL=.*#…#"`) — повторный `--only secrets`
  без preflight вернёт старое значение из архива.
- **Вопрос из скрипта — только через `/dev/tty`, и двумя `open()`.** При `curl | bash`
  stdin это труба (`input()` даёт EOF), а `open('/dev/tty','r+')` падает с
  `UnsupportedOperation: not seekable`. Читать и писать отдельными хендлами; при
  отсутствии tty возвращать дефолт. Перед вопросом закрывать панель прогресса (`PANE.finish()`).
  То же касается не только `ask()`/`confirm()`, но и `prompt()`: без tty-ветки интерактивный
  режим под `curl | bash` не работает вообще — вопросы молча заменяются дефолтами.
  Проверка — под pty с трубой на stdin: `echo 'x' | script -qec "printf '' | python3 probe.py" /dev/null`,
  в пробе печатать `sys.stdin.isatty()` (должно быть `False`) и результат `prompt()`.
- **Токен — необязательный, но если он есть — с доступом к нужному репо.** Репозитории
  публичные, поэтому клон и реестр работают без токена; fine-grained токен, выданный
  только на `vps-infra`, на чужой приватный репо отвечает **404, а не 403**, и любой
  fallback на `getUpdates` даёт пустоту (Telegram не отдаёт сообщения старше 24 ч).
  Причины и разбор всех токенов прогона —
  [references/restore-drill.md](references/restore-drill.md) и
  [references/installer-pitfalls.md](references/installer-pitfalls.md).
