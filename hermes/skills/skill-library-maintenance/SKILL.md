# Maintaining this profile's skills

## When to Use

Недельный аудит самописных скиллов, «скилл разросся», «разбей на references»,
«почему SKILL.md стал оглавлением», правка своего скилла после провальной
задачи.

## Форма, к которой приводим

- `SKILL.md` — то, что нужно при **каждом** применении: триггер, порядок шагов
  с командами, гейты, самые дорогие грабли, указатели на глубину.
- `references/<тема>.md` — глубина, нужная иногда: разборы, таблицы решений,
  точные значения, длинные процедуры.
- `scripts/` — то, что запускается, а не перепечатывается каждый раз;
  `templates/` — заготовки для копирования.

## Главное правило

**После разбиения по одному `SKILL.md` должно быть можно выполнить типовую
задачу класса, не открывая references.** Если в нём остались только ссылки —
работа не сделана, это оглавление, а не скилл.

## Процедура

1. Найди исходник до правки: `git -C /var/lib/hermes-state/repo log --oneline -- <path>`
   (или `git show <commit>:<path>`). Без исходника «сравнил и перенёс» — самообман.
2. Выпиши смысловые блоки старой версии и реши, где каждый живёт.
3. Режь по темам, а не по размеру: один reference = одна тема (firewall, VPN-ingress,
   install-pitfalls). Не «часть 1/2» и не по одному файлу на инцидент.
4. **Переноси текст, а не пересказ.** Команды, значения, последовательности
   сохраняются дословно; сжимать можно только воду. Пересказ теряет именно то,
   зачем скилл существует.
5. Проверь программно: все `](references/…)` и якоря существуют, размеры в норме,
   `SKILL.md` не потерял ни одного исходного раздела по смыслу.
6. Отчитайся таблицей «было → стало» по файлам и перечнем того, что перенесено.

## Грабли

- **Описание нового скилла — жёсткий лимит 60 символов.** Формула: `Use when <триггер>.` Длиннее — создание отклоняется («must fit the 60-char system-prompt budget»), а вместе с ним откатывается весь батч `skill_manage`. Детали триггера уводи в тело, в описание — только когда скилл нужен.
- **Батч `skill_manage` атомарен.** Любая упавшая операция отменяет и уже применённые в этом же вызове — после ошибки перечитывай файл и выдавай батч заново, а не «допатчивай остаток».
- **Линтер скиллов ругается на два конкретных места:** нет секции `## When to Use` у самого верха и «dangling-reference» — если в тексте упомянут файл из `references/`, которого нет в каталоге этого скилла. Чужой справочник ссылай прозой: «справочник по X есть в скилле `Y`».
- **Серия мелких патчей плодит дубли.** После нескольких итераций по одному скиллу перечитай его целиком (`skill_view`) и склей повторы: одно правило — одно место, иначе следующая правка исправит только одну копию.
- **Уложиться в лимит — не цель.** Жёсткий предел `SKILL.md` (100k) — аварийный
  порог; нормальный размер — с запасом ниже ~15k. Файл на 14.9k символов,
  который прошёл проверку, остаётся плохим результатом.
- **Пересказ вместо переноса** — самая частая поломка: команды и точные значения
  исчезают, остаются общие фразы.
- **Битая ссылка ломает навигацию молча** — проверяй существование файлов и
  якорей, а не «выглядит нормально».
- **Одно правило — в одном месте.** В `SKILL.md` указатель, в reference — текст;
  копия в обоих разъезжается при следующей правке.
- **Не создавай reference на инцидент.** Файл называется темой и переиспользуется;
  «<дата>-<случай>.md» — признак, что ты пишешь лог, а не скилл.
- **`patch` по большому блоку падает, если разбивка строк в файле другая.**
  Бери `old_string` из свежего `read_file`/`skill_view`, а не из памяти сессии:
  один лишний перенос — и правка молча не применится.
- Крупную механика-переработку можно отдать фоллбэк-модели
  (`hermes chat --oneshot -m <model> --provider <provider> -q '…'`, фоном +
  `process wait`), но в задании требуй: сверку с исходником по git, сохранение
  практического ядра в `SKILL.md` и отчёт об утраченном. Без этого она просто
  сократит текст.

## Порядок работы с владельцем

Он ждёт результат за один заход, а не серию «сделал — продолжать?». Согласованный
план выполняй целиком, отчёт — в конце, разницей «было → стало».
